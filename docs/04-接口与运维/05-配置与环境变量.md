# 配置检查 Runbook

## 1. 适用范围

修改主 YAML、环境变量、Options、Secret、cache policy、Event Catalog、gRPC ACL、证书路径或部署挂载时执行。本页只给检查步骤；配置分层、外部文件和 fail-closed 语义以[配置、Secret 与外部文件](../03-基础设施/config-deployment/10-配置、Secret与外部文件.md)为准。

## 2. 仓库侧预检

```bash
git rev-parse HEAD
git diff --check
go test -count=1 \
  ./internal/pkg/configcontract \
  ./internal/pkg/options \
  ./internal/pkg/grpc \
  ./internal/apiserver/options \
  ./internal/collection-server/options \
  ./internal/worker/options
bash scripts/cd/test-prepare-package.sh

for service in apiserver collection worker; do
  make cd-validate SERVICE="$service"
done
```

预期：配置/ACL/外部文件契约、部署包回归和三个服务的 CD metadata 全部退出 0。未知字段、废弃键、必填值缺失、ACL 非 default-deny 或被启用能力所需文件缺失时必须停止，不能补一个宽松默认值绕过。

## 3. 展开部署配置

在受控主机使用本次实际 env file 展开 Compose；输出含敏感环境信息时只能写入权限为 0600 的临时文件，并在提取脱敏 hash 后安全删除：

```bash
umask 077
export COMPOSE_FILE='build/docker/docker-compose.prod.yml'
export COMPOSE_ENV_FILE='/replace/with/authorized/config.prod.env'
export EFFECTIVE_COMPOSE_FILE="$(mktemp)"
trap 'rm -f "$EFFECTIVE_COMPOSE_FILE"' EXIT

docker compose \
  --env-file "$COMPOSE_ENV_FILE" \
  -f "$COMPOSE_FILE" \
  config >"$EFFECTIVE_COMPOSE_FILE"
shasum -a 256 "$EFFECTIVE_COMPOSE_FILE"
```

不要把原始展开文件、DSN、token、私钥或明文 Secret 上传到 CI artifact/工单。证据只记录 hash、Secret 是否存在及其轮换版本、非敏感 endpoint/开关/预算的脱敏摘要。

## 4. 容器内文件与有效值

对本次服务逐项检查主配置、cache policy、Event Catalog、gRPC ACL 和证书是否真实挂载且权限符合预期：

```bash
export COMPOSE_SERVICE='replace-with-compose-service'
export MAIN_CONFIG='/app/configs/replace-with-main.prod.yaml'

docker compose -f "$COMPOSE_FILE" exec -T "$COMPOSE_SERVICE" \
  sh -ceu 'test -r "$1"; stat "$1"' sh "$MAIN_CONFIG"
```

再从该实例启动日志或受保护的治理入口取得 masked effective config，核对本次变更项与仓库/部署覆盖一致。只看 `configs/*.prod.yaml`、workflow variable 或 Compose `command` 都不能证明进程实际读取了该值。

以下项目有变化时必须逐项采证：

- 数据库、Redis、MQ、IAM endpoint 与 TLS/mTLS；
- gRPC ACL 文件、default policy 和 workload identity；
- scheduler、retry governance、backpressure、queue/pool 与租约；
- metrics/profile/governance listener 和网络限制；
- migration、one-off、repair/replay 开关；
- 日志 level/format/development 与敏感字段脱敏。

## 5. 正反向验证

1. 正向：三个进程都能读取所需文件、完成 Options 校验并启动预期 listener；
2. 反向：临时移除非生产测试环境中的必需文件或提供无效 ACL，确认启动 fail closed；
3. Secret：确认日志和 artifact 中没有明文值，CLI flag 未携带 Secret；
4. 漂移：比较本次 source SHA、镜像 digest、effective-config hash 与部署计划；
5. 回滚：确认旧镜像能否读取已执行 migration 和当前配置；不能只准备旧 tag。

## 6. 失败处置与完成标准

- 文件不可读：修挂载、owner/mode 或路径，不复制 Secret 到镜像临时绕过；
- 配置解析/校验失败：修生成源和部署包，不降级成开发配置；
- 目标值与启动值不同：查 flag/env/YAML 优先级并重新生成脱敏证据；
- ACL/证书失败：保持服务不接流量，不关闭 mTLS/default-deny；
- 无法取得 effective config：本次配置验收记为未完成，不以 repo YAML 代替。

完成记录必须绑定命令、结果、source/deployed SHA、镜像 digest、effective-config hash、owner、限制和失效期；环境/生产结果写入[基础设施生产证据台账](../00-总览/10-基础设施生产证据台账.md)。
