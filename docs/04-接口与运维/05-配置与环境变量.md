# 配置检查 Runbook

## 1. 适用范围

修改主 YAML、环境变量、Options、Secret、cache policy、Event Catalog、gRPC ACL、证书路径或部署挂载时执行。本页只给检查步骤；
配置分层、外部文件和 fail-closed 语义以[配置、Secret 与外部文件](../03-基础设施/config-deployment/10-配置、Secret与外部文件.md)为准。

## 2. 仓库侧预检

```bash
git rev-parse HEAD
git diff --check
go test -count=1 \
  ./internal/pkg/configcontract \
  ./internal/pkg/options \
  ./internal/pkg/grpc \
  ./internal/apiserver/options \
  ./internal/collection-server/options \
  ./internal/worker/options
bash scripts/cd/test-prepare-package.sh

for service in apiserver collection worker; do
  make cd-validate SERVICE="$service"
done
```

预期：配置/ACL/外部文件契约、部署包回归和三个服务的 CD metadata 全部退出 0。未知字段、废弃键、必填值缺失、ACL 非 default-deny 或被启用能力所需文件缺失时必须停止，不能补一个宽松默认值绕过。

## 3. 展开部署配置

在受控主机使用本次实际 env file 展开 Compose；输出含敏感环境信息时只能写入权限为 0600 的临时文件，并在提取脱敏 hash 后安全删除：

```bash
umask 077
export COMPOSE_FILE='build/docker/docker-compose.prod.yml'
export COMPOSE_ENV_FILE='/replace/with/authorized/config.prod.env'
export EFFECTIVE_COMPOSE_FILE="$(mktemp)"
trap 'rm -f "$EFFECTIVE_COMPOSE_FILE"' EXIT

docker compose \
  --env-file "$COMPOSE_ENV_FILE" \
  -f "$COMPOSE_FILE" \
  config >"$EFFECTIVE_COMPOSE_FILE"
shasum -a 256 "$EFFECTIVE_COMPOSE_FILE"
```

不要把原始展开文件、DSN、token、私钥或明文 Secret 上传到 CI artifact/工单。证据只记录 hash、Secret 是否存在及其轮换版本、非敏感 endpoint/开关/预算的脱敏摘要。

## 4. 容器内文件与有效值

对本次服务逐项检查主配置、cache policy、Event Catalog、gRPC ACL 和证书是否真实挂载且权限符合预期：

```bash
export COMPOSE_SERVICE='replace-with-compose-service'
export MAIN_CONFIG='/app/configs/replace-with-main.prod.yaml'

docker compose -f "$COMPOSE_FILE" exec -T "$COMPOSE_SERVICE" \
  sh -ceu 'test -r "$1"; stat "$1"' sh "$MAIN_CONFIG"
```

再从该实例启动日志或受保护的治理入口取得 masked effective config，核对本次变更项与仓库/部署覆盖一致。只看 `configs/*.prod.yaml`、workflow variable 或 Compose `command` 都不能证明进程实际读取了该值。

以下项目有变化时必须逐项采证：

- 数据库、Redis、MQ、IAM endpoint 与 TLS/mTLS；
- gRPC ACL 文件、default policy 和 workload identity；
- scheduler、retry governance、backpressure、queue/pool 与租约；
- metrics/profile/governance listener 和网络限制；
- migration、one-off、repair/replay 开关；
- 日志 level/format/development 与敏感字段脱敏。

## 5. 正反向验证

1. 正向：三个进程都能读取所需文件、完成 Options 校验并启动预期 listener；
2. 反向：临时移除非生产测试环境中的必需文件或提供无效 ACL，确认启动 fail closed；
3. Secret：确认日志和 artifact 中没有明文值，CLI flag 未携带 Secret；
4. 漂移：比较本次 source SHA、镜像 digest、effective-config hash 与部署计划；
5. 回滚：确认旧镜像能否读取已执行 migration 和当前配置；不能只准备旧 tag。

## 6. 失败处置与完成标准

- 文件不可读：修挂载、owner/mode 或路径，不复制 Secret 到镜像临时绕过；
- 配置解析/校验失败：修生成源和部署包，不降级成开发配置；
- 目标值与启动值不同：查 flag/env/YAML 优先级并重新生成脱敏证据；
- ACL/证书失败：保持服务不接流量，不关闭 mTLS/default-deny；
- 无法取得 effective config：本次配置验收记为未完成，不以 repo YAML 代替。

完成记录必须绑定命令、结果、source/deployed SHA、镜像 digest、effective-config hash、owner、限制和失效期；环境/生产结果写入[基础设施生产证据台账](../00-总览/10-基础设施生产证据台账.md)。

## 7. RocketMQ 开发与 M1 验收

QS API、Worker 与 IAM 的开发入口使用 RocketMQ。API 使用 `qs.mysql`、`qs.mongo` 两个事务 owner，Worker 只消费；IAM 使用 `iam.mysql`。旧 NSQ 与发布型 Outbox 不再是启动前置。

### 开发前置

1. 准备隔离 MySQL、Mongo replica set、Redis 和带 Proxy 的 RocketMQ。
2. 按当前迁移工具安装 schema，并建立与开发配置一致的数据库绑定。API 和 IAM 的 `migration.enabled` 必须为 false；常驻进程不执行初始化或升级。
3. 将开发 Broker 的 CA、凭据和路由清单放入各仓 `configs/rocketmq/`。文件名见对应 `apiserver.dev.yaml`、`worker.dev.yaml`；这些文件不提交 Git。路由清单使用当前 SDK 格式，逻辑 Topic 与事务 owner 与现行契约一致。
4. 配置中的 `qs-dev-mysql`、`qs-dev-mongo`、`iam-dev-mysql` 和 `dev-1` 仅用于新建隔离环境。已有环境沿用数据库内实际 binding，不通过改名重新初始化。
5. 准备现有 gRPC 证书、IAM 和应用配置，再从仓库根目录启动 API、Worker、IAM。AI 沿用其仓库配置说明中的完整配置要求。

开发模板表达真实运行约束，不会自动生成 Broker、账号、证书、路由或数据库绑定。缺少这些前置时不得切回 NSQ 或启用旧 Outbox。

### M1 验收

- `bash scripts/cd/test-verify-observability-nginx.sh`：无 NSQ DNS/路由也可通过；Worker 副本不足仍失败。
- `go test ./internal/pkg/configcontract ./internal/apiserver/process ./internal/worker/process`：使用实际配置解码器验证开发配置进入最终事务／只消费分支。
- IAM 仓库执行配置与 Options 的定向测试。
- 集成验证使用既有 CI；完整开发启动和正常生产发布分别记录，单元与配置检查不代替运行验收。

应用 Nginx 观测入口只检查 Collection、Worker 和 Prometheus。Broker 协议状态使用 infra 的 `rocketmq-transactions.yml` 和既有 RocketMQ 观测流程，不通过 NSQ `/stats` 代替。

发布替换副本后，Prometheus 目标发现和 federation 样本可能稍后收敛。每个服务的指标族存在性与就绪副本数使用同一组 `READY_PROBE_ATTEMPTS` / `READY_PROBE_INTERVAL_SECONDS` 有界重试；两项均满足才通过。HTTP 错误、空指标或副本不足耗尽预算仍失败，不把空响应记为零积压或就绪。

M1 交付范围仅含发布与开发入口。旧发布表继续保留，不对现有数据库执行迁移或删除。

## 8. 宿主退役 M2：当前消息观察

本节的 M1–M5 指宿主工程退役，不复用 infra 早期同名迁移阶段的完成计数。M1 代码与 CI 已交付并合并；完整人工开发启动和正常发布未执行。M2 为四仓协调草稿，源码、CI、隔离运行和部署分别验收；M3-A 已从原 stash 恢复到独立分支，验收范围见下一节，M4/M5 未实施。

| 指标 | 持久事实与范围 |
| --- | --- |
| `qs_server_ai_mq_committed_commands` | 非 retired 命令及其已提交 execution、witness、首次档案；任一证据缺失或冲突则整次采样不可用 |
| `qs_server_ai_mq_awaiting_command_receipts` | 当前命令尚无 accepted/rejected 的 AI 准入回执；held 也在等待中并单独统计 |
| `qs_ai_mq_pending_interpretation_receipts` | MQ 持有、尚无 QS 业务 ACK 的解读状态历史；不覆盖所有 AI 事件，不是 Broker 队列深度 |
| `reliable_messaging_transaction_*` | 半消息、本地事务、Broker 确认观察及 Checker 状态；不证明消费者业务完成 |

`*_observation_available=0` 表示本次读取不可用，其他快照值缺席，不生成零积压结论。原 staged/due/发布型 Outbox held 指标退出；现用状态历史、业务 ACK、会话撤销、事务凭证和调度记录保留。

后台“事务消息指标”对应 infra 的 `event-transactions` dashboard；自定义地址使用 `REACT_APP_GRAFANA_EVENT_TRANSACTIONS_URL`。未来经授权发布时先更新 QS/AI 指标生产端，再更新 Prometheus/Grafana，最后更新后台。

验收复用 `AI bridge MySQL` 的真实隔离数据库测试、AI `checks` 的 MySQL 分区、infra Prometheus 规则测试及后台 Jest/TypeScript。普通测试、模拟器、CI 状态或旧结果不能替代当前提交的业务观察链证明。M5 必须在 M4 部署观察后进入，当前没有现库 DDL。

协调草稿为 [QS #460](https://github.com/FangcunMount/qs-server/pull/460)、[AI #237](https://github.com/FangcunMount/qs-ai/pull/237)、[infra #408](https://github.com/FangcunMount/infra/pull/408) 和[后台 #74](https://github.com/FangcunMount/qs-operating-system/pull/74)。PR 检查绑定各自最终 SHA；成对隔离验收另固定 QS/AI 两个 SHA 和已发布 SDK，保留历史 RC 入口，不使用浮动分支或本地 replace。任何本轮失败、条件跳过和未执行项均保留，不能用单仓成功代替四仓协调验收。

## 9. 宿主退役 M3-A：热榜按日重建

当前 v2 答卷通过 `rm_tx_execution` 的冻结计划、精确事务 reference 和已提交 witness 还原原始消息事实，不读取旧发布集合。v1 历史答卷仍严格核对原 `rm_outbox`；混合日中的任一缺失或冲突使整日失败。保留历史数据责任，不能据新版路径通过而提前删集合。

工具模式、完整日限制、租约与回执处理见[热榜重建说明](../../scripts/oneoff/hotrank_day_rebuild/README.md)。默认 inspect 只读；prepare-index 和 apply 会写存储，本次不连接或操作现有 Mongo/Redis。

M3-A 叠加于尚未合并的 M2 已验收提交，草稿 PR 以 M2 分支为 base。现有主 CI 增加该 base 的 pull_request 入口，复用隔离 Mongo 副本集完成 source 验收；不新增发布入口。M2 合并后须将 M3-A 整理到当时最新 main，再重新核对差异和 CI。

本阶段测试区分真实 Mongo 原事务与 Redis 模拟器。历史 `ActualNSQConfirmationLoss` 案例仅证明历史兼容路径；当前 RocketMQ 重投、Broker/Worker 重启、真实 Redis 与无重复业务效果留待 M3-C。答卷缺口和提醒恢复属 M3-B；M3-A 通过不等于 M3 整体验收完成。生产部署和现库退役均未执行。

## 10. 宿主退役 M3-B：答卷缺口与提醒恢复边界

[缺口只读核对](../../scripts/oneoff/answersheet_gap_audit/README.md)支持当前 v2 与历史 v1。v2 的 `missing_committed` 仅证明原提交凭证成立而 Assessment 不存在，不代表 Broker 确认；v1 的 `missing_confirmed` 保留历史发布确认含义。未知版本或不完整/冲突凭证不能成为“扫描零行、无缺口”；读取失败不得生成零缺口结论。软删除的 Assessment 仍属于曾受理事实，需人工核对并拒绝再次创建。

[单份恢复工具](../../scripts/oneoff/answersheet_gap_recover/README.md)在固定 cutoff、机构和原答卷范围内重查 source，使用原 wire 调用既有 EnsureAssessment；沿用持久操作日志和原 Intake 唯一键，不向 MQ 广播。v2 不要求 `rm_outbox`，v1 仍保留历史读依赖。Mongo 页及证据在一个主库快照内读取，但与 MySQL 不构成共同事务；正常 Worker 竞态仍依靠业务唯一键和原请求回执收口。

M3-B 答卷交付时，提醒恢复仅有历史 `rm_outbox` 重排队协议；当前宿主未装配该 reader，该写入口保持不可用，即使配置 gap recovery 和提醒为 true 也不能启用。原治理回执查询保留。后续当前事务协议见第 11 节；不能伪造 Outbox version、重置 witness 或以新事件 ID 重发。答卷 source 验收不代表提醒恢复或真实 RocketMQ 重投/重启已完成。

M3-B 草稿叠加 M3-A，既有 CI 为该 base 增加 PR 入口，在自建随机 Mongo/MySQL 数据库运行三个必需 source 用例并禁止跳过。该验证不执行生产恢复或通知发送，也不新增部署入口。M2/M3-A 合并后需整理到当时最新 main 并重新核对 CI；M4/M5 仍按原依赖顺序推进。

## 11. 宿主退役 M3：当前事务提醒恢复

当前事务缺批次恢复沿用 `POST /internal/v1/system-governance/actions/reminder-gap-recoveries`，显式指定 `source_protocol: "transaction"`。`expected_version` 必须为 0；`expected_schedule_revision` 是原任务调度修订号，不能使用旧 Outbox version 或事务 fence 代替。机构和操作者来自现有受保护的管理作用域，写入同时受 gap recovery 与任务提醒开关控制；不会修改默认配置。

| 操作 | 请求与持久行为 |
| --- | --- |
| `?mode=inspect` | 只读核对 task_id、expected_schedule_revision、固定过去 opened_before；返回原 opening_event_id、source_fingerprint、截止时间和 disposition。不要求 confirm 或 request_id，不暴露入口 URL、收件人和完整冻结内容。 |
| `?mode=apply`（默认） | 携带审核后的原事件、指纹、唯一 request_id、evidence_reference、reason 和 confirm=true。锁定原任务，确认尚无该提醒责任和其他恢复操作，先在既有治理审计落下原输入，再调用正常提醒服务。 |
| `?mode=resume` | 只续办同机构、操作者和完整原输入的原 request_id；重启后沿用原收件批次、投递账本、租约和调用标记。来源变化或过期不再调用业务服务；未知发送结果留待人工核对。 |
| `/resolve` | 只读查询完全匹配的原操作；关闭写开关或已过提醒窗口后仍可读取。缺失回执不能成为另建 request_id 的理由。 |

来源在 MySQL 只读主库快照中读取原 `rm_tx_request`、冻结 execution、精确 reference、已提交 witness、绑定及当前任务，复用生产 task-opening 私有 artifact、消费者 wire 校验及原开通恢复的稳定输入哈希比较；计划时间、量表、参与轮次等静默变化即使未增加修订号也拒绝恢复。它证明本地已提交事实，不证明 Broker 确认；不安装 schema、不获取新事务令牌、不改事务凭证，也不读写 `rm_outbox`。

审计先落库，业务效果由原 `TaskOpenedReminderService` 执行。恢复不发布 MQ 消息，也不更换事件、收件人或发送期限。服务返回 nil 不构成完成证据：必须重读既有批次与投递记录。`platform_confirmed` 仅表示通知平台已接受；`rejected`、`suppressed`、`reviewed` 分别计数。`pending` 或 `unknown` 保持 `pending_reconciliation`；sending、manual_required 或已跨外部调用边界的未知记录不会触发再次调用。并发的不同 request_id 只能保留一个原恢复操作。

既有 CI 在 M3-B base 上增加七个必需原生 MySQL 用例，要求实际执行并零跳过：两个原事务 source 用例（含九个冲突子场景），以及已知回执复用、nil 返回未完成、未知结果不重发、冻结批次续办、并发操作唯一性五个恢复用例。测试使用随机新建数据库；协调器测试的发送效果受控，原事务 source 另行使用实际 SDK 提交根验证。这些结果不等于真实 Broker、完整通知提供方或生产故障验收。

本阶段不新增自动恢复调度器；未结束责任持久保存在原审计及通知账本，由显式 resume 续办。真实 RocketMQ 重投、Broker/Worker 重启、真实 Redis 和端到端无重复业务效果仍由 M3-C 验收。草稿按 M2 → M3-A → M3-B → 本批次叠加；整理到最新 main 后须重新核对差异和 CI。未合并、未部署、未操作现有数据库，M4/M5 依赖顺序不变。

## 12. 宿主退役 M3-C：真实重投、重启与业务效果验收

本节定义当前验收协议，完成状态以绑定最终源码 SHA 的原生报告及 CI 为准。它不与 infra 早期同名 M3/M4 阶段混用计数。既有 infra `m4-qs-runtime.yml` 工作流增加独立的 `host-retirement-recovery` job，使用 `ci-transactions.py --qs-recovery-host`；旧 API/Worker/dispatch profile 和 SDK 门禁保持各自证据归属。手动触发时 `recovery_qs_ref` 指定确切 QS 提交，未提供时不运行新增 job。既有必填 `qs_ref` 仍用于早期 profile 的独立源码，不应填入当前 M3-C SHA。

验收复用当前 RocketMQ 事务 owner、真实 MySQL/Mongo 原事务、现有恢复 CLI、业务应用服务及生产 Worker 进程入口。每轮创建独有 Compose 项目、随机数据库和真实 Redis；仅向本轮 loopback 资源写入，结束时检查容器、网络、进程组、临时目录及数据库清理。原事务计划、事件 ID、首发消息字节、事务 witness 和业务 ACK 不得通过重置、改写或创建替代事件来制造通过。

必需场景包括：真实 Redis 当日重建及同请求重试；答卷恢复在业务提交后丢失 RPC 响应并按原审计查询；提醒已知回执不再发送、外部响应未知不再发送、冻结后中断并按原名单续办；关闭、过期或静默修改的任务拒绝新发送；关闭写入口后仍可查询原回执。提醒 source 使用已注册 MySQL owner 的只读 artifact verifier，按其 manifest 校验当前路由及显式登记的历史路由，缺失 verifier 时关闭恢复写入口，不能按旧物理主题猜测当前原事务。

验收同时装配生产 API 默认开启的 Evaluation／Interpretation 租约恢复 runner，保留十秒扫描、真实 leader 锁与原租约时长，并在删测试库前取消和排空。原生故障点通过 Mongo command monitor 观察原报告 claim 事务真正提交后暂停原 RPC；随后 SIGKILL Worker，未完成的原报告运行必须在真实五分钟租约到期后按同一运行身份恢复。迟到原报告 RPC 在受控网络边界等待已有 artifact 后再调用实际服务，不伪造业务返回、不创建替代事件。`QS_M3C_NEGATIVE_OMIT_API_LEASE_RECOVERY=1` 仅用于本地反例，故意省略 API runner，不得计作通过；当前验收回执必须确认 runner 已启动和排空、真实报告 claim 正 PTTL 及原运行身份不变。

随后真实 Worker 在提交业务效果但尚未 ACK 时被 SIGKILL；同一独有 Broker 容器被 SIGKILL 后重启，确认真实健康状态、TLS 握手及 NameServer 原主题注册恢复后，再启动不同 PID 的 Worker。必须观察到原事件 ID、原始 wire 哈希完全相同的再次投递。实际业务链从答卷进入 Assessment、EvaluationRun、冻结 Outcome 和标准报告，SIGKILL 后必须读到真实 Redis 去重锁的正 PTTL，等待生产默认五分钟租约自然到期，不改 TTL、不删除锁。迟到原请求完成且 Worker 排空后再次检查，持久记录各仅一份，Outcome/Run/报告身份保持不变；热榜仍为一次，受控通知提供方调用数不增加。来源证据冲突时，整日重建失败且 Redis 投影不被部分替换。退出报告要求全部 14 项成立、失败/跳过为零，并绑定确切 QS SHA、发布 SDK 版本及原始模块和校验和、manifest 版本和清理结果。

身份目录及通知 HTTP 提供方为本轮受控边界；未知响应和冻结后中断在这些边界注入。Worker/Broker 的 SIGKILL 和 Redis/MySQL/Mongo/RocketMQ 为真实实例。报告不宣称已完成真实微信发送、AI 质量、独立 API daemon 启动、生产部署或现有存储退役。带 tag 的原生用例不得把依赖缺失计作 skip；未生成完整回执不能算验收通过。

M3-C 通过后，按 M2 → M3-A → M3-B → 提醒恢复 → M3-C 的依赖整理草稿到当时最新 main，并核验最终提交组合的 CI 和发布前置。现有“不部署、不操作现有数据库”约束继续生效；本节不授权发布、自动恢复或清表。M4 代码依赖收口与 M5 数据库退役仍按原顺序单独验收。

### 冻结期间准备正式镜像

`Production Deploy` 手动入口的 `operation=build` 只构建并发布精确 SHA 标签；可在 `PRODUCTION_DEPLOY_PAUSED=true` 时执行，不更新 latest，不连接部署主机，不产生完整部署成功 marker。`service=all` 准备三个进程；每个服务保留绑定源码、linux/amd64、GHCR/ACR digest 与实际 image ID 的 `qs-image-*` 回执。构建失败仍使本次运行失败。普通 `operation=deploy` 仍服从暂停开关、原服务顺序、就绪与治理检查；构建回执不代表部署或线上业务验收。

协调发布先执行只读 `release-snapshot.yml` 记录各宿主当前镜像身份、挂载及文件指纹。`operation=build` 的镜像回执固定各 registry digest 和 image ID；正式发布可设 `reuse_images=true`，`image_digests` 填写服务名到已核验 ACR digest 的 JSON 对象，避免重建。远端按 digest 拉取，保留原有规范镜像名和就绪验证。快照不读取数据库，不代表业务验收通过。

### 固定业务镜像与部署工具版本

部署工具修正后，手动入口可同时指定 `operation=deploy`、`revision=<完整 main 祖先 SHA>`、`reuse_images=true` 和已验收的 `image_digests`。`revision` 必须有成功的 push CI，且入口必须位于 main；短 SHA、非祖先、构建模式和未复用镜像的覆盖请求都会拒绝。

业务镜像和运行回执仍绑定 `revision`；规划、打包、远端部署及治理检查使用本次工作流的 `github.workflow_sha`。因此部署脚本修正可以复用原固定镜像。API 就绪后才更新 Collection/Worker，原镜像身份、材料预检、就绪和公开治理门禁继续生效。Collection 只使用标准输出时不处理宿主日志目录；Worker 包保留 `MYSQL_TLS_CA_REF`，供部署前按不可变 infra 版本校验 CA。此入口不授权数据库迁移、清表或故障重投。

Worker 替换前预检使用同一候选 Compose 文件与 image env。它先验证 `/etc/qlume/mysql/ca-chain.pem` 的固定宿主来源、只读绑定及禁止自动创建路径，再以候选镜像的普通用户、只读文件系统和 `network=none` 检查证书可读性，最后执行既有 MySQL greeting 检查。预检不启动 Worker 应用；任一步失败均在旧副本替换之前退出。证书绑定、文件可读和端点连通分别验证，凭据不进入预检日志。

## 13. 宿主退役 M4/M5 边界

此处 M4/M5 指宿主工程退役，不复用 infra 更早迁移阶段的同名完成计数。M4 源码和 CI 验收、M4 生产发布、M5 数据处置分别记账。

当前共用 wire、Reference、指纹校验位于 `internal/apiserver/eventing/eventmessage`。迁包保留原消息 ID、组织范围、时间、Revision2 编码及指纹；历史 v1 与当前事务证据仍严格区分。`scripts/testing/check-production-messaging-deps.py` 对三个实际可执行进程的依赖图检查，拒绝 NSQ、发布型 Relay 以及历史测试夹具进入生产构建。

配置默认提供者改为 RocketMQ，API/Worker 的旧 NSQ 连接命令行选项退出。Worker 的 `nsq-message-timeout` 暂保留为已有发布配置的兼容键，含义是当前 RocketMQ handler 的有界处理期限；内部订阅器使用 `HandlerTimeout`，该键不再创建 NSQ 客户端。

当前 AI bridge 预检不依赖旧 `ai_messaging_outbox`。它仍要求业务准入、operations 的完整退役约束、Inbox、失败/隔离及技术观测结构；读取失败拒绝启动，不能因删除旧表检查而绕过当前责任。

M5 必须在 M4 已部署后逐对象核对：当前源码读写、未结束的发布和业务责任、历史格式读取、精确备份/导出及回退下限。候选名字不是删除授权。QS `rm_outbox` 的 v1 答卷/热榜、结果一致性与历史恢复依赖尚须逐项收口；IAM 的旧表仍由启动与就绪检查读取。AI 的 `interpretation_result_outbox`、IAM 会话撤销任务、事务凭证、档案、Inbox、receipt/ACK 和调度记录均保留。

那批缺原 command 事务锚点的 QS 历史操作不能被填成 Commit，也不能通过清空、批量 retired 或统计成零来解锁 M5。新建库、升级库、缺证据/冲突整批拒绝、删表后启动与观测/恢复/业务验收先在隔离环境完成；现有数据库的数据或结构变更须使用具体对象、快照及回退边界审查后执行。

### M5 首批候选：QS 空发布表（尚未执行）

候选追加 SQL 111，只处理 `qs.mysql.ai_messaging_outbox`；目标配对为 SQL 111 / Mongo 44。其余候选对象及当前事务、档案、业务 ACK/Inbox/receipt、调度均保留。SQL 110 / Mongo 44 的现网只读零行证据不等于已执行 SQL 111，也不替代执行时的锁内复核。

必须经既有配对迁移驱动的精确资源、身份和 dirty/clean 状态校验进入。驱动在同一专用连接设置两秒锁等待、取得目标表 WRITE 锁、全表计数为零后才设置执行绑定；任何状态的记录（含 confirmed、NULL、未知）均拒绝删除。SQL 资源直接执行而未绑定时失败。表缺失、权限/锁/读取错误均停止，不能当作已退役。结束时释放锁、临时绑定与 prepared statement，并恢复原会话等待设置；释放不确定时丢弃物理连接，不得污染业务连接池。
