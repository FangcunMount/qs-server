# 调度任务

## 1. 结论

调度任务必须从当前有效配置和 composition root 反向核对，不能根据“代码里有 runner”假设生产已启用。尤其是 Mongo consistency audit：能力已经实现，dev/prod 配置仍明确关闭；一次 one-off 扫描不是 scheduler 运行证据。

## 2. apiserver scheduler 清单

`internal/apiserver/process/runtime_bootstrap.go` 当前向 `scheduler.Manager` 装配七个 runner：

| Runner | 责任 | 持久进度/互斥 | 当前生产意图 |
| --- | --- | --- | --- |
| Plan | 打开/过期 Plan Task、生成周期任务 | 业务状态 + leader lock | 启用 |
| StatisticsSync | 上海时间 nightly publish | repair window、Fact、SyncRun、机构/leader lock | 启用 |
| EvaluationConsistencyAudit | 跨 MySQL Evaluation 事实只读审计 | audit progress + leader lock | 启用 |
| EvaluationLeaseRecovery | 恢复过期 Evaluation 运行租约 | 业务 CAS + 专用 leader lock | 启用 |
| InterpretationLeaseRecovery | 恢复过期 Interpretation Run | Generation/Run CAS + 专用 leader lock | 启用 |
| ReportCatalogAudit | 分批检查 Artifact/Catalog winner | MySQL checkpoint + leader lock | 启用 |
| MongoConsistencyAudit | 七阶段跨 Mongo 集合只读巡检 | MySQL checkpoint revision CAS + Redis leader lock | **关闭** |

这里的“生产意图”来自版本化 `configs/apiserver.prod.yaml`，仍需以进程启动时合并后的 config/flags/env 和运行指标复核。

## 3. Mongo consistency audit 操作契约

### 3.1 “只读”的精确边界

- Mongo scanner 没有写方法，不 insert/update/delete/repair AnswerSheet、Outbox、Generation、Run、Artifact、Model、Questionnaire 或 Norm。
- scheduler 会写 MySQL 表 `mongo_consistency_audit_checkpoint`，也会在 Redis 创建/续租 leader lease。
- one-off CLI 不启动 scheduler、不写 MySQL checkpoint；它只连接 Mongo、执行有界查询并输出统计。
- finding 只是证据，不能自动触发数据修复；Report Catalog repair plan 也不是 Mongo consistency finding 的通用修复入口。

### 3.2 七阶段与严重度

| 顺序 | phase | 责任范围 | finding 严重度 |
| --- | --- | --- | --- |
| 1 | `answersheet_outbox` | durable AnswerSheet → submitted Outbox | high |
| 2 | `outbox_answersheet` | submitted Outbox → AnswerSheet | high |
| 3 | `generation_run` | Generation → LatestRun / 状态映射 | high |
| 4 | `generated_terminal` | generated Generation → Artifact + terminal Outbox | high |
| 5 | `retry_outbox` | retry fact → scheduled Outbox | high |
| 6 | `model_release` | head → active model/questionnaire snapshot | high |
| 7 | `published_model_runtime` | DefinitionV2 hash、NormRef、runtime materialization | hash mismatch 为 medium，其余 high |

每阶段进入时冻结 upper bound，并按稳定 cursor 分批推进。完整周期结束才更新 last completed timestamp 和 drift gauges；不能把某一 batch 成功写成“七阶段审计成功”。

### 3.3 checkpoint/CAS 与 leader lock

MySQL checkpoint 固定 key 为 `mongo_consistency`，schema version 为 1，保存 revision、cycle、phase、cursor、upper bound、working statistics、last completed 和 next cycle time。

保存规则是 `Save(expectedRevision, nextCheckpoint)`：首次并发 create 遇 duplicate，或 update 的主键+revision 没有精确影响一行，都返回 CAS conflict。Redis leader lock 负责正常情况下的单 leader 执行；checkpoint CAS 负责持久进度不被并发覆盖。二者都存在仍不能把 repair 变成安全动作，因为审计本身没有 repair port。

workload 为 `mongo_consistency_audit`，默认 lock key `qs:mongo-consistency-audit:leader`、TTL 30 秒并自动续租。lock manager 不可用时 runner fail-closed；拿不到 lease 的 tick 只跳过，不以无锁模式继续。

## 4. one-off 预检

入口：`scripts/oneoff/mongo_consistency_audit`。生产执行必须在已批准的只读窗口、使用精确部署版本，并通过 secret 管理注入 URI；禁止把 DSN 写入命令历史、文档或工单。

命令形状：

```bash
go run ./scripts/oneoff/mongo_consistency_audit \
  --mongo-uri "$MONGO_URI" \
  --mongo-db qs \
  --scope all \
  --batch-size 200 \
  --batch-timeout 3s \
  --max-samples 10 \
  --timeout 30m \
  --json
```

退出码：

| code | 含义 | 运维动作 |
| --- | --- | --- |
| 0 | 扫描完成且 finding=0 | 保存完整报告，继续检查启用门禁；不自动启用 |
| 2 | 扫描完成且发现 drift | 保存报告、冻结 finding 清单；scheduler 保持关闭 |
| 1 | 配置、连接或扫描失败 | 先修执行条件；不能当作“无漂移” |

正式生产 one-off 于 2026-08-16 01:13:35 CST 扫描 347,494 个 anchor、耗时 25.43 秒，退出码 2；唯一 finding 为 `outbox_missing_answersheet=269`。这些历史孤立 Outbox 未被删除或修复。

## 5. 生产默认值与启用条件

`configs/apiserver.prod.yaml` 当前值：

```yaml
mongo_consistency_audit:
  enable: false
  initial_delay: 30m
  tick_interval: 5s
  cycle_interval: 24h
  batch_size: 200
  batch_timeout: 3s
  max_samples: 10
  lock_key: "qs:mongo-consistency-audit:leader"
  lock_ttl: 30s
```

只有以下条件全部满足，才能新建受控生产配置变更把 `enable` 改为 `true`：

1. 最后通过 CI、目标部署 SHA 和实际运行 SHA 对齐；
2. MySQL migration 000069、Mongo migration 000024 及所需索引已在目标环境确认；
3. 正式部署版本完成全七阶段 one-off，且没有未处置 high drift；
4. 每个历史 finding 都有冻结范围、原因、owner、处置决定和复验；任何写操作另行授权；
5. Redis leader lock、Mongo backpressure、`qs_mongo_consistency_audit_*` 指标和告警已验证；
6. 批量/周期容量、停止/回退方式和上线观察窗口已经评审；
7. 取得独立生产配置变更批准。

当前第 3、4 项未通过，因此必须保持 `enable: false`。不得通过清空 checkpoint、跳过 `outbox_answersheet`、降低 severity 或隐藏 269 条 finding 来绕过门禁。

## 6. 停止、恢复与排障

- 安全停止：把配置恢复为 `enable: false` 并按正常发布流程部署；进程 context 取消也会停止 ticker/当前 batch。
- 不要删除 checkpoint 作为“重跑”手段；已完成周期会按 `next_cycle_at` 等待，CAS conflict 应先查多实例/lease/配置。
- `enabled=1, ready=0`：查 service 依赖、MySQL checkpoint repository 和 Mongo scanner。
- lock degraded/无法取得：查 Redis family/keyspace/TTL 和 lease metrics，不要改成无锁执行。
- last success 过旧：区分 runner 未启用、idle 等待、batch 持续失败、CAS conflict 和周期尚未完成。
- drift > 0：先按 kind/severity/样本 ID 冻结证据；不要直接查改生产正文或删除 Outbox。

指标说明见[健康检查与观测](./08-健康检查与观测.md)，数据层边界见[Data Access](../03-基础设施/data-access/README.md)。

## 7. 通用运维要求

每个任务应有启用开关、周期/批量、互斥或租约、幂等、失败重试、运行账本或进度、指标和安全停止方式。Statistics 不使用持久扫描 checkpoint，而以日期修复窗口、稳定 FactKey 和 SyncRun 实现重跑与恢复。

从配置字段找到 runner 装配，再找到 application service 和持久化状态；最后确认 health/metrics/logging 能观察到它实际运行。Statistics 当前只保留 `statistics_sync`：Behavior Journey Scan、Pending Reconcile 和 V1 三段同步均已退役，不应再出现在配置或运行清单中。
