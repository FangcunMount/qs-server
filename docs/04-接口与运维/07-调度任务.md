# Scheduler 操作 Runbook

## 1. 前置条件

Scheduler 必须从 composition root、当前有效配置、LockLease 和持久进度一起核对；代码存在 runner 不代表目标环境已启用。生命周期见 [Runtime canonical 文档](../03-基础设施/runtime/10-进程生命周期、启动与关闭.md)，租约见 [LockLease](../03-基础设施/concurrency/50-LockLease与长任务互斥.md)，Migration/one-off 边界见 [Migration 与恢复](../03-基础设施/migration-recovery/README.md)。

操作前记录：

```bash
git rev-parse HEAD
make docs-facts
go test -count=1 \
  ./internal/apiserver/runtime/scheduler \
  ./internal/apiserver/application/mongoconsistency \
  ./internal/pkg/resilience/locklease/...
```

`docs-facts` 会从 `runtime_bootstrap.go` 派生九个 apiserver Scheduler runner，并把名称、配置段与本文矩阵精确比较：

| Runner | 责任 | 持久进度/互斥 | 当前生产意图 |
| --- | --- | --- | --- |
| Plan | Plan Task 周期推进 | 业务状态 + leader lock | 启用 |
| StatisticsSync | 夜间统计同步 | Fact/SyncRun + leader/task lock | 启用 |
| EvaluationConsistencyAudit | Evaluation 一致性只读审计 | audit progress + leader lock | 启用 |
| EvaluationLeaseRecovery | 恢复 Evaluation 过期租约 | 业务 CAS + leader lock | 启用 |
| InterpretationLeaseRecovery | 恢复 Interpretation 过期租约 | Generation/Run CAS + leader lock | 启用 |
| AIExplanationPromptEvaluationLeaseRecovery | 仅唤醒 AI Prompt 评测中过期的 `prepared` checkpoint | PromptEvaluationRun CAS + Mongo Outbox + leader lock | 关闭 |
| AIExplanationParticipantLeaseRecovery | 唤醒 Participant AI 解读的精确过期 Run lease | Run wake-up CAS + Mongo Outbox + leader lock | 关闭 |
| ReportCatalogAudit | Artifact/Catalog 分批审计 | MySQL checkpoint + leader lock | 启用 |
| MongoConsistencyAudit | Mongo 跨集合只读巡检 | MySQL checkpoint CAS + Redis leader lock | 关闭 |

“当前生产意图”只表示版本化 `configs/apiserver.prod.yaml`，操作前仍须从目标实例 masked effective config 和 runtime metrics 复核。

AI Prompt 评测恢复器保持默认关闭。它只查询 `collecting + execution.phase=prepared + lease_expires_at<=now`，并在同一 Mongo 事务内再次校验 invocation 与扫描到的 lease expiry、CAS 保存恢复审计和写入下一条耐久事件。扫描器不调用 Provider；若候选已竞态进入 `dispatching` 或被重新认领，聚合会拒绝自动恢复。过期 `dispatching` 仍须走带成本确认的人工恢复，并先固化 `provider_result_unknown`。

Participant AI 解读恢复器也保持默认关闭。它查询 `running + lease_expires_at<=now`，以 `GenerationID + RunID + lease expiry + invocation phase` 生成稳定事件 ID，并在同一 Mongo 事务中写入 Run 上的精确 wake-up 证明和 Outbox。Worker 只恢复这条证明指向的同一个 attempt：`prepared` 可通过 CAS 重领；当前 OpenAI Route 的 `dispatching` 不具备幂等重放能力，因此只提交 `provider_result_unknown` 并释放活跃槽。状态已被其他 owner 推进时旧事件幂等结束；扫描器绝不创建下一 attempt，也不新增日预算预留。

### 1.1 AI Prompt 评测容量与告警基线

Prompt 评测 start 不是仅靠前端确认控制成本。`ai_explanation.evaluation.capacity` 默认约束如下：

```yaml
capacity:
  max_active_runs_per_org: 1
  daily_provider_invocation_budget_per_org: 140
```

v1 每个 start 在 Run 与首条 Outbox 的同一 Mongo 事务内，按机构和 UTC 日预留完整 70 次 generation + semantic Provider 调用。超过日预算或触发同机构 `collecting` unique 时返回 HTTP 429；同一冻结 release 已有 active run 则仍可能先按业务重复返回 409。取消、失败和 unknown result 不退款。人工恢复只继续原 inventory，不另增预算。精确审计读取 `ai_explanation_prompt_evaluation_daily_budgets`；`qs_ai_explanation_prompt_evaluation_reserved_provider_invocations_total` 是可能受进程重启、采集窗口影响的累计 telemetry，不能用于余额或计费裁决。

目标环境尚无仓库内可部署的 Prometheus rule bundle，因此以下只是上线前必须落入实际监控平台的建议表达式，不是“告警已部署”证据：

```promql
increase(qs_ai_explanation_prompt_evaluation_start_admission_total{result="error"}[5m]) > 0
increase(qs_ai_explanation_prompt_evaluation_lease_recovery_items_total{result="error"}[10m]) > 0
increase(qs_ai_explanation_participant_lease_recovery_items_total{result="error"}[10m]) > 0
increase(qs_ai_explanation_prompt_evaluation_start_admission_total{result="daily_budget_exceeded"}[30m]) > 0
increase(qs_ai_explanation_prompt_evaluation_start_admission_total{result="org_concurrency_exceeded"}[30m]) > 0
```

前三条是执行/恢复异常，应由值班人员检查事务、Outbox、Worker、gRPC 和 lease owner；后两条是治理信号，应联系发起机构核对 active run、UTC 日预留和计划内评测次数，不能自动扩容或提高预算。机构管理员应优先调用 `GET /internal/v1/interpretation/ai-explanation/prompt-evaluation-capacity`。接口同时要求 audit 和 org-admin capability，只从可信身份派生机构，并固定查询当前 UTC 日；返回 limit、reserved、remaining、available full starts 与 reservations。若管理 API 不可用且已获得只读数据库处置授权，可用下列查询冻结原始证据：

```javascript
db.ai_explanation_prompt_evaluation_daily_budgets.findOne(
  {org_id: NumberLong("<org_id>"), budget_day: ISODate("<utc-midnight>")},
  {_id: 0, org_id: 1, budget_day: 1, reserved_provider_invocations: 1, reservations: 1}
)
```

若 ledger 与 Run/Outbox 不一致，先冻结 source/deployed SHA、Run ID、预算日和事务日志；不得手工 `$inc`、删除 reservation 或解除 unique index。当前管理 API 不提供跨机构或历史日期参数；历史审计仍须走批准后的只读数据流程。

## 2. 启停通用检查

每个 runner 依次核对：

1. effective `enable`、周期、batch、timeout 和 lock key/TTL；
2. 对应 migration、索引、外部依赖与 service wiring；
3. Redis leader lock 可创建、续租和失租；不可用时保持 fail closed；
4. checkpoint/SyncRun/业务 CAS 的当前位置、revision 和 stale 判定；
5. 指标、日志、告警、停止阈值和 owner；
6. 多实例中只有 lease owner 推进，非 owner 不以无锁模式运行。

启用或修改周期必须走正常配置发布。停止时先把 `enable` 恢复为 `false` 并部署，观察当前 batch/context 退出；不要 kill -9、删除 checkpoint、延长 TTL 或关闭 CAS 来“恢复”任务。

## 3. Mongo consistency audit 专项预检

版本化 production 配置的预期块由 `docs-facts` 与源码配置精确比较：

```yaml
mongo_consistency_audit:
  enable: false
  initial_delay: 30m
  tick_interval: 5s
  cycle_interval: 24h
  batch_size: 200
  batch_timeout: 3s
  max_samples: 10
  lock_key: "qs:mongo-consistency-audit:leader"
  lock_ttl: 30s
```

启用前必须全部满足：

1. source、CI、deployed SHA 与镜像 digest 对齐；
2. **MySQL migration 000069**、**Mongo migration 000027** 和所需索引在目标环境确认；
3. Redis leader lock、checkpoint revision CAS、metrics 与告警完成环境验证；
4. 在精确部署版本执行完整 one-off，只读扫描七阶段：`answersheet_outbox`、`outbox_answersheet`、`generation_run`、`generated_terminal`、`retry_outbox`、`model_release`、`published_model_runtime`；
5. 没有未处置 high finding；每个 finding 有范围、owner、决定和复验；
6. 已批准观察窗口、停止方式和独立生产配置变更。

任一项缺失时保持 `enable: false`。

## 4. one-off 只读执行

只能在已批准的只读窗口、使用目标版本和 Secret 管理注入 URI。以下是参数形状；正式执行必须防止 DSN 出现在 shell history、process capture 或工单：

```bash
go run ./scripts/oneoff/mongo_consistency_audit \
  --mongo-uri "$MONGO_URI" \
  --mongo-db qs \
  --scope all \
  --batch-size 200 \
  --batch-timeout 3s \
  --max-samples 10 \
  --timeout 30m \
  --json
```

退出处理：

| 退出码 | 判定 | 动作 |
| --- | --- | --- |
| 0 | 完整扫描且 finding=0 | 保存报告；继续其它启用门禁，不能自动启用 |
| 2 | 完整扫描且存在 drift | 冻结报告和有界样本；Scheduler 保持关闭 |
| 1 | 参数、连接或扫描失败 | 修执行条件并重跑；不能解释为“无漂移” |

**退出码 2** 是找到 drift 的预期语义，不是工具崩溃。任何历史扫描数量、耗时或 finding 只从[基础设施生产证据台账](../00-总览/10-基础设施生产证据台账.md)引用，不在本页复制。

## 5. 运行观察与失败处置

- `enabled=1, ready=0`：查 service wiring、checkpoint store、Mongo scanner 和 effective config；
- 没有 lease/失租：查 Redis family、keyspace、TTL 与续租指标；禁止无锁继续；
- last success 过旧：区分未启用、等待下周期、batch 失败、CAS conflict 和 cycle 未完成；
- CAS conflict 增长：先冻结实例/lease/checkpoint 证据，排查并发 owner；不要清 checkpoint；
- drift > 0：按 phase/kind/severity 冻结证据，不自动删除 Outbox、补建业务实体或修改 checkpoint；
- shutdown 超时：按 Runtime 风险处理，不通过强杀掩盖未结算的 batch。

指标查询步骤见[健康检查与观测](./08-健康检查与观测.md)。完成记录必须绑定 source/deployed SHA、effective config、leader/lease、checkpoint、完整周期结果、命令、owner、限制与失效期。
