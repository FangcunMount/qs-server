# 常见排障 Runbook

## 1. 先冻结证据

在执行重启、replay、repair、清理或配置变更前，记录故障时间窗、source/deployed SHA、镜像、脱敏 effective config、实例和关联标识：

```bash
export INCIDENT_FROM='2026-01-01T00:00:00Z'
export REQUEST_ID='replace-with-request-id'
export COMPOSE_FILE='/path/to/docker-compose.prod.yml'

git rev-parse HEAD
date -u '+%Y-%m-%dT%H:%M:%SZ'
docker compose -f "$COMPOSE_FILE" ps
docker compose -f "$COMPOSE_FILE" images
```

保存原始证据的受控位置与 hash；不要把 token、答案、报告正文、DSN 或原始敏感 error 放入工单。

## 2. 沿责任链定位失败层

```text
client
  -> collection admission / identity / resource ownership
  -> gRPC transport + service ACL
  -> apiserver use case + transaction
  -> durable Outbox
  -> MQ publish / consume / settlement
  -> Evaluation Outcome
  -> Interpretation Report
  -> query projection / Cache / Signal
```

不要从最终“报告未完成”直接跳到 WebSocket、MQ 或 Cache。以一个 request ID、idempotency key、event ID、AnswerSheet/Assessment/Report ID 为主线，每过一层记录“存在/不存在/未知、时间、版本、查询命令”。

## 3. 日志、probe 与 metrics

```bash
docker compose -f "$COMPOSE_FILE" logs --since "$INCIDENT_FROM" qs-apiserver |
  grep -F -- "$REQUEST_ID"
docker compose -f "$COMPOSE_FILE" logs --since "$INCIDENT_FROM" server |
  grep -F -- "$REQUEST_ID"
docker compose -f "$COMPOSE_FILE" logs --since "$INCIDENT_FROM" runtime |
  grep -F -- "$REQUEST_ID"

curl --silent --show-error --max-time 5 "$APISERVER_URL/readyz"
curl --silent --show-error --max-time 5 "$COLLECTION_URL/readyz"
curl --silent --show-error --max-time 5 "$WORKER_MANAGEMENT_URL/readyz"
```

Compose service 名以本次实际展开结果为准。日志没有同一 request ID 时，改用 event/business ID 和窄时间窗；禁止无条件下载全量生产日志。probe 只按[健康探针 Runbook](./08-健康检查与观测.md)解释。

## 4. 症状处置

| 症状 | 按顺序执行 | 立即停止/禁止 |
| --- | --- | --- |
| 401/403 | 核对 token issuer/audience/expiry → principal → org/Testee scope → capability → resource ownership → gRPC service/delegation | 不关闭 IAM、mTLS、ACL 或扩大 default policy |
| 429/排队超时/503 | 保存状态码、`Retry-After`、路由和实例 → 查 Gate/RateLimit/Backpressure/Redis runtime → 对照 effective budget → 查依赖时延 | 不先调大并发、连接池或 timeout |
| 重复提交/冲突 | 用同一 idempotency key + fingerprint 查 durable result → 区分同键同内容、同键异内容和 commit-unknown → 查 coalescer/transaction 指标 | 不换 key 猜测重试；不删除唯一记录 |
| 答卷已受理但无 Assessment | 查 AnswerSheet transaction → `answersheet.submitted` durable Outbox → relay/publish → MQ settlement → worker EnsureAssessment → retry/dead-letter | 不因 MySQL 暂时缺 Assessment 删除 AnswerSheet/Outbox |
| Outcome 已有但无 Report | 查 `evaluation.outcome.committed` → Interpretation Generation/Run → retry Outbox/hold/dead-letter → Artifact/Catalog | 不补空 Report、改 terminal 状态或无限 replay |
| 等待未唤醒 | 查 Redis Signal 发布/订阅和连接状态 → 立即回查持久 Report/Assessment 事实 → 验证客户端轮询回退 | 不把 Signal 当持久事件；不因漏 Signal 改业务事实 |
| 统计不一致 | 查 Fact/SyncRun、日期窗口、leader/task lock、投影版本和 stale running → 用批准的只读 reconcile/audit | 不直接改读表、清 ledger 或并行启动第二 owner |
| Scheduler 无最近成功 | 查 effective enable → ready → Redis leader lock → batch/phase → checkpoint CAS → last success/next cycle | 不清 checkpoint、不改成无锁、不把单 batch 当完整 cycle |
| governance 操作无结果 | 查 request ID、capability/confirm、幂等 claim、主/备用 action audit、目标组件和 recovery runner | 不绕过审计直接调用内部 repair/replay |

相关稳定事实分别见 [Event](../03-基础设施/event/README.md)、[Cache](../03-基础设施/cache/README.md)、[Concurrency](../03-基础设施/concurrency/README.md)、[Data Access](../03-基础设施/data-access/README.md)、[Security](../03-基础设施/security/README.md)。

## 5. Mongo consistency finding

按[Scheduler 操作 Runbook](./07-调度任务.md)先确认 effective enable、ready、leader lock、phase、checkpoint 和 last success。finding 是跨集合矛盾证据，不是 repair instruction：

1. 冻结 phase/kind/severity、稳定 cursor/upper bound 和有界内部 ID；
2. 区分当前写链延迟、历史物理/软删除、migration、人工改库或工具缺陷；
3. 用独立只读查询做双向复核；
4. 指派 owner 和处置决定；写操作必须另起方案、审批、备份、apply-time recheck 与复验。

`outbox_missing_answersheet` 不得通过补空 AnswerSheet 或删除已发布 Outbox 归零。危险 AnswerSheet cleanup 当前为 blocked；边界见 [One-off、恢复与生产证据](../03-基础设施/migration-recovery/20-One-off、恢复与生产证据.md)。

## 6. 重启、replay 与修复门禁

仅当已经证明“进程状态故障且持久事实安全、重启不会扩大重复副作用”时才能按正常部署流程重启。以下动作必须独立授权：

- Event replay、dead-letter/hold release；
- checkpoint/SyncRun/业务状态变更；
- migration force/down 或 dirty 处理；
- AnswerSheet、Outbox、Assessment、Report 的补写/删除；
- 任何 one-off apply 或生产数据清理。

先做 dry-run/只读盘点，冻结 exact manifest/fingerprint，准备备份与恢复，apply 时重查，逐批停止和复验。完整规则见 [Migration 与恢复](../03-基础设施/migration-recovery/README.md)。

## 7. 退出与升级材料

排障结束必须给出：

- 已定位的失败层，以及仍为未知的层；
- source/deployed SHA、镜像 digest、effective-config hash、时间窗和实例；
- 命令/查询、退出码、脱敏结果和证据 hash；
- 是否改变了外部状态；若改变，附审批、manifest、备份和复验；
- 当前影响、临时隔离、长期修复、owner 和下次检查时间。

真实环境结论写入[基础设施生产证据台账](../00-总览/10-基础设施生产证据台账.md)；没有 exact-SHA 与有效配置证据时，只能报告“仓库/环境观察”，不能写“生产已恢复”。
