# 健康检查与观测

## 1. 结论

存活、依赖就绪、服务准入和业务可用性是不同层次。单个 `/health` 返回成功不证明异步链、数据库或报告生成正常。

## 2. 检查层次

| 层次 | 关注点 |
| --- | --- |
| liveness | 进程是否存活、事件循环是否卡死 |
| readiness | 必需依赖与 transport 是否可服务 |
| serving readiness | 已完成必要初始化，是否可在依赖降级时继续承接受保护的低流量 |
| dependency | MySQL/Mongo/Redis/MQ/gRPC/IAM 状态 |
| business | 提交、outbox lag、worker 消费、Outcome、Report、统计投影 |
| governance | queue/backpressure/lease/cache/resilience 状态与审计 |

## 3. 排障关联键

优先使用 request ID、event ID、AnswerSheet/Assessment/Report 标识、租户/组织标识串联日志与指标；不要记录 token、答案或报告正文。

collection 的 `/readyz` 严格要求 Redis dependency ready 且首次 resilience
control sync 已完成；`/serve-readyz` 在首次同步后允许 Redis degraded，并在
响应中返回 `serve_ready`、`dependency_ready` 与完整 Redis snapshot。CD 与
周期 runner 使用 `/serve-readyz`，可靠提交与 K6 验收继续使用严格 `/readyz`。

## 4. Mongo consistency audit 指标

| 指标 | 含义 | 解释边界 |
| --- | --- | --- |
| `qs_mongo_consistency_audit_enabled` | 配置是否启用 scheduler | `0` 是当前生产预期，不应单独告警为故障 |
| `qs_mongo_consistency_audit_ready` | application scanner/checkpoint 依赖是否可用 | 只在 enabled 场景判断；不能替代 last success |
| `qs_mongo_consistency_audit_last_success_timestamp_seconds` | 最近一次完整七阶段 cycle 完成时间 | batch 成功不会更新；过旧要结合 enabled/next cycle 判断 |
| `qs_mongo_consistency_audit_drift{severity,kind}` | 最近完整 cycle 的 finding 数 | 是 gauge，不是累计 counter；按 kind/severity 路由 owner |
| `qs_mongo_consistency_audit_errors_total{stage}` | checkpoint load/save、upper bound、scan 等固定阶段错误 | 看增量和 stage；不能用总量判断当前仍失败 |
| `qs_mongo_consistency_audit_checkpoint_cas_conflicts_total` | MySQL checkpoint revision CAS 冲突累计数 | 增长通常意味着并发执行/lease 异常，先保留现场 |
| `qs_mongo_consistency_audit_batches_total{phase,outcome}` | 各阶段 batch outcome 累计数 | 只能证明 batch 活动，不能证明 cycle 完成 |
| `qs_mongo_consistency_audit_batch_duration_seconds{phase,outcome}` | batch 耗时 histogram | 与 batch timeout、Mongo latency 一起判断 |
| `qs_mongo_consistency_audit_scanned_total{phase}` | 每阶段累计扫描 anchor 数 | counter 增长不表示 finding=0 |

当前生产 scheduler 关闭，所以 `enabled=0` 是事实；2026-08-16 的正式 one-off 不写 scheduler gauges/checkpoint。不能拿 one-off 输出推断 `last_success_timestamp_seconds` 已更新。

## 5. 日志与隐私

Mongo audit batch 日志只应包含 cycle、phase、cursor、upper bound、scanned、finding count、duration 和固定 status。样本只保留有界内部 ID；不得记录 AnswerSheet answers、报告正文、token 或 Mongo URI。

观察一个完整周期时必须同时保存：实际部署 SHA、配置 effective value、leader lock 状态、每阶段 batch 进度、last-success 时间和 drift gauges。单条 `started` 日志、一个 phase 的 `success` 或 `/readyz=200` 都不能替代完整周期证据。
