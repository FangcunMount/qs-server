# Probe 与观测验收 Runbook

## 1. 判定边界

端点的稳定语义以[健康探针、治理与持久证据](../03-基础设施/observability/20-健康探针、治理与持久证据.md)为准，日志/指标标签规则见[日志、指标与关联标识](../03-基础设施/observability/10-日志、指标与关联标识.md)。本页只说明怎样执行验收。

不得把单个 200 扩大解释为全依赖、异步链或业务数据健康；特别是 apiserver `/readyz` 的依赖覆盖与 fail-open gap 必须按 canonical 文档保留。

## 2. 前置记录

```bash
git rev-parse HEAD
date -u '+%Y-%m-%dT%H:%M:%SZ'
```

同时记录 deployed SHA、镜像 digest、脱敏 effective-config hash、实例标识、允许源/禁止源和本次观察窗口。探针必须逐实例执行，不能只经负载均衡请求一次。

## 3. HTTP / gRPC probe

按目标环境设置逐实例地址：

```bash
umask 077
export PROBE_BODY="$(mktemp)"
trap 'rm -f "$PROBE_BODY"' EXIT

curl --silent --show-error --output "$PROBE_BODY" \
  --write-out 'status=%{http_code} total=%{time_total}\n' \
  --max-time 5 "$APISERVER_URL/health"
curl --silent --show-error --output "$PROBE_BODY" \
  --write-out 'status=%{http_code} total=%{time_total}\n' \
  --max-time 5 "$APISERVER_URL/readyz"

curl --silent --show-error --output "$PROBE_BODY" \
  --write-out 'status=%{http_code} total=%{time_total}\n' \
  --max-time 5 "$COLLECTION_URL/readyz"
curl --silent --show-error --output "$PROBE_BODY" \
  --write-out 'status=%{http_code} total=%{time_total}\n' \
  --max-time 5 "$COLLECTION_URL/serve-readyz"

curl --silent --show-error --output "$PROBE_BODY" \
  --write-out 'status=%{http_code} total=%{time_total}\n' \
  --max-time 5 "$WORKER_MANAGEMENT_URL/healthz"
curl --silent --show-error --output "$PROBE_BODY" \
  --write-out 'status=%{http_code} total=%{time_total}\n' \
  --max-time 5 "$WORKER_MANAGEMENT_URL/readyz"

grpcurl -cacert "$GRPC_CA_FILE" -cert "$GRPC_CERT_FILE" -key "$GRPC_KEY_FILE" \
  "$APISERVER_GRPC_TARGET" grpc.health.v1.Health/Check
```

删除临时响应前只提取所需状态与脱敏摘要，不保存 token、AnswerSheet、报告正文或内部 error。generic HTTP `/healthz` 是否启用、collection 的 control-sync readiness 和 gRPC health listener 必须按实际 effective config/listener 复核，不能由 YAML 注释推断。

## 4. worker 9092 网络双向验收

版本化 worker production 配置把 management listener 绑定到 `0.0.0.0:9092`；同一 listener 提供 metrics、health/readiness 和 governance，且没有业务 API 认证。必须同时执行：

```bash
# 从批准的 Prometheus/CD/governance 网络
curl --fail-with-body --silent --show-error --max-time 5 \
  "$WORKER_MANAGEMENT_URL/metrics" >/dev/null
curl --fail-with-body --silent --show-error --max-time 5 \
  "$WORKER_MANAGEMENT_URL/healthz" >/dev/null

# 从公网或其它禁止源
if curl --fail --silent --show-error --max-time 3 \
  "$FORBIDDEN_WORKER_MANAGEMENT_URL/healthz"; then
  echo 'FAIL: worker 9092 reachable from forbidden source' >&2
  exit 1
fi
```

`expose: 9092` 不是网络 ACL。还要保存容器 network membership、宿主 mapping、防火墙/Nginx effective config，并确认非 Prometheus、CD 与 apiserver governance 来源不可达。

## 5. Mongo consistency audit 指标检查

从目标 apiserver 实例抓取 metrics，并确认下列时间序列存在/缺失符合 effective `enable` 与 runner 状态：

```bash
curl --fail-with-body --silent --show-error "$APISERVER_METRICS_URL/metrics" |
  grep -E '^qs_mongo_consistency_audit_(enabled|ready|last_success_timestamp_seconds|drift|errors_total|checkpoint_cas_conflicts_total|batches_total|batch_duration_seconds|scanned_total)'
```

机器契约中的完整名称为：

- `qs_mongo_consistency_audit_enabled`
- `qs_mongo_consistency_audit_ready`
- `qs_mongo_consistency_audit_last_success_timestamp_seconds`
- `qs_mongo_consistency_audit_drift{severity,kind}`
- `qs_mongo_consistency_audit_errors_total{stage}`
- `qs_mongo_consistency_audit_checkpoint_cas_conflicts_total`
- `qs_mongo_consistency_audit_batches_total{phase,outcome}`
- `qs_mongo_consistency_audit_batch_duration_seconds{phase,outcome}`
- `qs_mongo_consistency_audit_scanned_total{phase}`

判定顺序：effective enable → ready → leader/lease → batch/phase → checkpoint/CAS → last-success → drift。batch counter 增长不等于完整 cycle 成功；one-off 不写 scheduler gauges/checkpoint。任何历史扫描结果只从[基础设施生产证据台账](../00-总览/10-基础设施生产证据台账.md)引用。

## 6. 依赖故障与持久事实复核

在受控环境分别对 Redis、MySQL、Mongo、IAM、MQ 做经批准的故障注入：

1. 记录注入前逐实例 probe、metrics 和持久状态；
2. 注入单一故障并观察端点状态是否与 canonical 语义一致；
3. 查 runtime/governance snapshot，再查 Outbox、checkpoint、retry-hold/dead-letter 和业务实体；
4. 恢复依赖，验证 readiness、积压和持久状态收敛；
5. 保存时间窗与限制；未执行真实环境测试时明确标记 `not_run`。

禁止在生产临时停数据库/MQ 做未经批准的演练，也不得为让 probe 变绿而删除 Outbox、清 checkpoint 或放宽网络/ACL。

## 7. 完成标准

逐实例探针、允许来源成功、禁止来源失败、Prometheus 抓取、日志关联和持久事实相互一致；证据绑定命令、结果、source/deployed SHA、effective config、owner 和失效期。任何一层缺失都只能签署该层，不能写“生产健康”。
