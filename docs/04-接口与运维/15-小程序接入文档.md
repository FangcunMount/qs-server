# 小程序接入文档

**适用对象**：小程序、H5、Taro 等受试者端前端  
**接入服务**：collection-server  
**机器契约**：[`api/rest/collection.yaml`](../../api/rest/collection.yaml)

本文是小程序接入的执行入口。联调前先按 [collection REST 核验](./02-collection-REST.md)生成/验证当前契约；报告等待机制的容量、WebSocket 和降级步骤见 [12-小程序报告等待接入指南.md](./12-小程序报告等待接入指南.md)。

---

## 1. 接入结论

小程序主流程固定为：

```text
开始会话
  → 请求前落盘 fingerprint + idempotency_key + request_id
  → 提交答卷（HTTP 202 accepted + answersheet_id）
  → 按 answersheet_id 查询 assessment-readiness
  → status=ready 时取得 assessment_id
  → 查询报告状态
  → status=interpreted 后读取报告
```

前端必须按以下契约更新：

| 项目 | 当前契约 |
| ---- | -------- |
| HTTP 服务 | collection-server，业务前缀 `/api/v1` |
| 人格产品 URL | 使用 `/typology-*`，不再使用 `/personality-*` |
| 人格目录身份 | `kind=typology`、`product_channel=typology` |
| 测评/报告兼容身份 | `model.kind=personality`；WebSocket `subscribe.kind=personality` |
| 提交结果 | `POST /answersheets` 只有在 AnswerSheet + 幂等记录 + Outbox 提交后返回 `accepted + answersheet_id` |
| Assessment 就绪 | `GET /answersheets/{id}/assessment-readiness?testee_id=...` 返回 `pending` 或 `ready + assessment_id` |
| 报告完成判断 | 以 `report-status.status=interpreted` 为准，不以 Assessment 的内部状态为准 |
| ID 类型 | 所有 64 位 ID 在 TypeScript 中按 `string` 保存和比较 |

> `typology-assessment-sessions.endpoints.assessment_readiness` 是获取 Assessment 就绪状态的唯一 session 模板。

## 2. 服务、鉴权与响应包络

### 2.1 地址

| 环境 | 示例 |
| ---- | ---- |
| 本地 | `http://localhost:18083/api/v1` |
| 生产 | `https://collect.fangcunmount.cn/api/v1` |
| OpenAPI | `GET /api/rest/collection.yaml` |
| Swagger UI | `/swagger-ui/` |

除下列目录接口外，业务接口都需要：

```http
Authorization: Bearer <IAM JWT>
```

可匿名访问的只读接口：

```text
GET /api/v1/assessment-models
GET /api/v1/assessment-models/hot
GET /api/v1/assessment-models/options
GET /api/v1/typology-models
GET /api/v1/typology-models/categories
```

`GET /assessment-models/{code}`、`GET /typology-models/{code}`、会话、答卷、测评和报告接口仍需登录。

### 2.2 通用响应

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

失败：

```json
{
  "code": 112001,
  "message": "Assessment not found",
  "reference": ""
}
```

前端应同时判断 HTTP 状态码与 `code`；只有 `2xx && code === 0` 才进入成功分支。

## 3. 人格测评完整流程

### 3.1 开始会话

```http
POST /api/v1/typology-assessment-sessions
Content-Type: application/json
```

```json
{
  "model_code": "MBTI_OEJTS",
  "testee_id": "618855887087350318"
}
```

响应 `data`：

| 字段 | 用法 |
| ---- | ---- |
| `model` | 当前已发布模型摘要 |
| `questionnaire` | 与模型绑定的精确题版和题目 |
| `submit_contract` | 提交答卷时必须原样带回的问卷编码、版本、受试者 ID |
| `endpoints.submit_answer_sheet` | 提交地址 |
| `endpoints.wait_report` | legacy 长轮询模板 |
| `endpoints.report` | 报告地址模板 |
| `endpoints.assessment_readiness` | 按 AnswerSheet ID 查询 Assessment pending/ready |

会话只聚合读取已发布模型与问卷，不创建 Assessment。不要缓存“最新问卷版本”替换 `submit_contract.questionnaire_version`。

### 3.2 提交答卷

```http
POST /api/v1/answersheets
Authorization: Bearer <token>
X-Request-Id: <uuid>
Content-Type: application/json
```

```json
{
  "questionnaire_code": "MBTI_OEJTS",
  "questionnaire_version": "1.0.0",
  "testee_id": "618855887087350318",
  "idempotency_key": "mp-MBTI_OEJTS-618855887087350318-20260712-001",
  "answers": [
    {
      "question_code": "Q1",
      "question_type": "Radio",
      "score": 1,
      "value": "{\"option\":\"A\"}"
    }
  ]
}
```

注意：

- `testee_id` 请求端可传字符串或数字，建议始终传字符串。
- `value` 是 JSON 字符串，不是任意嵌套对象。
- `questionnaire_code`、`questionnaire_version`、`testee_id` 取自 session 的 `submit_contract`。
- 重试同一次业务提交时复用同一个 `idempotency_key`；一次新的作答使用新 key。
- `idempotency_key` 必填，只允许 8–128 个安全字符；同一填写人的同键异内容返回 409。
- 建议显式传 `X-Request-Id`，它只跟踪本次 HTTP，不替代幂等键。
- 必须先持久化 fingerprint、`idempotency_key` 和 `request_id`，再发 HTTP。
- fingerprint 使用版本化 `v2:SHA-256`；只用于客户端判断是否为同一作答快照，不代替服务端幂等指纹。
- 每次 HTTP 尝试生成新的 `request_id` 并在发送前落盘；网络重试和进程恢复只复用 `idempotency_key`。

成功受理返回 HTTP 202：

```json
{
  "code": 0,
  "message": "accepted",
  "data": {
    "status": "accepted",
    "request_id": "8bde6a9f-2c3e-4ee8-bb8d-64d48e5b6762",
    "answersheet_id": "71001"
  }
}
```

HTTP 202 表示答卷已可靠受理，前端必须立即落盘 `answersheet_id`。它不表示 Assessment 或报告已完成。

### 3.3 查询 Assessment readiness

```http
GET /api/v1/answersheets/71001/assessment-readiness?testee_id=618855887087350318
```

等待响应：

```json
{"code":0,"message":"success","data":{"status":"pending","answersheet_id":"71001","next_poll_after_ms":2000}}
```

就绪响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "ready",
    "answersheet_id": "71001",
    "assessment_id": "80001"
  }
}
```

`pending` 不是提交失败。按 `next_poll_after_ms` 轮询；超过 60 秒展示“答卷已接收，测评生成延迟”。`404` 表示答卷不存在，`403` 表示当前用户的 ProfileLink 不允许，依赖异常返回 `503`。

### 3.4 查询报告状态

推荐短轮询：

```http
GET /api/v1/typology-assessments/{assessment_id}/report-status?testee_id={testee_id}
```

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "processing",
    "stage": "interpreting",
    "message": "报告生成中",
    "next_poll_after_ms": 3000,
    "updated_at": 1783785600
  }
}
```

前端状态机：

| `status` | 行为 |
| -------- | ---- |
| `processing` | 按 `next_poll_after_ms` 继续轮询；具体阶段看 `stage` |
| `interpreted` | 停止轮询，读取报告 |
| `failed` | 停止轮询，展示 `reason` |

`stage` 用于提示 `queued / processing / scoring / interpreting` 等内部阶段，不作为终态判断。服务端会把内部兼容值 `completed` 对外归一化为 `interpreted`。

可选增强：连接 `WSS /api/v1/report-events`，订阅帧仍使用 `kind=personality`：

```json
{
  "op": "subscribe",
  "assessment_id": "80001",
  "kind": "personality",
  "testee_id": "618855887087350318"
}
```

WebSocket 只有在服务端启用 `report_events` 时存在。断线、超时或未启用时必须降级到 `report-status`。

### 3.5 读取报告

仅在状态为 `interpreted` 后调用：

```http
GET /api/v1/typology-assessments/{assessment_id}/report?testee_id={testee_id}
```

核心响应：

```json
{
  "assessment_id": "80001",
  "model": {
    "kind": "personality",
    "sub_kind": "typology",
    "code": "MBTI_OEJTS",
    "version": "1.0.0",
    "title": "MBTI 人格类型测评",
    "product_channel": "typology",
    "algorithm_family": "factor_classification"
  },
  "primary_score": null,
  "level": { "code": "INTJ", "label": "建筑师" },
  "conclusion": "...",
  "dimensions": [],
  "suggestions": [],
  "model_extra": {
    "type_code": "INTJ",
    "type_name": "建筑师",
    "one_liner": "...",
    "image_url": "https://...",
    "rarity": { "percent": 2.1, "label": "较少见", "one_in_x": 48 }
  },
  "created_at": "2026-07-12 12:00:00"
}
```

展示建议：

- 人格主结果优先使用 `model_extra.type_code/type_name/one_liner`，再回退到 `level`。
- 通用结果使用 `primary_score`、`level`、`dimensions`、`suggestions`。
- 不要用 `algorithm` 判断页面类型；产品分流使用 URL 上下文或 `model.product_channel`，具体模型使用 `model.code`。
- `model_extra`、`primary_score`、`level` 都可能为空，类型定义必须可选。

## 4. TypeScript 最小类型与状态机

```ts
type Id = string;

interface SubmitAccepted {
  status: 'accepted';
  request_id: string;
  answersheet_id: Id;
}

interface AssessmentReadiness {
  status: 'pending' | 'ready';
  answersheet_id: Id;
  assessment_id?: Id;
  next_poll_after_ms?: number;
}

interface ReportStatus {
  status: 'processing' | 'interpreted' | 'failed';
  stage?: string;
  message?: string;
  reason?: string;
  next_poll_after_ms?: number;
  updated_at: number;
}

function assertAccepted(value: SubmitAccepted) {
  if (value.status !== 'accepted' || !value.answersheet_id) {
    throw new Error('durable submit contract violation');
  }
}
```

建议页面状态：

```text
idle
  → loading_session
  → answering
  → submit_prepared
  → answersheet_accepted
  → assessment_pending
  → assessment_ready
  → report_processing
  → report_ready | failed
```

本地恢复至少保存：`fingerprint`、`idempotency_key`、`request_id`、`model_code`、`testee_id`、`answersheet_id`、`assessment_id`。

## 5. 禁止继续调用的旧契约

```text
/api/v1/personality-*
/api/v1/answersheets/{id}/assessment
/api/v1/answersheets/submit-status
/api/v2/assessments*
```

不得调用已删除的 AnswerSheet→Assessment 旧接口，也不得通过 Assessment 列表按 `answer_sheet_id` 匹配作为新提交兜底。唯一正常路径是 `assessment-readiness`。

## 6. 联调验收清单

- [ ] 所有 64 位 ID 在 TypeScript 中使用 `string`
- [ ] session 返回的题版与 submit 使用的版本完全一致
- [ ] HTTP 请求前已落盘 fingerprint、幂等键和 request ID
- [ ] POST 答卷返回 202 后立即保存 `answersheet_id`
- [ ] 网络超时、429、503 重试复用同一幂等键；409 不自动重试
- [ ] 按 readiness 的 `next_poll_after_ms` 轮询，ready 后保存 `assessment_id`
- [ ] session 使用 `assessment_readiness` 模板
- [ ] 报告轮询按 `next_poll_after_ms` 退避
- [ ] 仅在 `interpreted` 后读取报告
- [ ] 所有报告请求携带同一个 `testee_id`
- [ ] WebSocket 使用 `kind=personality`，且具备 HTTP 降级
- [ ] 404 不重试读取他人报告；429 采用指数退避

## 8. Task 待填写列表与入口

本节说明家庭档案下的待填写 Task、仅使用 task_id 的直接入口和微信开放提醒。服务端合同以当前路由与生成 REST 契约为准；客户端行为需绑定实际客户端版本验证。部署、上传及真实微信验收结果应记录在有日期、版本和原始证据的发布记录中。

### 8.1. 权威链路

首页按当前家庭档案查询 `GET /api/v1/plan-tasks?testee_id=...`。collection 从登录凭证取得 UserID，在查询前后校验有效 IAM ProfileLink；内部 PlanEntry 读取原 assessment_task 和 enrollment。没有新增任务账本。pending、opened 可展示；终态、已关联 assessment、超过硬失效时间的任务不展示，错过开放窗口的 pending 任务也不展示。

列表展示测评名称、所属计划、开放时间和填写截止时间。Plan 没有独立名称字段，所属计划用测评名称及计划编号展示。opened 的填写截止取 expire_at，pending 还未产生 expire_at 时显示 due_at；due_at 是计划履约时间，expire_at 才是现有入口硬失效时间，两者不合并改写。切换家庭档案、返回首页、下拉及前台每 15 秒刷新；失效后即使列表响应尚未刷新也不能点击开始。

Task 入口为 `pages/assessment/fill/index?task_id=...`，调用 `GET /api/v1/plan-task-entries/{task_id}`。服务端读取 Task 的机构、档案、量表，校验 opened、open_at、expire_at、assessment 关联及有效 enrollment；collection 再校验当前用户的档案关系。URL 上补传 token、问卷 code、模型 code、档案 ID 不改变这些事实，TaskID 不构成授权。

入口解析取 Task 量表的已发布模型绑定，返回精确 questionnaire_code、questionnaire_version 和 model_version；小程序按精确题版加载，并在开始作答时携带精确模型版本。版本或返回题版不匹配则拒绝，不能回退到外传 code 或默认最新题版。

开始作答仍用原 answering-start 准入，来源为 `plan_task`。提交保留 answering_start_id、origin_ref 和 task_id；Survey 原来源解析校验机构、档案和模型，同时校验开放时间、硬失效及已关联 assessment。原 AnswerSheet 冻结 admission、来源快照、可靠受理和 Journey assessment intake 不改。intake 使用原 Task resolver / CompleteTask 建立关联；原完成路径是 best effort，须实际核对 Task completed 与 assessment_id，不能仅凭提交返回成功认定关联完成。

Task/Plan 当前没有独立的创建时模型版本快照；已有版本冻结点在作答开始及答卷准入。当前冻结点位于作答开始及答卷准入；已受理答卷和历史事件继续使用原快照。

### 8.2. 旧入口与历史提醒兼容

- 旧 Task 页面链接含 `task_id` 和 token：新版小程序优先按 TaskID 解析并丢弃入口 token；仍要求登录及有效档案关系。
- 旧 REST `/plan-task-entries/{task_id}/{token}` 保留；历史 token 参数忽略，不授权。内部 protobuf Token 字段保留并标为 deprecated，兼容旧 collection。
- 新 Task entry_token 为空，entry_url 的查询参数只有 task_id；新开放事件继承此无 token URL。
- 新构造的微信页面统一为 `pages/assessment/fill/index?task_id=...`。旧持久化 entry_url 即使含 token，也只提取 TaskID 用于新页面构造。
- 历史事件、Task 字段和已发送提醒不批量改写、不回填、更不重发。提醒 recipient snapshot、delivery ledger、调用标记、unknown 人工复核和发送截止策略保持原样；结果未知不能自动重发。
- 正常登录 access/refresh token、Authorization header，以及医生推荐 ae token 和其他扫码契约均保留。

旧小程序版本仍要求 Task token，不能消费新生成的无 token 链接。正式切换必须协调服务端与小程序发布时间，在旧客户端仍承担入口流量时不要启动新的无 token Task 提醒；不得通过重发历史通知弥补版本切换。该风险须在生产部署方案中明确，不能把“服务端先部署”理解为任意长时间的混合版本兼容。

### 8.3. 验证范围

自动回归应覆盖：仅 TaskID、旧 token 忽略、未开放与未来开放、完成/取消/过期、有效 enrollment、越权档案、外传 code/档案无法覆盖服务端事实、硬失效边界及无 token URL。源码入口见 `internal/collection-server/application/planentry`、`internal/apiserver/application/plan/task_entry_resolver.go` 和 `internal/apiserver/infra/mysql/answersheetattribution/resolver.go`。

代码测试、真实数据库提交、已部署服务端、客户端构建与微信提醒送达分别记录。可选跳过的数据库测试、提交返回成功或列表刷新均不能替代业务关联验收。

### 8.4. 发布与业务验收步骤

1. 先确定已授权的测试环境、新服务端版本及可消耗的真实测试 Task。服务端需同步 apiserver、collection 及 collection 证书允许的 ListParticipantTasks ACL；没有新增数据库迁移。按现有部署 Runbook 准备 exact SHA、镜像 digest、回滚版本和兼容窗口，生产执行另行授权。
2. 微信开发者工具使用与待验收客户端版本对应的构建。确认接口指向测试环境；正式小程序上传与发布由用户完成。
3. 登录测试用户，在首页选择其有效家庭档案，从待填写列表进入 opened 测试 Task。核对名称、计划编号、开放／截止；网络请求只有 TaskID 定位，正常 Authorization 登录凭证继续存在。
4. 完成作答并提交，记录 task_id、answering_start_id、answer_sheet_id 和 assessment_id。等异步处理完成后从服务端核对 assessment 的 plan／task 来源及原模型版本；查询 assessment_task 的 status、assessment_id、completed_at，要求 completed 且关联相同 assessment。返回首页，列表应移除此任务。
5. 用自定义编译路径 `pages/assessment/fill/index`、参数 `task_id=<测试Task>` 验证直接进入；清理本测试项目登录态后再进入，登录／必要注册后应继续原 Task。不要清理其他项目的登录态。
6. 使用另一有效 Task 验证新开放提醒页面只有 TaskID，实际微信收到后点击并完成相同链路。提醒测试须使用新 Task／新开放事件，不重放既有 sent 或 unknown delivery。
7. 用无关系的测试用户、pending、未来 open_at、completed、canceled、expired 及到 expire_at 的 Task 测试入口、开始和提交拒绝；补传 q、mc、t、testee_id 不能绕过。有效用户保留原机构／enrollment 范围。
8. 验证旧含 token Task 链接在新版小程序可用；抽测医生推荐 ae token、普通问卷、人格和行为测评。分别保存代码 SHA、自动检查、已部署版本与实际业务结果；尚未执行的项目保持未验收。

真实业务关联可只读核对：

```sql
SELECT id, org_id, testee_id, plan_id, enrollment_id, status,
       assessment_id, open_at, expire_at, completed_at
FROM assessment_task
WHERE id = <测试TaskID> AND deleted_at IS NULL;
```

在记录中保留必要 ID 与版本，隐藏登录凭证、openid、个人资料及答案内容。本说明不授权生产部署或历史通知重发。
