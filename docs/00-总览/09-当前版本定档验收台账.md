## 6. Mongo consistency audit 当前真值

### 6.1 能力边界

- scanner 对 Mongo 业务集合只有读方法，没有 repair port；“只读”专指不写 Mongo 业务事实。
- scheduler 会写 MySQL `mongo_consistency_audit_checkpoint`，并使用 Redis leader lease；不能把它描述为“对所有存储零写入”。
- one-off CLI 不启动 scheduler、不写 checkpoint，退出码 `0/2/1` 分别表示无漂移/发现漂移/执行失败。
- 七阶段固定为 `answersheet_outbox`、`outbox_answersheet`、`generation_run`、`generated_terminal`、`retry_outbox`、`model_release`、`published_model_runtime`。
- 每阶段冻结 upper bound，以稳定 cursor 分批推进；checkpoint 的 `revision` 通过 compare-and-swap 防止并发覆盖，完成后保存 last completed cycle 和 next cycle time。
- scheduler 以 `mongo_consistency_audit` workload 获取自动续租 leader lock；拿不到锁就跳过，Redis lock 不可用则不启动。

### 6.2 生产状态与启用门禁

`configs/apiserver.prod.yaml` 当前 `mongo_consistency_audit.enable: false`。现有 269 条 `high` finding 意味着启用门禁未通过；本次只补文档，不修改生产配置。

只有同时满足以下条件，才能另起受控变更把生产开关改为 `true`：

1. 确认 MySQL 000069 checkpoint 表、Mongo 000024 索引和目标部署 SHA 均已就绪；
2. 对正式部署版本执行全七阶段 one-off，扫描完整结束且不存在未处置的 high drift；
3. 对每个 finding 冻结清单、原因、owner 与处置决定；任何 repair/delete 都有独立审批和复验；
4. Redis leader lock、Mongo backpressure、Prometheus 指标和告警查询均可用；
5. 明确 batch/cycle 容量预算、回退方式和观察窗口，并取得生产配置变更授权。

当前第 2、3 项未满足，所以结论只能是“能力已实现、生产 scheduler 关闭、one-off 有 high drift”，不能写成“周期审计已上线”。

## 9. 破坏性操作边界

本台账不授权任何新的生产 `DROP`、`DELETE`、Mongo collection 删除、Redis 批量清理、checkpoint 重置或业务 ledger 修改。

1. 269 条孤立 Outbox 只能在独立维护任务中处理；必须先冻结精确清单、说明业务与合规影响、准备备份/回滚和写后复验。
2. 不得为了让指标变绿而删除 finding、直接改 checkpoint、跳过阶段或降低 severity。
3. scheduler 的 `enable: true` 是独立生产配置变更，不随文档合并、CI 成功或一次 one-off 自动生效。
4. 兼容观察窗口完成只提供退役候选证据，不自动授权删除接口、字段、指标或历史数据。
