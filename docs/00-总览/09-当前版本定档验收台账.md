## 9. 破坏性操作边界

本台账不授权任何生产 DROP、DELETE、Mongo collection 删除或 Redis 批量清理。

1. MySQL 物理删除前必须有当前 schema/row count、备份、恢复命令、审批、执行窗口和执行后 migration/schema 核验。
2. Mongo 候选集合已有正式 archive 与 mongorestore dry-run，但仍需保留期限、明确对象清单和删除批准；不得用备份成功代替恢复演练。
3. Redis 清理必须精确到 DB、family、namespace 和 key pattern；先证明旧实例退出并等待最长 data TTL。无 TTL token 只能单独审批，禁止使用宽泛通配删除。
4. Statistics running ledger 禁止批量改状态或先删锁；必须先满足 FINAL-P1-005 的三项只读条件。
5. Attention 恢复禁止直接在三个 worker 实例上并发 apply；先解决 leader/lease 或采用受控单实例执行。

## 11. 定档签署条件

当前版本只有满足以下条件后才能从“阻断”升级：

- FINAL-P1-001 至 FINAL-P1-005 全部关闭，或形成符合标准的正式风险接受。
- FINAL-P1-006 为每个活跃兼容项补齐 Owner、观察窗、指标和退出版本。
- 当前 HEAD 的全仓测试、必跑 CI、制品和三进程运行指纹一致。
- Attention 恢复后全量对账为 0，Evaluation 数据库唯一性在真实 MySQL 验证。
- Statistics 旧 running ledger 逐条结算，不留下无法解释的运行中状态。
- 所有高置信物理遗留对象保持“待批准”，或在独立运维窗口完成备份、删除、验证和回滚闭环。
- 本台账最终只保留当前事实，不重新混入某个模块的历史过程日志。

目标模式继续按“只读验收 → 小批修复 → 聚焦测试 → Conventional Commit 中文主题 → push → CI/CD → 运行证据 → 更新台账”维护。每个可独立验收阶段立即提交，不跨阶段积攒；提交或 push 本身不提升任何验收状态。
