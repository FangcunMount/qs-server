# 项目完成画像与验收标准

> 状态：现行验收基准。本文定义“qs-server 什么情况下可以定档”，不记录某个 commit 的当前结论。当前版本证据与结论见[当前版本定档验收台账](./09-当前版本定档验收台账.md)。

## 1. 目标与边界

项目完成不是“代码可以编译”，也不是“主链路演示成功”。`qs-server` 只有同时满足业务闭环、工程质量、数据可演进和生产可证明四类要求，才具备定档条件。

本标准从两个方向建立完成画像：

1. 业务方向：4 个核心业务模块与 3 个辅助业务模块。
2. 技术方向：事件、缓存、背压、分布式锁、重试、数据迁移、安全、可观测性和运行时治理等横切能力。

每个方向都从代码、接口、数据、状态与一致性、安全、容量、测试、可观测性、运维和遗留兼容等角度验收。本文不把历史文档、命名中的 `legacy` 或单次测试通过直接当成删除、完成或生产成功的证据。

## 2. 完成画像

### 2.1 业务模块

| 类型 | 模块 | 完成时必须成立 |
| --- | --- | --- |
| 核心 | `survey` | 精确问卷版本可发布、作答契约可执行、答卷可靠受理且作答事实受权限保护 |
| 核心 | `modelcatalog` | 模型身份、Definition、Questionnaire binding 和 published release 可冻结、可查询、可回放 |
| 核心 | `evaluation` | Assessment、Run、Outcome 的执行、幂等、失败、重试和一致性恢复闭环成立 |
| 核心 | `interpretation` | Outcome 到报告事实、模板、自动化执行、交付状态和历史追溯闭环成立 |
| 辅助 | `actor` | 操作者、从业者、受试者、ProfileLink、租户与资源访问边界成立 |
| 辅助 | `plan` | 计划、入组、任务、调度、完成和通知语义成立，不出现部分成功冒充完成 |
| 辅助 | `statistics` | 统计事实、增量/重建、发布水位、读模型和运行治理成立 |

核心模块决定主要业务事实，辅助模块仍属于定档范围；“辅助”不等于可以降低数据、安全或恢复标准。

### 2.2 技术模块

| 技术模块 | 完成时必须成立 |
| --- | --- |
| Event / Outbox / MQ | 事件身份、payload、owner、delivery、事务边界、重放和失败归属明确 |
| Cache / Signal / Warmup | 事实源、key、TTL、失效、降级、恢复和多实例收敛明确 |
| Rate limit / Gate / Backpressure | 入口、队列、in-flight、下游预算和超时均有界，过载不会转化为无限堆积 |
| LockLease / Leader / Duplicate suppression | workload、key、TTL、续租、lease loss、释放和降级语义明确 |
| Retry / Manual governance | 业务重试、Outbox 重试、MQ 重投、hold、人工动作和终态不混用 |
| Data / Migration / Retirement | MySQL、MongoDB、Redis 事实边界清晰；迁移可重复、可验证、可恢复；遗留对象有退出证据 |
| IAM / Security / Tenant | 认证、主体、租户、能力、资源归属和内部服务身份形成完整授权链 |
| Runtime / Scheduler / Shutdown | 三进程装配、后台任务、并发、优雅关闭、配置覆盖和健康门禁明确 |
| Observability / Governance | 日志、指标、状态、告警、审计和人工操作能够证明成功、失败与恢复 |
| Delivery / Performance | CI、制品、部署 SHA、运行进程、容量场景和回滚路径能够闭环 |

## 3. 十二个验收角度

每个业务模块和技术模块都必须回答下列问题；不适用项要说明原因，不能留空。

| 角度 | 验收问题 | 最低证据 |
| --- | --- | --- |
| 1. 职责与边界 | 负责什么、不负责什么，谁拥有最终业务事实 | 模块注册、组合根、端口与调用方 |
| 2. 代码与装配 | 正常路径是否唯一，依赖是否在生产组合根真实注入 | application、container、registry、启动路径 |
| 3. 领域与不变量 | 状态机、身份、幂等、版本和不可变事实是否被代码保护 | domain、validator、错误分类、表征测试 |
| 4. REST / gRPC / Event 接口 | 输入、输出、错误、版本、幂等与兼容契约是否一致 | OpenAPI、proto、events/signals 配置、handler |
| 5. 数据与迁移 | MySQL 表、Mongo 集合、索引、约束、迁移和数据所有权是否收敛 | migration、PO、Repository、生产只读盘点 |
| 6. 状态与一致性 | 跨 document、跨库、跨进程的成功点、失败窗口和恢复语义是否确定 | transaction、Outbox、补偿、故障测试 |
| 7. 安全与隐私 | 身份、租户、能力和资源归属是否逐层校验 | middleware、authorizer、query filter、越权测试 |
| 8. 缓存与并发 | 缓存一致性、重复请求、锁、限流、背压和降级是否不破坏主事实 | capability、配置、并发测试、故障注入 |
| 9. 测试与质量门禁 | 正向、负向、并发、事务、迁移和架构测试是否进入必跑门禁 | 本地结果、CI job、跳过项说明 |
| 10. 可观测与运维 | 能否从日志、指标、治理接口和手册判定阶段、失败与恢复 | 指标、结构化日志、告警、runbook |
| 11. 性能与容量 | 正常、峰值、下游慢、Redis/MQ/DB 异常时是否满足预算 | 压测场景、资源曲线、拒绝/恢复证据 |
| 12. 遗留与兼容 | 兼容入口是否仍有消费者、数据和退出条件，能否删除 | 调用搜索、流量、数据计数、迁移与回滚 |

## 4. 证据等级

| 等级 | 证据 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- | --- |
| E0 | 源码与静态搜索 | 代码存在、调用和候选死代码 | 生产是否执行、数据是否存在 |
| E1 | 机器契约 | API、事件、配置和 schema 的声明 | 实现与运行时一定遵守 |
| E2 | 单元/架构测试 | 局部行为、边界和负向契约 | 真实数据库事务和跨进程行为 |
| E3 | 真实依赖集成测试 | 数据库、索引、事务、并发和迁移行为 | 完整部署与生产流量 |
| E4 | 当前运行时闭环 / 故障 / 压测 | 多进程主链、故障语义或容量场景 | 生产数据分布和长期稳定性 |
| E5 | 当前 SHA 的必跑 CI | 可重复构建、测试、lint 与策略门禁 | 部署目标运行的是该 SHA |
| E6 | 部署与运行时指纹 | 制品、部署、健康和进程 SHA 一致 | 业务数据长期正确、接口无人调用 |
| E7 | 生产只读证据 | 实际数据、索引、流量、日志、指标和消费者 | 未覆盖时间窗之外永远不会发生 |

结论必须写明使用到的最高等级和仍缺失的等级。没有 E7 时，可以完成代码定档，但不能把遗留数据库对象判为“已可安全删除”，也不能把容量或长期运行写成生产已确认。

## 5. 状态与严重级别

### 5.1 指标颜色

| 颜色 | 含义 |
| --- | --- |
| 绿 | 当前基线已满足该指标，证据与结论匹配 |
| 黄 | 主体成立，但有明确的补证、兼容窗口或非阻断缺口 |
| 红 | 存在安全、数据、契约、恢复或发布阻断，不能定档 |

### 5.2 模块状态

| 状态 | 判定 |
| --- | --- |
| 未验收 | 尚未沿责任链完成当前基线复核 |
| 阻断 | 存在至少一个红色硬阻断项 |
| 有条件通过 | 无硬阻断；仅有具备 owner、期限、监控和退出条件的黄色项 |
| 通过 | 本版本范围内的验收项全部满足，剩余项明确不属于本版本 |
| 不适用 | 经证据说明该角度确实不适用于该模块 |

问题严重级别使用 P0 至 P3：P0 为必须先修复的安全/数据/核心不变量问题；P1 为定档前必须关闭或经正式决策降级的问题；P2 为有明确退出条件的改进项；P3 为不影响本版行为的维护项。

## 6. 硬阻断

出现以下任一情况，模块和当前版本均不得标记为通过：

1. 未授权主体可读取、修改或触发他人/他租户业务事实。
2. 接口可能在主事实和恢复事实持久化前返回成功。
3. 同一业务幂等意图可能产生两份有效事实，或同 key 不同内容不会冲突。
4. published snapshot、模型 release 或 evaluation input 不能精确回放历史语义。
5. 多步写入可能留下对外可见中间态，且没有事务、恢复或阻断读策略。
6. 迁移可能破坏生产数据，或 schema / index 事实源不确定。
7. Plan、Evaluation、Interpretation 或 Statistics 将部分成功投影为完成。
8. 必跑测试、构建、迁移、制品或部署 SHA 门禁失败或被跳过而未说明。
9. P0 未关闭，或 P1 没有正式降级决策、owner、期限、可观测信号和退出条件。

## 7. 遗留代码与数据对象的判定

遗留项统一分为四类：

| 分类 | 判定与动作 |
| --- | --- |
| 已确认可删除 | 当前代码无调用、机器契约无暴露、生产窗口无流量、数据已迁移且有回滚/备份 |
| 活跃兼容 | 仍有调用方或数据依赖；保留并记录 owner、监控与退出条件 |
| 高置信候选、生产未证实 | 静态证据显示新写已切断，但缺生产数据/流量证据；不得直接删除 |
| 证据不足 | 无法确定 owner、消费者或数据语义；先补盘点，不做破坏性操作 |

MySQL 表、MongoDB 集合、索引、API、proto 字段、事件、配置开关和 fallback 分支都使用同一判定。名称中出现 `legacy`、`v1`、`deprecated` 或“兼容”只生成候选，不产生删除授权。

删除前至少需要：当前调用搜索、跨仓消费者确认、生产对象与行/文档计数、观察窗口流量、数据迁移/归档方案、回滚方案和删除后的门禁。

## 8. 定档层级

| 层级 | 进入条件 |
| --- | --- |
| 完成画像建立 | 两个方向和十二角度已有明确标准与责任范围 |
| 代码定档候选 | 7 个业务模块和技术模块均已验收，无“未验收”空白 |
| 代码定档 | 无红项；黄色项满足有条件通过要求；当前 SHA 的 E5 门禁成功 |
| 部署确认 | 代码定档 SHA 的制品与运行进程一致，部署、健康、配置和回滚已验证 |
| 生产确认 | 关键业务闭环、数据一致性、错误率、延迟、队列和遗留退出指标在约定窗口内成立 |

“代码定档”“部署确认”“生产确认”必须分开记录。候选构建成功或一次部署健康不能替代生产确认。

## 9. 目标模式

定档工作完成后采用目标模式持续维护：

1. 本文保持稳定。只有业务边界、质量门槛或证据规则正式改变时才修改，并在 commit/ADR 中说明原因。
2. [当前版本定档验收台账](./09-当前版本定档验收台账.md)绑定一个基线 SHA，随当前目标、证据和结论更新；历史由 Git 保留。
3. 每轮只验收一个业务模块或一个明确技术专题，沿入口、调用、数据、事件、运行和测试责任链完成后再切换。
4. 每个目标必须有：编号、期望不变量、影响面、owner、证据、退出条件、回滚/恢复方式和状态。
5. 修复批次结束后重新跑受影响的聚焦测试、广泛门禁、文档门禁和必要的真实依赖/运行时门禁；不得继承旧 SHA 的通过结论。
6. 红项优先于黄色项，安全与数据问题优先于结构清理；遗留删除必须等生产退出证据。
7. 模块结论只能由证据升级，不能因“代码看起来完成”自动升级。
8. 一个目标可以拆成多轮小批次 commit；每个可独立验收阶段完成后立即 commit，不跨阶段积攒改动。每个 commit 只承载一个可描述的不变量或一组不可分割的契约变更，并独立记录验证结果。
9. 在门禁通过、工作区范围清晰、没有夹带用户未授权改动且远端目标明确时，可以由执行者自行 push；push 后必须跟踪远端 CI/CD，并把 commit、分支、run 与运行 SHA 回填台账。
10. commit 或 push 不是验收成功。远端失败时继续在同一目标下修复、重新提交和复验，直到退出条件成立或形成新的阻断结论。
11. commit message 使用 Conventional Commits 类型前缀，例如 `feat:`、`fix:`、`docs:`、`test:`、`ci:`、`refactor:`、`chore:`；前缀后的主题使用中文，并准确描述本阶段产出。

推荐节奏为：`建立目标 -> 只读验收 -> 讨论结论 -> 小批修复 -> 重新验收 -> 更新台账 -> 进入下一目标`。

提交节奏允许是：`目标 A / batch 1 -> commit -> batch 2 -> commit -> push -> CI/CD -> 运行证据`。不得为了追求单 commit 而把高风险改动堆成大批次，也不得用频繁 commit 掩盖尚未满足的模块退出条件。

## 11. 全局签署检查

最终定档前必须确认：

- 7 个业务模块无未验收项，模块边界与跨模块 Journey 一致。
- 技术模块无未验收项，事件、缓存、背压、锁、重试和运行时责任不重叠。
- REST、gRPC、事件、信令、配置和数据库契约与实现同步。
- MySQL/MongoDB schema、索引和迁移状态有真实依赖证据；遗留对象有分类。
- 权限测试覆盖正向访问、同租户越权、跨租户越权和内部服务调用。
- 事务、并发、幂等、故障与恢复测试进入必跑门禁或明确记录补证原因。
- 当前 SHA 的 CI、制品、部署和运行时指纹可追溯。
- 所有黄色项具备 owner、期限、监控、退出条件和重新决策触发器。
