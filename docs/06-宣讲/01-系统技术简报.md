## 1. 本文回答

本文用一条系统主线和五张决策案例卡，回答：

1. 多模型测评平台为什么是“模块化单体 + 三进程”，而不是三个微服务；
2. AnswerSheet 如何从“进程内排队即返回 202”收敛到 Mongo transaction + Outbox 可靠受理；
3. Evaluation 为什么只固化 Outcome，Interpretation 为什么拥有报告生命周期；
4. 110 QPS 通过、120 QPS 失败时，为什么不能只看成功率就宣称容量通过；
5. Mongo 一致性审计如何发现跨集合漂移，同时保持只读且不越权修复。

## 2. 30 秒结论

qs-server 是一个以 `qs-apiserver` 模块化单体为业务核心，由 `collection-server`、`qs-apiserver`、`qs-worker` 三个进程组成的事件驱动多模型测评后端。

```text
Survey 保存作答事实
  -> ModelCatalog 提供已发布模型资产
  -> Evaluation 执行评估并提交不可变 Outcome
  -> Interpretation 基于冻结 Outcome 生成可查询报告
```

这套设计的主线不是“用了 MongoDB、Redis、NSQ”，而是在三类压力下维持明确承诺：

- 入口可以限流、背压和快速拒绝，但不能在答卷与 Outbox 持久化前返回 `202 Accepted`；
- 评估与报告可以独立失败和重试，但 Interpretation 不能重算或覆盖 Evaluation Outcome；
- 压测和审计必须保留失败证据；容量 FAIL 不因“最终成功”被涂绿，finding 也不自动变成 repair instruction。

## 4. 案例卡一：为什么是模块化单体 + 三进程

### 问题

一个同时支持医学量表、类型人格、连续特质、行为能力和认知任务的平台，既要避免每种模型重写一套提交/评估/报告链，又要把前台流量、核心业务事务和耗时异步执行隔离开。

### 约束

- Survey、ModelCatalog、Evaluation、Interpretation、Actor、Plan、Statistics 七个业务模块当前在同一 `qs-apiserver` 组合根中装配，共用发布单元和部分事务边界；
- 小程序 BFF、身份投影、缓存、限流和报告等待的资源模型，与核心业务写入不同；
- 计分、结果提交和报告生成可能长于一次 HTTP 请求，需要消息重试、租约和人工处置边界；
- 当前团队和交付规模没有证据说明值得承担分布式事务、多仓契约和独立发布的微服务成本。

### 备选方案

1. 单进程分层单体：部署简单，但前台流量与异步耗时任务互相争抢资源；
2. 按领域拆微服务：独立伸缩更彻底，但在数据所有权、发布节奏和团队边界尚未独立时，会提前引入分布式成本；
3. 模块化单体 + 边界进程：领域规则仍集中在 apiserver，只将入口适配和异步控制面独立运行。

### 决策

当前选择第 3 种：`qs-apiserver` 拥有业务规则和业务事实，`collection-server` 承接 BFF 和入口保护，`qs-worker` 承接事件消费、重试和消息结算。这是运行职责分离，不是三个自治业务中心。

### 代码链

```text
collection REST -> collection application / ACL -> internal gRPC
  -> qs-apiserver application + domain modules -> transaction + Outbox
  -> NSQ -> qs-worker handler -> qs-apiserver internal gRPC use case
```

- 进程入口：[`cmd/collection-server`](../../cmd/collection-server)、[`cmd/qs-apiserver`](../../cmd/qs-apiserver)、[`cmd/qs-worker`](../../cmd/qs-worker)；
- 模块注册表：[`internal/apiserver/container/modules/registry.go`](../../internal/apiserver/container/modules/registry.go)；
- 组合根：[`internal/apiserver/process`](../../internal/apiserver/process)、[`internal/collection-server/process`](../../internal/collection-server/process)、[`internal/worker/process`](../../internal/worker/process)；
- 真源解释：[系统地图](../00-总览/03-系统地图.md)与[三进程协作总览](../01-运行时/00-三进程协作总览.md)。

### 失败窗口

- collection 过载时应在有界预算后返回 429/503，不应无界排队或伪造受理成功；
- apiserver gRPC 不可用时，collection 不能绕过业务中心直写核心库；
- MQ 不可用时，已提交 Outbox 留在数据库中等待 relay；
- worker 重复收到消息时，正确性来自业务幂等、claim/CAS、状态机和租约，不是假设 MQ exactly-once。

### 验证

- 当前代码事实：模块 registry 与三个 process composition root；
- 契约事实：`api/grpc/proto`、`configs/events.yaml`和 `configs/signals.yaml`；
- 文档证据：[运行时真源](../01-运行时/README.md)和[源码事实矩阵](../00-总览/07-源码事实矩阵.md)。

### 仍存边界

- 三进程仍共用一个仓库、一次发布族和多项基础设施，不具备微服务的完整自治性；
- collection 与 worker 可独立伸缩，不等于核心数据已能独立分片；
- 是否进一步服务化，应由数据所有权、团队、发布节奏和故障隔离证据重新决策，不由进程数量决定。

## 5. 案例卡二：AnswerSheet 从内存受理收敛到 Mongo transaction + Outbox

### 问题

历史链路在 AnswerSheet 进入 collection-server 进程内 SubmitQueue 后即返回 `202 Accepted`。如果进程在后台 worker 持久化前崩溃，客户端已收到成功，Mongo 却没有 AnswerSheet 和 `answersheet.submitted` Outbox，这个成功承诺无法恢复。

### 约束

- `202` 只应表示“系统已可靠接管请求”，不能暗示 Assessment、Evaluation 或报告已完成；
- 相同 `idempotency_key` 必须收敛到同一 AnswerSheet，不同业务内容复用同一键必须冲突；
- AnswerSheet 和驱动后续处理的 Outbox 都在 MongoDB，可以使用同库 transaction 原子提交；
- 入口仍需要有界并发、超时和快速拒绝，不能用“可靠”为理由恢复无界排队；
- Assessment 创建、评估和报告仍然适合异步执行，不应塞回 `202` 之前。

### 备选方案

1. 保留内存入队即 202：确认快，但进程崩溃窗口无法恢复；
2. 先持久一条 SubmissionCommand，再异步生成 AnswerSheet：可承接更大峰值，但引入新状态机、数据清理和运维成本；
3. 在 `202` 前用现有 Mongo transaction 提交 AnswerSheet + 幂等事实 + Outbox，后续由 Worker 异步处理。

### 决策

当前已直接切换到第 3 种。Submit Gate 限制在途请求，SubmitCoalescer 降低跨实例重复工作，但最终正确性由 Mongo unique index、payload fingerprint 和 AnswerSheet + Outbox transaction 保护。只有可靠事实已提交才返回 `202 + request_id + answersheet_id`。

### 代码链

```text
POST /api/v1/answersheets -> collection REST / SubmissionService
  -> AnswerSheet gRPC -> apiserver submission service
  -> TransactionalSubmissionDurableStore.CreateDurably
  -> Mongo: AnswerSheet + idempotency metadata + Outbox -> commit -> 202
  -> answersheet.submitted -> worker -> EnsureAssessment
```

- REST 入口：[`internal/collection-server/transport/rest/handler/answersheet_handler.go`](../../internal/collection-server/transport/rest/handler/answersheet_handler.go)；
- collection 受理用例：[`internal/collection-server/application/answersheet/submission_service.go`](../../internal/collection-server/application/answersheet/submission_service.go)；
- gRPC 业务入口：[`internal/apiserver/transport/grpc/service/answersheet.go`](../../internal/apiserver/transport/grpc/service/answersheet.go)；
- 事务边界：[`internal/apiserver/application/survey/answersheet/transactional_durable_store.go`](../../internal/apiserver/application/survey/answersheet/transactional_durable_store.go)与 [`internal/apiserver/infra/mongo/answersheet/durable_submit.go`](../../internal/apiserver/infra/mongo/answersheet/durable_submit.go)；
- 后续驱动：[`configs/events.yaml`](../../configs/events.yaml)与 [`internal/worker/handlers/answersheet_handler.go`](../../internal/worker/handlers/answersheet_handler.go)；
- 决策入口：[同步保存答卷，异步执行评估与报告](../05-决策记录/01-架构决策总表.md#2-同步保存答卷异步执行评估与报告)；完整实现见 [Survey 答卷校验与可靠受理](../02-业务模块/10-survey/31-关键链路-答卷校验与可靠受理.md)。

### 失败窗口

- AnswerSheet 写入或 Outbox Stage 失败：transaction 回滚，必须返回错误，不能返回 `202`；
- Mongo commit 结果不确定：用脱离原请求取消的短时只读回查，只有确认已完成才承认受理；
- commit 成功但 HTTP 响应丢失：客户端复用相同 `idempotency_key` 应读回同一 AnswerSheet；
- 相同幂等键对应不同 fingerprint：返回冲突，不得静默覆盖旧答卷；
- MQ 不可用或发布后标记前崩溃：Outbox 保证事件可继续投递，但可能重复发布，消费者必须幂等。

### 验证

- 防回流架构测试：[`internal/collection-server/application/answersheet/reliable_submission_architecture_test.go`](../../internal/collection-server/application/answersheet/reliable_submission_architecture_test.go)；
- 事务/故障契约：[`internal/apiserver/infra/mongo/answersheet/durable_submit_integration_test.go`](../../internal/apiserver/infra/mongo/answersheet/durable_submit_integration_test.go)，需要 Mongo Replica Set；
- Outbox 保证边界：[Outbox 可靠出站链路](../03-基础设施/event/30-Outbox可靠出站链路.md)；
- 容量实证：[当前 QPS 容量档位](../04-接口与运维/10-QPS容量档位与资源配置建议.md)包含可靠提交，但容量通过不等于所有故障注入已在生产完成。

### 仍存边界

- 原子性只覆盖同一 MongoDB 内的 AnswerSheet 与 Mongo Outbox，不是跨 Mongo/MySQL 分布式事务；
- `202` 不承诺 Assessment、Outcome 或 Report 已完成，前端仍需 readiness/报告状态查询；
- Outbox 提供 at-least-once 可恢复投递，不提供 exactly-once；
- 高峰提交量如果远高于当前目标，是否引入持久 SubmissionCommand 需要新证据。

## 6. 案例卡三：Evaluation / Interpretation 为什么分离

### 问题

如果评估执行、结果事实、展示文案和报告生命周期放在同一个模型里，模板或文案变化就可能改写历史评估语义，报告失败也会被误判为评估失败。

### 约束

- 多种计算机制需要统一结构，但不能把稳定 code、得分和风险层级与可变中文文案混为一体；
- Outcome 必须能追溯到 Assessment、EvaluationRun、模型版本、运行时身份和输入快照；
- 报告生成的失败与重试节奏和 Evaluation 不同；
- Evaluation 事实主要在 MySQL，Interpretation 报告聚合主要在 MongoDB，不存在覆盖两库的单一事务；
- 历史报告必须解释当时 Outcome 和冻结 ReportInput，不能重读最新模型后重算。

### 备选方案

1. Evaluation 计算完同步生成报告：链路直观，但放大成功事务和重试粒度；
2. Interpretation 在需要时重跑 Evaluation：省去 Outcome 事实层，但无法保证历史结果稳定；
3. Evaluation 提交不可变 Outcome 和 `evaluation.outcome.committed` Outbox，Interpretation 通过只读 fact port 消费并独立管理报告生命周期。

### 决策

当前选择第 3 种。Evaluation 回答“结构化结果事实是什么”；Interpretation 回答“如何将这份已成立事实变成可读、可查询、可重试的报告”。报告失败不回滚或否定已成功的 Evaluation。

### 代码链

```text
Evaluation execute
  -> Outcome Committer: Outcome + Assessment evaluated + Run succeeded + Outbox
  -> evaluation.outcome.committed -> qs-worker -> InterpretationAutomation
  -> immutable Outcome + frozen ReportInput -> Starter / Registry / Builder
  -> InterpretationCommitter: Artifact + Catalog + Run + Generation + Outbox
```

- Evaluation 编排：[`internal/apiserver/application/evaluation/execute/service.go`](../../internal/apiserver/application/evaluation/execute/service.go)；
- Outcome 提交：[`internal/apiserver/application/evaluation/outcome/commit/committer.go`](../../internal/apiserver/application/evaluation/outcome/commit/committer.go)；
- Worker 转发：[`internal/worker/handlers/assessment_evaluated_handler.go`](../../internal/worker/handlers/assessment_evaluated_handler.go)；
- Interpretation：[`internal/apiserver/application/interpretation/automation/service.go`](../../internal/apiserver/application/interpretation/automation/service.go)与 [`internal/apiserver/application/interpretation/automation/execution/committer.go`](../../internal/apiserver/application/interpretation/automation/execution/committer.go)；
- 真源：[Outcome 事实与解释边界](../02-业务模块/30-evaluation/22-核心设计-Outcome事实与解释边界.md)与[从 Outcome 到 InterpretReport](../02-业务模块/40-interpretation/30-关键链路-从Outcome到InterpretReport.md)。

### 失败窗口

- Evaluator 返回成功，但 Outcome/Assessment/Run/Outbox 事务失败：只是内存 Execution，不能宣布 Evaluation 已完成；
- Outcome 已提交，Interpretation Builder 失败：持久化 Interpretation 失败与重试事实，Assessment 仍保持 evaluated；
- 重复 `evaluation.outcome.committed`：Starter 依据 Generation/Run/租约收敛，不无条件生成重复报告；
- 报告 Mongo commit 失败：不发布未持久化的伪成功；未持久的不确定错误由 NACK/租约恢复兜底。

### 验证

- 事实与事务约束：Outcome Committer 与 Interpretation Committer 及其测试；
- 模块边界：[`internal/apiserver/application/interpretation/architecture_test.go`](../../internal/apiserver/application/interpretation/architecture_test.go)和 `internal/pkg/contract`；
- 事件契约：`configs/events.yaml` 中的 Outcome 提交与 Interpretation 终态事件；
- 未给出生产故障注入记录时，不宣称所有跨存储故障都已验收。

### 仍存边界

- Outcome schema、模型版本和报告模板版本是三个独立维度，当前 ReportInput 仍缺少独立版本标识；
- 模块分离不代表跨 MySQL/Mongo 具备原子事务，跨库收敛依赖 Outbox、幂等、租约和审计；
- Outcome 的风险等级或类型是模型规则的结构化结果，不应扩大成医学诊断。

## 7. 案例卡四：110 QPS 通过、120 QPS 失败后如何做容量判断

### 问题

同一混合流量下，110 QPS 阶段通过，120 QPS 阶段的 HTTP 与业务成功率仍为 100%，但出现 Dropped iterations、提交 P95 越界和 CPU 饱和。容量结论应看“最终有没有成功”，还是看系统能否在约定的吞吐、时延、正确性和恢复门内持续完成？

### 约束

- QPS 是 K6 business iteration 到达率，不等于 HTTP RPS，也不等于同时在线用户数；
- 必须在同一代码/配置族、硬件拓扑和流量配比下比较，否则两个档位不可直接归因；
- 验收要同时覆盖目标到达率、Dropped、关键 P95/P99、成功/错误/超时、最终完成、Outbox/MQ 恢复、流量隔离和进程连续性；
- 当前前台参照单元是 serverA 4C/8G，Nginx + apiserver ×1 + collection ×2 共享物理 CPU；
- 容量证据只对当时 SHA、配置、数据、硬件和时间窗有效。

### 备选方案

1. 只看成功率，将 120 QPS 记为通过：会忽略到达率和用户时延已经失约；
2. 把 110 QPS PASS 直接当作长期运行承诺：会忽略该档 CPU 已很高，没有留出流量波动和故障余量；
3. 将 110 记为已验证通过边界、120 记为保护上限，向下留余量把 100 QPS 作为当前稳态运行建议。

### 决策

当前选择第 3 种。容量判断不是找“系统还没完全挂掉”的最大数字，而是找同时满足吞吐、时延、正确性、可观测性和恢复条件的最高已验证档，再为生产稳态留出余量。

### 代码链

```text
make perf-run PLAN=ceiling-120
  -> capacity_110 -> bounded recovery -> capacity_120
  -> generated mixed profile -> K6 scenarios
  -> readyz / metrics / Outbox / NSQ / process evidence
  -> per-phase verdict -> capacity conclusion
```

- 计划编排：[`scripts/perf/perfctl/plan.go`](../../scripts/perf/perfctl/plan.go)和 [`scripts/perf/perfctl/runner.go`](../../scripts/perf/perfctl/runner.go)；
- 流量契约：[`scripts/perf/qs-perf.config.example.json`](../../scripts/perf/qs-perf.config.example.json)与 [`scripts/perf/k6/mixed.js`](../../scripts/perf/k6/mixed.js)；
- 执行 SOP：[300QPS 混合场景压测 SOP](../04-接口与运维/11-300QPS混合场景压测SOP.md)；

### 失败窗口

## 8. 案例卡五：Mongo 一致性审计如何发现漂移但不越权修复

### 问题

MongoDB 没有跨集合外键，局部 transaction 与唯一索引不会自动发现旧脚本、历史物理删除、人工改库或早期无事务写入留下的跨集合矛盾。但审计进程如果同时具有 repair 能力，又会把“发现异常”与“获授权改写生产数据”混为一件事。

### 约束

- 要覆盖 AnswerSheet/Outbox、Interpretation Generation/Run/Artifact/Outbox 和 ModelCatalog 发布/runtime 三类不变式；
- 生产数据不适合每次无界全扫，需要稳定 cursor、冻结 upper bound、batch size 和 timeout；
- apiserver 多实例下只能有一个调度者推进周期进度，并防止并发覆盖 checkpoint；
- finding 可能来自历史保留或人工操作，不能只根据类型自动删除、回填或重放；
- scheduler 对 Mongo 业务文档只读，但会写 MySQL checkpoint 并续租 Redis leader lock；one-off 才不启动 checkpoint/租约。

### 备选方案

1. 扫描到 drift 立即自动 repair：能快速归零，但缺少原因、owner、影响范围和维护授权；
2. 只保留人工 one-off 全量扫描：权限最小，但缺少持续进度、周期发现和多实例互斥；
3. 共用七阶段只读 Scanner：one-off 用于首次/专项证据，scheduler 用 checkpoint/CAS 和 leader lock 有界推进，两者都不暴露 repair port。

### 决策

当前实现第 3 种，但生产 scheduler 默认关闭。七阶段依次为 `answersheet_outbox`、`outbox_answersheet`、`generation_run`、`generated_terminal`、`retry_outbox`、`model_release`、`published_model_runtime`。Scanner 只能 `UpperBound` 和 `ScanBatch`；任何 delete/backfill/repair 都必须进入独立维护方案和授权流程。

### 代码链

```text
config/options -> runtime bootstrap -> Runner + Redis leader lease
  -> RunAuditBatch -> read-only Mongo Scanner
  -> MySQL CheckpointStore.Save(expectedRevision, next) -> metrics/findings

one-off CLI -> same bounded Scanner -> report + exit code
  -> no scheduler checkpoint, no automatic repair
```

- 应用编排：[`internal/apiserver/application/mongoconsistency/audit.go`](../../internal/apiserver/application/mongoconsistency/audit.go)；
- Mongo Scanner：[`internal/apiserver/infra/mongo/mongoconsistency/scanner.go`](../../internal/apiserver/infra/mongo/mongoconsistency/scanner.go)；
- scheduler：[`internal/apiserver/runtime/scheduler/mongo_consistency_audit.go`](../../internal/apiserver/runtime/scheduler/mongo_consistency_audit.go)；
- MySQL checkpoint：[`internal/apiserver/infra/mysql/mongoconsistency/checkpoint_repository.go`](../../internal/apiserver/infra/mysql/mongoconsistency/checkpoint_repository.go)；
- one-off：[`scripts/oneoff/mongo_consistency_audit/main.go`](../../scripts/oneoff/mongo_consistency_audit/main.go)；
- 生产配置：[`configs/apiserver.prod.yaml`](../../configs/apiserver.prod.yaml)；
- 运维真源：[调度任务](../04-接口与运维/07-调度任务.md)与[健康检查与观测](../04-接口与运维/08-健康检查与观测.md)。

### 失败窗口

- Redis lock manager 不可用：runner fail-closed，不降级成多实例无锁扫描；拿不到 lease 的 tick 只跳过；
- 执行者竞争：`Save(expectedRevision, next)` 未精确更新一行时返回 checkpoint CAS conflict，不覆盖对方进度；
- batch 超时或查询失败：保留旧 checkpoint，不把局部成功当作完整七阶段成功；
- 发现 high drift：记录 kind/count/有界 sample，保持 scheduler 关闭，不通过删 Outbox、伪造 AnswerSheet 或降低 severity 让指标归零。

### 验证

- 代码约束：`Scanner` 只有 `UpperBound`/`ScanBatch`，`CheckpointStore` 只有 `Load`/`Save`，指标覆盖 enabled、ready、last success、drift、error、CAS conflict、batch 和 scanned total；
- 生产时点证据：2026-08-16 01:13:35 CST 的 one-off 扫描 347,494 个 anchor，耗时 25.43 秒，退出码 2；
- 唯一 finding 为 `outbox_missing_answersheet=269`，其余为 0；这 269 条历史孤立 Outbox 没有被删除或自动修复；
- `configs/apiserver.prod.yaml` 当前仍是 `mongo_consistency_audit.enable: false`，one-off 输出不是 scheduler `last_success` 指标证据。

### 仍存边界

- 当前存在 269 条未处置 high drift，因此不能说“生产定期审计已启用”或“生产一致性已清零”；
- 启用前必须满足 SHA 对齐、migration/索引完成、七阶段无未处置 high drift、finding 有 owner/决定/复验、lock/backpressure/指标/告警已验证、容量/回退已评审和独立生产配置批准；
- 只读审计只证明某个扫描上界内的时点结果，不证明之后没有新漂移；
- 任何 repair/delete/backfill 都需要单独可审计的维护方案，本链路故意没有该权限。
