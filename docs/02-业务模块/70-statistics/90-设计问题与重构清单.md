# Statistics 设计问题与后续优化清单

> 历史验收判定（2026-08-06）：当时的 V1 退役、内部正名、调用方切换、migration、冷启动/运行闭环、首次生产 publish、Task schedule revision 治理和六条陈旧 running ledger 结算已关闭。
> 该结论没有针对当前 checkout 重跑，也不覆盖本轮新识别的 `ST-010` inactive clinician 授权缺口；当前版本、CI、部署和生产证据以[当前版本定档验收台账](../../00-总览/09-当前版本定档验收台账.md)为准。

## 1. 使用原则

这份清单不是愿望池。一个条目只有同时满足以下条件才进入实施：

1. 问题可以由代码、数据、执行计划或故障演练证明；
2. 对业务正确性、可恢复性、容量或维护成本有明确影响；
3. 已经确定验收方式；
4. 不以重新引入 V1 双轨、实时 Projector 或持久 Checkpoint 为解决方案。

当前优先级：

| 优先级 | 含义 |
| --- | --- |
| P0 | 当初上线或宣布重构完成前必须关闭；历史对应条目均已关闭 |
| P1 | 当前架构的重要可靠性与容量保护 |
| P2 | 有明确触发条件的后续优化 |

优先级是条目固有风险，不随关闭而删除，也不与 `FINAL-P*` 互换。

## 3. ST-001：Migration 完整演练

> 当前结果：已关闭。生产只读盘点确认 MySQL migration `67/0`、Mongo migration `21/false`，canonical Statistics schema/index clean；物理遗留对象退役后再次独立复核通过。

### 问题

Migration 56 删除 V1 表并完成快照正名，Migration 57 补齐 canonical Collector 来源索引。即使业务历史数据已经清空，也必须证明它们不误删三类 Fact、五类 Result、SyncRun 或任何业务表。

### 必须验证的三条路径

1. 从 migration 55 前向执行 56、57；
2. 从空库执行全部 migration；
3. 依次执行 57、56 down，恢复上一版镜像所需的空 V1 Schema。

前两条路径最终得到的 canonical Statistics Schema 必须一致。Down 只验证结构回退能力，不声明恢复旧统计数据。

### 验收

- 最终只存在三张 Fact、五张 Result 和 SyncRun；
- `statistics_org_snapshot` 的列、索引和约束一致；
- 三类事件扫描索引存在；
- 业务表和 canonical Statistics 数据不被删除；
- migration contract test 与真实 MySQL 结果一致。

## 4. ST-002：冷启动端到端验收

> 当前结果：已关闭当前版本门禁。认证 integration contract、当前 runtime 闭环 E2E、幂等 publish、Redis 故障边界和部署后服务巡检均已通过。后续新增存储或来源时仍需复用本节矩阵。

一次性环境至少包含：

- MySQL；
- 单节点 MongoDB Replica Set；
- Redis；
- qs-apiserver 与 qs-worker 所需最小运行组件。

建立最小 Actor、Entry、AnswerSheet、Assessment、Outcome、InterpretReport、PlanEnrollment 和 Task 后，执行一次 publish，逐层核对：

```text
权威数据
  → Access / Assessment / Plan Fact
  → 五类 Result
  → Read Service
  → /api/v2/statistics
```

然后重跑相同窗口，Fact 和 Result 行数不得增长，聚合值不得漂移。

## 5. ST-003：首次生产发布

> 当前结果：已关闭。当前生产已有成功 SyncRun、对齐 Snapshot/Generation 和明确 freshness；849,692 条 assessment fact 已冻结，v2 Redis key 已出现。
> 六条无活动进程/租约的陈旧 running ledger 已精确结算为 failed，未删除 Fact。

历史数据清空不等于不需要初始化。没有成功的 SyncRun 时，Read Service 必须返回 `statistics_not_ready`；因此发布后需要为每个启用机构执行一次 publish。

- `statistics_org_snapshot`；
- `as_of_date/snapshot_at`；
- 首个机构级 Cache Generation；
- 可审计的成功 SyncRun。

验收时记录：

- 机构；
- Run ID；
- 窗口；
- Collector 计数；
- Projection 结果计数；
- Generation；
- API freshness。

## 6. ST-004：Collector 数据库级验证

每个生命周期来源已经拆成单独扫描，后续验收必须证明：

- 使用 `(event_time,id)` 跨页时无遗漏、无重复；
- 恰好落在窗口边界的数据只属于一个窗口；
- 迟到数据能被 repair 重新采集；
- 相同 FactKey、相同核心字段是幂等成功；
- 相同 FactKey、不同核心字段使整个 Run 失败；
- 来源查询命中 `(org_id, deleted_at, event_time, id)` 索引；
- 单页 500 时不会退化为多时间列 OR 全表扫描。

新来源接入时必须复用这组合同测试。

## 7. ST-005：Organization Snapshot 不变量

Organization Snapshot 表达“截至最近发布水位，机构当前资源状态与累计业务量”，不是历史资源趋势。

必须守卫：

- 当前 clinician、entry、testee 等资源数来自当前 MySQL 读模型；
- 累计测评量来自 Fact；
- 结果事务内不扫描 MongoDB；
- 删除或转移资源不会反写历史 Fact 归属；
- Snapshot 不伪装成任意历史日期的资源快照；
- 若未来需要资源历史趋势，应新增明确的维度历史或 Resource Daily，而不是回填当前状态。

## 8. ST-006：Plan Fulfillment 容量边界

第一版按机构全量重建 Plan Fulfillment，这是符合当前规模的奥卡姆选择。只有出现以下任一证据才启动增量化设计：

- 单机构重建耗时逼近夜间批次 SLA；
- 锁持有时间影响其他机构运行；
- Enrollment/Task 数据量使全量查询稳定超过容量预算；
- 故障恢复窗口无法接受。

届时优先按受影响 Enrollment 重建，不引入通用 Metric DSL 或分布式计算平台。

## 9. ST-007：缓存故障闭环

需要通过故障注入验证四个停点：

| 故障点 | 期望结果 |
| --- | --- |
| Collector 失败 | Run failed，已提交 Fact 可幂等重采 |
| Projection 失败 | Result 事务整体回滚 |
| 结果提交后进程退出 | Run 保持 `data_committed` |
| Generation/预热失败 | 不重复计算，使用 `resume-cache` 闭环 |

查询侧还需验证：

- Redis 可用时命中当前 Generation；
- Redis 不可用时优先返回带 stale 语义的 L1；
- 没有 stale 时由 LoadGuard 限制 MySQL 回源；
- 超限返回 503，不让故障流量直接打垮数据库。

## 10. ST-008：保留与归档

当前不提前删除 Fact 或 SyncRun。连续运行三个月后，根据以下证据制定策略：

- 每日 Fact 增长量；
- SyncRun 记录增长量；
- repair 最大回看窗口；
- 审计和问题定位实际使用周期；
- 索引体积和查询延迟。

归档策略不得破坏指标重建所需的事实窗口，也不得把 Statistics 变成业务事实的唯一保存者。

## 11. ST-009：Task 调度轮次生产验收

Plan Resume 沿用 Task ID 和 Enrollment，因此 Task 用 `schedule_revision` 区分同一身份的多次调度。
Statistics 以 `task_schedule_defined` 和同 revision 的 `task_schedule_terminal` 计算最新 planned/due cohort，旧生命周期 Fact 只保留 Activity 语义。

该生产数据治理已经完成：286,552 个 Task 均有 revisioned schedule fact，legacy fulfillment fallback 为 0；
源数据 audit/apply/verify、Statistics repair/validate/publish 与 cohort 对账均已闭环。未来新增恢复语义时继续沿用同一 revision 契约，不再设计旁路。

## 13. ST-010：inactive clinician 的 self overview 授权

`/api/v2/statistics/clinicians/me/overview` 的 handler 以“current operator is not an active clinician”作为空结果语义，
但其 `ReadStore.ListClinicians` 查询只过滤机构、删除状态和 operator user，没有过滤 `c.is_active=1`。相邻的 `CurrentClinicianID` 查询明确包含该条件，
说明 self overview 的实现与自身授权声明不一致。当前风险限于已认证用户读取同机构内自己的停用 clinician overview，不是任意 clinician ID 的跨用户读取，
因此 Statistics security 维度记为 `conditional`，但不能签署为完全闭环。

关闭门槛：self overview 每次请求必须先通过 `CurrentClinicianID` 或等价的非缓存授权路径解析 active clinician identity，再以 clinicianID 查询统计；
仅给 `ListClinicians` SQL 追加 `c.is_active=1` 不够，因为 operatorUserID 查询可能先命中 Statistics query cache，而 clinician 停用不会天然推进 Statistics generation。
SQL 的 COUNT/SELECT active 谓词和 Actor 状态变更后的缓存失效只能作为纵深防御。补 active/inactive/deleted clinician、active/deleted operator、跨
org、停用前已预热缓存的负向测试，并守卫错误语义仍为 `PermissionDenied`。

## 15. ST-011：作答开始记录、开展门店与客户端兼容

> 状态：规划改造。业务规则已确认，以下是本轮详细设计；接口、类型、存储与迁移均未实现。
> 本节是开始记录与提交传递的 canonical 设计，Survey 和 Statistics 阅读入口回链本节。它不改变上述历史验收，也不表示新统计已经上线。

### 15.1 目标、口径与设计依据

实际开始作答时确定开展门店，此后转店不改写；预生成或开放计划任务不确定开展门店。
提交量按正式受理时间统计；完成量按同一 Assessment 首次规范评估成功时间统计。同次重试、重复消费、报告重建不重复计量。
当前服务人数和待办采用当前受试者归属；历史开展量采用开始记录的冻结归属。两者分别命名和查询。

当前源码依据：

- [AnswerSheet 来源快照](../../../internal/apiserver/domain/survey/answersheet/attribution.go) 在受理时冻结来源、医生、入口和计划信息，没有开始门店。
- [答卷事件处理](../../../internal/worker/handlers/answersheet_handler.go) 在提交后确保创建 Assessment，因此 Assessment 创建不是开始作答。
- [OpenTask](../../../internal/apiserver/application/plan/task_management_service.go) 生成入口、开放任务，不表示用户开始。
- [规范结果仓储](../../../internal/apiserver/infra/mysql/evaluation/outcome_repository.go) 按 Assessment 唯一保存 Outcome；[Collector](../../../internal/apiserver/infra/mysql/statistics/collectors.go) 按结果时间生成去重事实。
- [当前范围过滤](../../../internal/apiserver/infra/mysql/statistics/store_scope.go) 根据当前 Testee 门店查询事实，不是历史开展归属。

“开始”定义为：选定受试者和最终内容版本后，用户确认开始，服务端完成授权、内容/来源校验并持久化成功。
客户端进入答题状态应晚于该成功响应。离线点击、预加载题版、订阅提醒、打开二维码、预生成任务均不单独算开始。
人格自动开始和其他跳过介绍页的路径，也必须在进入可答题状态之前经过同一个用例。

### 15.2 领域对象与模块所有权

规划在 Survey 增加 AnsweringStart（作答开始记录）；它属于作答事实，不属于 IAM Session，也不是预先创建的 Assessment 或答卷草稿。
无模型绑定的独立问卷同样可以有开始记录与提交事实，但不会因此生成 Assessment 或贡献评估成功数。

| 归属 | 负责内容 |
| --- | --- |
| Survey domain | 开始记录、固定内容引用、开始上下文值对象；创建后不可变 |
| Survey application | 开始幂等、归属快照、受理引用校验；通过端口依赖外部事实 |
| Actor | 受试者当前公司/门店及转店事实；提供归属锁定读取端口 |
| Plan / ModelCatalog | 任务来源资格、内容版本与现有模型准入校验；不拥有开始记录 |
| Journey / composition root | 跨模块接入、端口适配和组合，避免 HTTP 层协调完整流程 |
| MySQL infra | 开始记录、幂等唯一约束、归属锁与短事务实现 |
| Mongo infra | AnswerSheet 的 start 引用、冻结上下文、唯一约束及原可靠受理事务 |
| Evaluation / Statistics | 消费冻结事实，分别产出规范结果和统计读模型，不重新推断门店 |

AnsweringStart 规划字段：

| 字段 | 语义 |
| --- | --- |
| ID | 服务端生成的字符串化 ID；识别一轮作答意图，不是访问凭证 |
| OrgID、TesteeID、StartedByUserID | 可信公司、受试者与开始者 IAM UserID；开始者可为参与者/监护人，不要求 Operator |
| QuestionnaireRef | 精确 code/version，不保存题目答案 |
| ModelRef（可空） | 开始时选择的模型引用；不替代提交时现有准入规则，模型变更导致冲突时重新开始 |
| OriginRef | 已校验的来源类型与引用：入口、计划任务、医生直接或自服务 |
| StartedAt | 服务端 UTC 时间，发生在归属锁获取并复核通过后 |
| ConductingStoreID（可空） | 开始时的服务门店；后续不允许编辑 |
| AttributionState | captured 或 unassigned_at_start；后者始终伴随空门店 |
| OwnershipVersion | 当时受试者归属版本，用于审计开始与转店顺序，不用于提交时强制相等 |
| RequestKey、RequestHash、ContractVersion | 开始请求幂等及规范编码版本 |

新建 MySQL 表的建议名称为 answering_start。唯一键为公司、开始者、RequestKey；ID 为主键。
按公司/受试者/StartedAt 建索引；门店是否需要额外索引以实际查询为准，统计主查询使用事实/投影索引。
记录没有可修改的 active、completed 状态，也不存“是否已提交”的跨库缓存标记。开始记录是否已有答卷由答卷唯一绑定事实查询。
第一版不自动到期或删除未提交记录；这些记录不计提交量、成功量或服务人数。保留策略后续按增长与隐私要求单独评估。

### 15.3 开始接口与响应

规划 Collection REST：POST /api/v1/answering-starts。此路径尚未注册。
使用现有认证、响应包装和请求标识；ID 一律为字符串。第一次创建返回 201，幂等重放返回 200，业务字段相同。

```json
{
  "request_key": "client-generated-key-for-this-answering-intent",
  "testee_id": "1001",
  "questionnaire_code": "questionnaire-code",
  "questionnaire_version": "1",
  "model_ref": null,
  "origin_ref": { "type": "self_service", "id": "" }
}
```

响应 data 的规划示例：

```json
{
  "answering_start_id": "2001",
  "started_at": "2026-09-12T03:00:00Z",
  "questionnaire_code": "questionnaire-code",
  "questionnaire_version": "1",
  "attribution_state": "captured"
}
```

不要求客户端提供 OrgID、StoreID、开始者或 StartedAt；这些字段若作为开始写入字段提交，应拒绝，不能作为可信来源。
面向参与者不必返回内部门店 ID。服务端在受试者身份及关系校验通过后解析公司，沿现有来源校验规则核对任务/入口/内容一致性。
普通用户持有 start ID 不代表授权；每次读取恢复或提交仍校验当前身份与业务资格。

增加对应的内部 gRPC 开始方法，由 Collection 经受托身份调用 QS 的共享用例；不得只把 mTLS 服务身份当作最终用户。
方法和字段编号在实现时按现有 proto 的可用编号追加，不能复用历史编号。REST 与其他客户端调用共用同一应用入口。
本轮无需改 IAM 公共协议；QS 自有 REST/gRPC、生成契约及调用方需要同步更新。

### 15.4 开始事务、重放与转店并发

1. 完成基本格式、可信身份及受试者访问校验；加载最终内容/来源资格。
2. 进入 QS MySQL 短事务，按 Actor 既定转店锁顺序锁定受试者归属事实，重新检查公司与可用业务状态。
3. 查询该开始者的 RequestKey。已存在则比较版本化 RequestHash；同输入返回原记录，异输入返回 409。
4. 对首次请求，在锁内读取 StoreID 与归属版本，取服务端开始时间，插入不可变 AnsweringStart；提交成功后才返回。
5. 唯一键竞争的失败方回读已提交记录，执行相同的 hash 校验，不能生成第二条开始事实。

开始幂等键只标识一轮作答；不按“受试者＋问卷”永远合并。RequestHash 含公司、开始者、受试者、精确内容/模型和来源，
不含动态当前门店或当前时间，否则转店后重试无法返回原开始记录。请求失败结果不明时复用同一 RequestKey。

转店与开始共享同一归属行锁：开始先提交则冻结旧店，转店先提交则冻结新店。
同一开始记录重放后仍检查访问者资格，但不以新的当前门店重新生成快照；不能因此将旧门店复活成明细授权。
内容或入口资格由现有端口检查，不在持有 MySQL 行锁时发起新的外部 IAM/网络调用；提交仍复核当时的业务资格。

### 15.5 客户端作答意图与恢复

选定最终受试者、题版与来源后产生 RequestKey；成功响应的 start ID 与既有答卷提交幂等键一起保存为本轮本地上下文。
恢复同一轮作答时沿用两个键。更换受试者、内容版本或来源，或明确“重新做一次”，生成新的开始键与提交键。
关闭页面不在服务端生成完成事件，也不增加统计计数。

每次 HTTP 尝试仍使用独立 request ID。开始失败时重试原键；新客户端不得静默改走旧提交来伪造一次已开始作答。
网络不可用时提示重试，未拿到持久受理结果不进入新的答题流程；已经取得记录的作答恢复可以沿用该记录。
若本地上下文丢失，不根据“最后一条开始记录”猜测恢复。只能恢复能明确匹配当前意图的记录，或让用户明确重新开始。
第一版不建设跨设备答卷草稿同步。

### 15.6 答卷传递与不可变上下文

在现有 POST /api/v1/answersheets 增加可选 answering_start_id；Collection DTO、写端口、QS gRPC DTO 与共享提交服务逐层传递。
新客户端必须携带，旧客户端允许省略。提供了错误标识时不能降级为旧路径。

提交服务校验：开始记录存在，StartedByUserID 与提交者一致，公司/受试者/精确题版/模型和来源匹配；仍通过当前自服务关系、任务与入口资格检查。
归属版本变化本身不构成拒绝理由：A 店开始后转到 B 店，若现有业务规则仍允许提交，则保持 A 店开展归属并按 B 店当前范围读取明细。
若旧二维码已因医生调店失效，start ID 不得绕过原有提交准入限制。

AnswerSheet 新增独立 StartContext，不覆盖现有 AttributionSnapshot 的“提交时来源”含义：

- answering_start_id、started_at、conducting_store_id、attribution_state、ownership_version、contract_version；
- 内容/身份/来源绑定保存在开始记录与现有提交上下文中，由服务端核对；客户端不能自行传冻结值；
- StartContext 随答卷持久化，其后不根据当前 Actor 数据修订；规范编码版本明确区分旧答卷。

提交 admission 仍由现有规则负责。不能把开始时选定模型当作绕过已撤回内容或旧任务资格的许可证；若最终版本不同，返回冲突而非偷偷修改本轮作答。

### 15.7 一次开始只绑定一份答卷

在 Mongo AnswerSheet 上新增针对有效 answering_start_id 的部分唯一索引；只覆盖真实新 start 引用，旧答卷缺失/null/空字段不参与唯一约束。
实施前以实际 Mongo 版本验证 partial filter，不能用包含所有 null 值的普通 unique 索引阻断旧数据。

答卷继续使用现有 Mongo 事务完成 AnswerSheet、提交幂等事实与 Outbox 的原子受理，不增加 MySQL“已提交”标记或伪装跨库事务。

| 场景 | 结果 |
| --- | --- |
| 同 start、同提交键、同规范内容重试 | 返回原可靠受理结果，不再产生答卷或事件 |
| 同提交键修改 start 或答案 | 409，保留原记录 |
| 同 start 使用另一个提交键 | 409，提示恢复原提交上下文；不能第二次绑定 |
| start 属于其他人/公司/受试者 | 按现有不可见或权限错误拒绝，不泄露原记录 |
| Mongo 持久化失败 | 无已受理答卷；原 start 保留，允许同键重试 |
| 持久化成功但响应丢失 | 同键查回原结果，不把网络失败当未提交 |

旧提交哈希算法保持原样；有 start 的新提交使用显式新编码版本，将 start 引用纳入内容 hash。
已有历史幂等记录不重新计算。遇到并发唯一冲突，通过原幂等查询判定重放或冲突，不把数据库异常一律报告 500。

### 15.8 异步传播与缺失处理

答卷的 StartContext 是跨库传播的冻结业务事实，MySQL 开始记录提供可追溯原始依据。受理后发布原有答卷事件，追加可选的 start 上下文字段。
Worker/Journey 优先从已持久化答卷获得并验证上下文；队列中的字段仅为传输，不接受外部消息直接授予门店事实。
测评创建时复制开展门店和开始时间，重复 Ensure 对既有记录校验一致，不按新门店覆盖。

规范 Outcome 沿用现有 Assessment 唯一约束和首次成功时间。提交与成功统计分别从其可靠事实采集，通过 start/answerSheet/assessment 关联到开展归属。
独立问卷只贡献提交量，不贡献完成测评量；统计页面需要标明这一分母差异。

有效 start 引用若对应的数据损坏/缺失，应停下该条异步处理、报警并按原受理事实修复，不能降级为 unknown 后继续计数。
旧事件缺少新增字段时，从答卷读取；旧答卷本身也缺少时按历史未知处理，不借当前门店推断。

### 15.9 旧客户端与历史数据兼容矩阵

| 输入/历史状态 | 写入与读取行为 | 统计归属 |
| --- | --- | --- |
| 新客户端，合法 start | 完整校验，保存 StartContext | captured 或 unassigned_at_start |
| 新请求携带不存在、跨人或格式非法的 start | 明确拒绝；无答卷/事件写入 | 不计数 |
| 旧客户端省略/null/空 start | 原业务校验与可靠受理照常执行 | legacy_start_not_captured，门店为空 |
| 原历史答卷/事件缺少 StartContext | 兼容读取，不修改原记录或幂等 hash | legacy_start_not_captured |
| 开始时本身未配置门店 | 新记录真实保存空值；以后配置不反填 | unassigned_at_start |
| 有 start 但服务端关联损坏 | 错误与修复队列，不按旧请求处理 | 暂不发布该不完整事实 |

unknown 在展示层汇总两类未知原因，在审计中区分。后续收集到的医生当前门店、受试者当前门店、任务开放门店都不能自动作为开始时证据。
历史补齐另做只读预演，只有能证明时间与主体关联的历史材料才进入审核；本轮默认不回填，不宣称旧数据恢复率。
总部获得有权查看的公司未知数量；门店与指定多店范围均不包含未知桶。不要改变现有 all_stores 明细查询对未归属受试者的拒绝规则。

### 15.10 统计与授权衔接

保留两种明确口径：current_service（当前服务对象/待办）与 conducting_workload（历史开展提交/首次成功）。规划名字不是现有 API 枚举。
新查询先用当前动作和 Scope 解析允许门店，再按冻结开展门店聚合；用户请求门店须为授权子集，越界返回拒绝，不静默返回公司全集。
所有明细下钻仍走当前受试者归属与专业结果动作校验，历史计数不能成为第二套明细权限。

首版建议独立的运营统计动作，而非给门店账号 OrgAdmin 或直接复用包含专业结果的综合 DTO。
动作目录及授予运营员/计划管理员等角色的最小清单应在统计 API 实施批次明确并审核；本设计不执行任何赋权，不改 Assignment Scope。
历史姓名清单、风险分布与小样本专业聚合不纳入纯运营计数响应。

提交时间与首次成功时间按服务端事实、上海时区自然月的左闭右开区间计算。不能使用报告生成时间或本轮运行时间。
事实新增维度涉及 core_hash/FactKey：旧历史键与原清单不改写；新增事实编码与新增投影版本先 validate/rebuild，再按现有发布机制切换。
缓存必须区分公司、口径、门店集合、时间和发布版本，查询前执行权限检查；开展查询不能命中旧公司总览缓存。
总部汇总需与同口径各店加未知桶对账；零业务门店的行展示与停用门店历史量保留规则在报表 DTO 中明确。

### 15.11 故障、发布与回滚

发布顺序：

1. 先实现新开始表、兼容的 Mongo 字段/部分索引和服务器端可选契约；新库全迁移链与旧库升级都通过。
2. 所有 QS 写入/Worker 实例升级到会保留和校验 StartContext 的版本后，再发布使用 start 的采集端。
3. 新客户端覆盖普通、自服务、计划、入口、人格自动开始等路径，检查新开始采集率与未知原因；旧客户端仍按明确兼容路径工作。
4. 采集与回放验证通过后，发布门店统计读模型和权限/页面；展示开始采集生效时间，避免把旧未知解释成零开展。

不能在仍会丢弃新字段的旧服务实例间开放新写入。无 start 的历史兼容是版本过渡能力，不提供伪造开始归属的配置开关。

| 失败窗口 | 恢复规则 |
| --- | --- |
| 开始成功、客户端断线 | 复用开始键返回同记录 |
| 开始成功、用户未提交 | 保留无答案开始记录，不计业务完成 |
| start 查询失败 | 新请求失败重试，不转成未知 |
| Mongo 答卷成功、Worker 失败 | 原 Outbox/幂等处理恢复；不新建作答意图 |
| 统计采集/发布失败 | 业务答题不依赖统计；维持原已发布代次，显式 freshness/错误 |
| 开始记录已存在后回退客户端 | 后续旧提交可成为未知，既有事实不清空或重写 |

常规回滚保留新表/字段和历史事实，回退到仍可读取、保留 start 的兼容服务版本。
已收集新记录后不能直接回退到忽略字段的旧 Writer/Worker；必要时先关闭新开始入口并向前修复。
统计口径回退不恢复宽松明细权限。物理删除字段与开始数据不属于本轮回滚。

### 15.12 实施验收与设计完成边界

实施验收矩阵：

- 普通、自服务、计划、二维码、人格自动开始均在进入答题前获得同一契约；独立问卷不产生虚假 Assessment。
- A 店开始 → 转 B → 提交 → 首次成功：开展量留 A，B 可读完整历史，A 明细拒绝；转店先于开始则记 B。
- 未配置开始、旧端提交均归未知，后续配店不改历史；非法 start 不降级。
- 开始并发同键同输入只一条、异输入 409；不同作答意图可分别开始；一开始只一答卷。
- 开始受理成功丢响应、Mongo 提交丢响应、Worker 重放、统计重建均不重复计数。
- 同一次失败重试首次成功计一条；报告重建不增加；跨月提交与成功分别归对应月份。
- 监护关系失效、跨人/跨公司、入口失效和任务资格变化不能被旧 start 绕过。
- 真 MySQL 转店竞争、Mongo Replica Set 部分索引/提交事务与故障注入，以及三端契约/界面测试通过。
- 上线前记录旧端比例、新端覆盖、未知原因、同步延迟和汇总对账，部署证据与业务验收分别留存。

本节交付的是开始记录、传递和兼容的详细设计；它不包含新代码、API 开放或数据库迁移。
下一实施批次先锁定端口签名与新旧编码测试，再写领域/持久化和采集端，最后建设统计视图；不得先以当前门店假数据交付图表。
