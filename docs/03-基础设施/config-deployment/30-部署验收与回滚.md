# 部署验收与回滚

## 1. 当前结论

部署完成必须同时绑定源码 SHA、镜像 digest、脱敏有效配置和逐服务探针。单独的 workflow 绿色、容器 running、HTTP 200 或历史巡检都不足以签署当前版本。回滚也不是简单切回旧镜像：旧二进制必须与已经执行的 schema migration、事件契约和有效配置兼容。

## 2. 部署前门禁

1. 当前提交的非缓存测试与文档门禁通过；记录命令、结果和 SHA。
2. 三个镜像由同一目标 SHA 构建，保存 digest 和 build metadata。
3. 部署包包含正确主配置、cache policy、Event Catalog、gRPC ACL、脚本和 env file；Secret 不出现在日志。
4. migration up/down 对完整、contract test 通过；真实 MySQL/Mongo 环境测试结果单列。
5. 目标机证书、目录 owner/mode、外部网络和依赖 endpoint 预检通过。
6. 明确本次服务计划、部署顺序、观察窗口、回滚镜像和数据兼容结论。

## 3. 部署后验收

| 服务 | 最低探针 | 必须追加的语义检查 |
| --- | --- | --- |
| qs-apiserver | `/healthz`、`/readyz`、gRPC health | `/readyz` 当前只代表其实现覆盖的依赖；必须另查 MySQL/Mongo、scheduler/governance 与 ACL 装配 |
| collection-server | `/healthz`、`/readyz`、`/serve-readyz` | 每个副本的镜像、IAM/gRPC 依赖与流量入口都要验证，不能只命中负载均衡一次 |
| qs-worker | 9092 `/healthz`、`/readyz`、`/metrics` | 每个副本的订阅、依赖预检、治理开关和消息结算指标都要验证 |

验收必须记录 effective-config hash 与配置开关，特别是 migration、scheduler、retry governance、ACL、mTLS、profiling、metrics 和修复任务。探针的含义以 Observability 文档为准，不能把 liveness 写成业务全链健康。

## 4. 回滚决策

```text
部署失败
  -> 仅进程/配置问题且 schema 向后兼容：回切旧镜像 + 旧配置
  -> migration 已执行但旧程序兼容：保留 schema，回切程序
  -> migration/数据变更不向后兼容：停止自动回滚，进入受控恢复
  -> one-off 已写业务数据：按该工具的备份/清单/复验方案恢复，不用 down migration 代替
```

应用内 migrator 只在启动时执行 up；仓库没有通用的 `make migrate-down`。down 文件是受控恢复材料，不证明数据可逆。任何 `force`、直接修改 dirty 状态、DROP/DELETE 或 checkpoint 重置都需要独立授权。

## 5. 证据记录

每次真实部署至少写入[基础设施生产证据台账](../../00-总览/10-基础设施生产证据台账.md)：

- `observed_at`、环境和 owner；
- source/deployed SHA、镜像 digest；
- effective config hash 及脱敏摘要；
- 执行命令/workflow run、结果与原始证据引用；
- 探针、关键查询、观察窗口；
- limitations、expires_on、supersedes。

历史证据过期时保留审计轨迹，但不得继续作为当前签署依据。

## 6. 未闭合 gap

- 当前 checkout 尚无对应 CI、部署和生产探针证据。
- 历史部署记录没有完整 effective-config hash，必须标记 limitation。
- 数据库与 MQ 的真实故障恢复演练不能由脚本单测替代。
- apiserver `/readyz` 的覆盖面窄，且实现边界需要在部署验收中补充依赖级检查。
