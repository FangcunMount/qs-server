# Data Access 核心设计决策与替代方案

本文不重复列举 repository。它回答的是：为什么 qs-server 同时使用 MySQL、MongoDB、Redis 和 OSS；为什么事务只在单一数据库内闭合；为什么跨存储流程选择 Outbox、幂等和状态机，而不是把调用顺序当成一致性保证。

文中的“当前实现”以 2026-07-28 checkout 为准；“目标约束”用于评审新代码，不表示相关能力已经全部落地。

## 1. 先建立判断模型

数据访问设计需要同时回答五个问题：

1. **Ownership**：哪一个存储拥有业务事实？
2. **Atomicity**：哪些写入必须一起提交或一起回滚？
3. **Concurrency**：重复请求和并发竞争最终由什么约束裁决？
4. **Freshness**：查询读到的是权威状态、异步投影还是缓存？
5. **Recovery**：跨边界失败后，系统依据什么持久事实继续推进？

如果只回答“用 MySQL 还是 MongoDB”，就还没有完成数据访问设计。

## 2. 决策总览

| 决策 | 当前选择 | 主要替代方案 | 当前选择的核心原因 |
| --- | --- | --- | --- |
| 多存储事实划分 | 按聚合所有权划分 MySQL/Mongo | 全部统一到一种数据库 | 现有领域模型和查询形态已经分化，迁移成本高且不能消除跨模块一致性问题 |
| 事务边界 | 单 MySQL transaction 或单 Mongo transaction | XA/分布式事务、应用层双写 | 本地事务可验证、故障边界清晰；跨存储用持久状态收敛 |
| 依赖方向 | application port + infra adapter | application 直接依赖 GORM/Mongo | 让业务语义、测试和存储实现解耦 |
| 可靠出站 | 与事实同库的 Transactional Outbox | 事务后直接发 MQ、CDC | 当前需要在 application 明确事件契约和发送状态，且不能承受 commit 后进程崩溃丢事件 |
| 并发正确性 | 唯一键、claim/CAS、事务 | Redis 锁、先查后写 | 数据库约束与事实同生存周期，Redis 故障时仍成立 |
| 查询模型 | 权威直读、异步投影、cache decorator 并存 | 所有查询都走聚合 repository | 不同查询的新鲜度、成本和返回形态不同 |
| 依赖保护 | 进程级 backpressure + driver pool | 只调连接池、只做入口限流 | 应用等待预算与数据库连接资源是不同控制量 |
| Schema 演进 | versioned migration + oneoff 修复 | AutoMigrate、手工线上改表 | 可审计、可排序，能显式处理数据修复与回滚边界 |
| 对象存储一致性 | OSS 独立资源，必要时用 pending/ready 补偿 | 假装与 DB 原子提交 | OSS 不参加数据库事务，必须承认并设计失败窗口 |

## 3. 决策一：按事实所有权划分存储，而不是按调用链划分

### 问题

一个业务流程可能同时读取 Mongo 问卷、写 MySQL Assessment、再生成 Mongo 报告。如果按“这条链路用了哪些数据库”定义所有权，会得到多个相互竞争的事实源。

### 当前实现

- MySQL 拥有 Actor、Plan、Evaluation、Statistics 及治理/投递状态等关系型事实。
- MongoDB 拥有 Questionnaire、AnswerSheet、ModelCatalog、Ruleset、Interpretation 等文档聚合。
- Redis 承担 cache、signal、rate limit、lease、ready-index 等可重建或运行时协调能力。
- OSS 保存二进制对象，不拥有业务访问权和发布状态。

Evaluation 读取 Mongo 发布快照，不会因此把 Assessment 的所有权转移给 Mongo；同样，报告对象落在 OSS，也不会使 OSS 成为报告授权事实源。

### 为什么当前选择合理

- 聚合结构和访问模式已经明显分化：复杂关系/claim/checkpoint 适合 MySQL，版本化大文档和报告聚合适合 Mongo。
- 所有权按业务事实而不是技术调用划分，排障时才能回答“最终应以哪一行或哪一份文档为准”。
- 强行统一数据库只能减少驱动种类，不能自动消除跨模块、MQ、OSS 和外部 IAM 的一致性问题。

### 替代方案

1. **全部迁到 MySQL**：运维面更统一，但大文档、版本化快照和既有 Mongo 事务链需要重写。
2. **全部迁到 MongoDB**：聚合写入更自然，但关系约束、复杂治理查询和行级 claim 需要重新设计。
3. **按服务拆独立数据库**：边界更强，但 qs-server 当前不是独立部署的微服务集合，先拆库会把进程内调用变成分布式一致性问题。

选择存储前，先写下“事实 owner”和“失败时以谁为准”；没有这两个答案，不应开始建表或建 collection。

## 4. 决策二：只承诺本地事务，不伪造跨存储原子性

### 当前实现

application 依赖窄 `transaction.Runner`：

- MySQL runner 通过 GORM UnitOfWork，把 transaction `*gorm.DB` 放入 context。
- Mongo runner 使用 `Session.WithTransaction`，显式要求 primary、snapshot read concern 和 majority write concern。
- repository 必须继续使用 callback 收到的 `txCtx`；若改用外层 context，就会悄悄逃出事务。

Mongo standalone 不支持这项跨文档事务语义，因此应失败，而不是降级为若干独立写入。

### 为什么不使用分布式事务

跨 MySQL、Mongo、Redis、MQ、OSS 的统一提交需要所有参与者支持共同协议，并会引入协调者、阻塞、恢复和运维复杂度。当前基础设施与外部依赖不具备这种统一事务能力。

当前方案把承诺缩小为可证明的本地原子性：

```text
本地事实 + 同库 Outbox  ── local commit ──> durable
                                    ↓
                           异步传播 + 幂等收敛
```

这比“先写 Mongo、再写 MySQL、都没报错”更可靠，因为任一进程崩溃点都有持久状态可查。

### 替代方案

- **XA/2PC**：理论原子性强，但当前 Mongo/MQ/OSS 组合不适合，故障恢复与可用性成本高。
- **Saga**：适合多步业务流程；qs-server 实际上已通过状态机、Event、claim 和补偿采用相近思想，但没有建立通用 Saga 编排框架。
- **TCC**：需要每个参与者提供 Try/Confirm/Cancel 语义，业务侵入和资源预留成本高。
- **应用层双写**：实现最简单，可靠性最差；commit 后崩溃会形成不可观察的缺口。

## 5. 决策三：port 表达业务边界，BaseRepository 只是实现复用

### 当前实现

domain/application-facing port 使用业务语言描述保存、查询、claim 和访问约束；infra adapter 才处理 PO/document、GORM/Mongo API、索引和错误翻译。

`mysql.BaseRepository` 与 Mongo `BaseRepository` 复用 CRUD、context 和 backpressure，但它们暴露 `DB()`/`Collection()`，因此是便利工具，不是架构边界。

### 为什么不让 application 直接使用 ORM

- application 会被表结构、driver error 和查询 DSL 污染。
- 单元测试只能构造数据库或大范围 mock ORM，难以表达业务契约。
- transaction context、组织 scope 和错误翻译容易散落。
- 更换查询策略或增加 cache decorator 会影响业务层。

### 代价与边界

port 不是越细越好。为每个 CRUD 建一个接口会产生样板代码；通用 repository 也可能遮蔽复杂 SQL 的成本。合理粒度应围绕业务用例和一致性边界，而不是围绕每张表。

允许 read model 使用专用 SQL/aggregate adapter，但必须明确数据源、新鲜度和组织过滤；它不需要伪装成聚合 repository。

## 6. 决策四：可靠事件与事实同库写入 Outbox

### 当前实现

- AnswerSheet、幂等事实和 `answersheet.submitted` 写入同一 Mongo transaction。
- Assessment 等 Evaluation 事实与对应事件写入同一 MySQL transaction。
- Stager 要求活跃 transaction context；`AfterCommit` 只负责 ready-index/immediate hint，失败不回滚已提交事实。

### 为什么选择 Outbox

直接在事务提交后发布 MQ 有一个无法靠重试完全消除的窗口：数据库已提交，但进程在 publish 前崩溃。Outbox 把“还有事件待发送”本身变成持久事实，relay 可以恢复。

### 替代方案

- **直接 publish**：低延迟、实现简单，只适合允许丢失的通知，不适合可靠业务事件。
- **MQ transaction**：只能解决特定 MQ 与本地流程的一部分问题，仍不能与 MySQL/Mongo 统一提交。
- **CDC/binlog**：减少应用 staging，但事件语义容易与表结构耦合；需要成熟 connector、schema registry 和运维能力。当前 Event catalog、payload 构造和治理都在应用层，Outbox 更直接。
- **轮询业务表推导事件**：容易重复推导、漏掉状态转移语义，也难保留原始 event ID。

Outbox 的代价是至少一次投递、积压治理、清理和 relay 运维；它解决“不丢已提交意图”，不解决 consumer exactly-once。

## 7. 决策五：数据库约束裁决正确性，Redis 只降低竞争代价

### 当前实现

- AnswerSheet 依赖 `(writer_id, idempotency_key)` 唯一约束、fingerprint 和 Mongo transaction。
- 任务/状态推进使用 DB claim、条件更新或 CAS。
- Redis SubmitCoalescer、LockLease 和 ready-index 用于减少重复工作、协调 owner 或加速发现。

### 为什么“先查再写”不够

两个并发请求都可能在插入前看到“不存在”。只有在同一事实存储中的唯一键或条件更新，才能在竞争时给出唯一裁决。Redis 锁存在过期、网络分区、进程暂停和绕过路径；若锁失效就能写坏数据，它就被错误地提升成了正确性根。

### 替代方案

- **悲观行锁**：适合已有行的短事务竞争；不能锁住尚不存在的自然键，且会增加等待和死锁风险。
- **乐观版本/CAS**：适合低冲突状态推进，冲突时调用方需重读和重试。
- **Redis 分布式锁**：可降低数据库热点，但除非引入 fencing token 并由事实存储校验，不能阻止过期 owner 写入。
- **单线程队列**：可在一个分区内串行化，但生产当前没有 SubmitQueue，且队列仍要处理重放与持久化失败。

## 8. 决策六：查询模型按新鲜度选择，而不是强制一种 repository

当前存在三类读路径：

| 类型 | 新鲜度 | 优点 | 主要风险 |
| --- | --- | --- | --- |
| 权威库直读/join/aggregate | 数据库当前可见状态 | 语义直接 | 查询成本、耦合、容量压力 |
| 异步投影 | 取决于 checkpoint/consumer lag | 为查询优化、可跨聚合 | 延迟、重建、版本切换 |
| cache decorator | TTL/version/失效协议决定 | 降低热点读取成本 | 陈旧、击穿、错误缓存 |

“read model”不自动等于最终一致；“用了 cache”也不自动意味着允许读旧值。每个 query port 应声明：事实源、最大可接受 lag、miss/failure 行为和重建路径。

替代的“所有查询都加载聚合”看似统一，却会让列表、统计、搜索和报表查询承担不必要的对象重建成本，也容易诱发 N+1。

## 9. 决策七：Backpressure 与连接池分层治理

### 当前实现

共享 limiter 在一次已接入的 DB 操作前 acquire，直到操作返回后 release；driver pool 负责连接复用和自身排队。两者解决不同问题：

- limiter 控制应用愿意给依赖的并发与最长等待；
- pool 控制真实连接资源；
- HTTP/MQ RateLimit 控制单位时间到达量。

当前 Mongo Outbox 接入共享 Mongo limiter；assessment MySQL Outbox Store 直接使用 GORM，未计入共享 MySQL limiter。这是接线缺口，也是指标解释边界。

### 替代方案

- **只调大连接池**：可能把更多并发直接压给数据库，放大尾延迟。
- **只做入口 QPS 限流**：无法表达一次请求执行多次 DB 操作、慢 SQL 和后台 worker 竞争。
- **每个 repository 独立 limiter**：隔离更细，但总预算容易相加后突破数据库容量。
- **全局分布式 semaphore**：跨实例预算更精确，但 Redis/协调依赖成为新的准入故障面；当前采用每进程静态预算并要求按副本数推导。

## 10. 决策八：Migration 与一次性修复分开

versioned migration 适合可排序、可审计、随部署执行的 schema/index 变化；`scripts/oneoff` 适合大规模 backfill、审计和不可安全重复的修复。

不选择运行时 `AutoMigrate` 作为生产真值，因为它通常不能表达：

- destructive change 的灰度顺序；
- 大表回填的 checkpoint 和限速；
- 旧版本进程的兼容窗口；
- dirty version 与人工判断；
- Mongo 索引、数据语义修复和回滚证据。

migration 文件存在只证明计划执行某项变更，不证明旧读写者已经退场。删除字段/表/集合前仍要搜索 composition root、repository、read model、worker、脚本和回滚版本。

## 11. 决策九：承认 OSS 与数据库之间存在失败窗口

OSS 不参加 MySQL/Mongo transaction。当前对象写入与元数据变更不能被描述成原子发布。

对必须一致的对象流程，推荐显式状态机：

```text
create pending metadata
      ↓ idempotent upload
verify object checksum/key
      ↓
mark ready
      ↓
garbage collect abandoned pending/object
```

替代方案包括先上传再写元数据、先写元数据再上传、临时 key 后原子 rename/copy；每种都有孤儿对象或悬空元数据窗口，必须配合幂等 key、状态和清理任务，而不是依赖调用顺序碰运气。

## 12. 评审时应追问的反例

1. transaction callback 内某个 repository 是否错误地使用了外层 `ctx`？
2. 新 Event 的 Outbox 是否与事实使用同一数据库 profile？
3. duplicate 后是直接报错，还是回读并比较业务意图？
4. read model 的 checkpoint、lag 和重建入口在哪里？
5. raw GORM/Mongo 调用是否绕过组织 scope、translator 或 backpressure？
6. migration 是否允许旧版本进程继续运行和回滚？
7. OSS 上传成功、DB 更新失败时，孤儿对象如何发现？
