# MQ 发布、消费与结算

QS 决定消息的业务含义和持久处理边界，SDK 执行 NSQ 发布、物理重投和失败中转。生产者发送结算、每个 channel 的 FIN 与业务效果分别成立。

## 发布与传输范围

Durable 事件走原事务 Appender→标准 Store/Relay→SDK Publisher；best-effort 走 RoutingPublisher→SDK wire codec→WirePublisher。两条链都保持原事件 UUID 与 wire 合同，完整链见[架构](./10-架构与责任边界.md)。

RoutingPublisher 按 Registry 解析 topic：未知路由报错并记录 `unknown_event`；`mq` 编码并发送，`logging/nop` 只用于直接发布退化或独立测试。生产标准 Outbox 必须使用 NSQ/MQ-backed 配置，不会以日志发布标记 published。

当前 QS API、授权通知与 Worker 支持显式选择 NSQ 或 RocketMQ 普通消息，默认仍为 NSQ。`provider=rabbitmq` 在配置校验阶段拒绝；旧 RabbitMQ 参数和装配已移除。component-base `v0.8.0` 不再拥有通用消息或 Redis Signal 包，codec/transport 使用 reliable-messaging。

M3 接入基础锁定 SDK `v0.5.0-rocketmq-tx.2`，增加显式 `qs.mysql`/`qs.mongo` 绑定、v2 路由读取及独立事务运行器。构造只读取配置，不启动 Broker、数据库查询或 DDL；Start、写准入、StopAdmission、Close 和 Wait 由宿主负责。暂停写入保留 Checker，关闭超时保留真实未完成结果。业务事务尚未接入该运行器，旧 Outbox wire 装配拒绝带事务 owner 的配置，不能仅改 provider 或版本就启用事务发布。完整进度统一由 [infra M3 总表](https://github.com/FangcunMount/infra/blob/codex/rocketmq-m3/docs/server/rocketmq-m3-execution.md)维护。

本次Go修订仅修复私有driver指标回写/ACK hook的meter指针race，协议/结算API不变；SDK PR46和固定源码`8fb6fc57`的源码race、NSQ及两档各31项实际双存储/跨语言验证通过。

本次 SDK 升级已重新审计失败交接：前后 tag 的 `transport/nsq`、`wire/legacy` 子树相同，RocketMQ `handle`、`Ack`、`dispatch` 结算实现保持原字节；v2 多物理输入共享预算的订阅选择变化不改变失败审计成功后才能 ACK 的边界。这是源码审计及回归结果，真实故障和生产切换另行验收。

Wire 分两层：`wire/domain` 保持领域 JSON 的 id/eventType/occurredAt/aggregate/data，`wire/legacy` 的 Revision2 保存原 UUID、metadata 和领域正文。QS 使用 SDK 编码算法，保留业务 DTO、topic 与 source；重投时原 ID/bytes 不变。

## M3 owner 凭据绑定

`messaging.rocketmq.transactions.<owner>.credentials_file` 可以覆盖该 owner 的发送/回查凭据。配置同时包含 `qs.mysql` 与 `qs.mongo` 时，两者必须显式指定不同文件，并读到不同 Broker username；即使两个文件内容相同也拒绝启动。基础 `rocketmq.credentials_file` 仍供普通通知和消费者使用；单 owner 未覆盖时沿用基础凭据。构造只读取配置文件，账号和 ACL 由 infra 安装，不在宿主启动时创建。

最终 manifest 及五个最小角色见 [infra M3 资源候选](https://github.com/FangcunMount/infra/blob/main/docs/server/rocketmq-m3-resources.md)。owner 凭据检查不代表完整进程装配、Broker 连通或生产切换通过，这些分别由 T21、T22 和生产任务验证。

## RocketMQ 普通消息接入

`messaging.provider=rocketmq` 要求 endpoint、私有 credentials_file、ca_file 和受审核的 routes_file（兼容 version1；M3 显式采用 version2）。普通发布的逻辑 topic/subscription 绑定预创建的 NORMAL topic/group；事务入口只选取精确 owner 的 TRANSACTION 路由。Broker 由 infra 以 Docker 维护，QS 不自动创建资源。Worker 仍共享 `qs-worker` 订阅，独立投影保留自己的订阅。IAM 通知使用稳定的 `qs-authz-sync-apiserver-<instance_id>` 以保持每实例广播语义。

原业务事务、标准 Outbox、Wire 字节、业务回执、持久幂等和冻结恢复边界不变。`publish_enabled=false` 在 Relay 领取前暂停；AI Relay 在扫描前暂停，Worker hold replay 不启动。Broker 确认只结算发布，不代替 AI/QS 的业务回执。此阶段没有 RocketMQ 事务消息，也没有移除 Outbox。

RocketMQ 使用手工 ACK、可见期续租和有界处理期限。处理期限复用现有 worker 超时配置，校验仍要求长于下游 RPC；消费失败预算仍受原有上限约束。耗尽后直接调用宿主持久失败审计，审计提交失败不允许 ACK，不经 NSQ 的失败中转 topic。迁移104新增 `event_delivery_transport_evidence`，在同一 MySQL 事务保存实际物理来源、独立应用身份、原始二进制 Wire、metadata 与原死信行；同传输身份内容冲突拒绝提交，非空证据表阻止回滚。原死信 payload 与人工重放政策保持独立。

源码能力和静态配置不证明生产启用。上线需另核对固定 SDK/镜像、有效 provider、私有端口、订阅就绪、持久回执与业务结果；切换后首次发布之前与之后的回退条件不同，后者必须先对账。

## Worker 主 channel

Worker 加载 YAML 和 EffectiveRegistry，创建显式 handler registry，校验必需客户端与 handler 后订阅。channel 使用 Worker service name；首次消费前用宿主给定 NSQ 节点准备持久 channel。装配、拓扑准备和失败 recorder 都是启动前提。

`messaging.nsq-message-timeout` 作用于所有 Worker topic；版本化生产配置为 `6m > grpc.ai-explanation-timeout 5m`，校验要求消息超时严格长于该 gRPC 等待上限。它不是 handler 执行许可，也不能替代 run lease、deadline 或 unknown-result 规则。未显式配置的通用 subscriber 保留零值交给服务端协商，负值拒绝。现场 effective value 仍需部署证据。

## 当前结算政策

SDK 在 handler 尚未显式结算时，返回错误触发 NACK/重投，返回 nil 触发 ACK；显式结算只执行一次。QS 适配器必须把返回值绑定到正确持久责任。

| 路径 | QS 处理 | 当前 Consume outcome |
| --- | --- | --- |
| 缺少 event type 且领域 envelope 无法解析 | 返回错误，由 SDK NACK | `decode_failed` |
| Worker unknown event | 先用原应用/物理身份保存持久失败审计，成功才 ACK | `unknown_acked` / `unknown_ack_failed` |
| unknown 审计失败 | 返回错误，不能 ACK；SDK NACK | `unknown_persist_failed` |
| handler error | 返回原错误，由 SDK NACK | `dispatch_failed` |
| handler 成功或安全重复 | ACK | `acked` / `ack_failed` |
| automatic retry 暂停且 hold 成功 | durable `retry_event_hold` 接管责任后 ACK | `held` / `hold_failed` |
| hold 缺失、写入失败或 ACK 失败 | 返回错误，不把内存接收当持久恢复 | `hold_failed` |

Worker 的 unknown 不是“只有日志然后丢弃”，也不是等待未来版本的无限重投；它已有持久审计供治理判断。附加 Hot-rank consumer 使用自己的过滤合同：同 topic 上其他事件直接 ACK，不走 Worker unknown recorder；无法解析或目标 handler 失败仍返回错误。

旧 `decode_nacked/nacked/nack_failed` 常量保留，不代表当前 SDK Worker/附加投影生成同名指标。SDK 负责实际 NACK，QS 的 `decode_failed/dispatch_failed` 记录进入 SDK 前的失败；不能由它们直接证明 Broker 的最终 REQ/FIN。

## 物理预算与失败审计

QS 默认及硬上限为每次 NSQ 物理消息最多 8 次业务 handler delivery，配置可下调；退避 30 秒起步、5 分钟封顶、20% jitter。重新 PUB 原应用消息会获得新物理 ID，物理次数不能替代原业务 attempt。

SDK 在真实来源 nsqd 准备失败消费者并向该节点的 `cb.failed.<hash>` topic 转交；这是当前兼容命名，不能因前缀仍为 cb 就推断执行器来自 component-base。

```text
业务 channel 达到 MaxAttempts
  → 发布 cb.failed.<hash> handoff topic，取得 PUB 确认
  → finish 原消息（FIN）
  → 独立 handoff consumer
  → MySQL FailedMessageHandler / recorder
  → event_delivery_dead_letter(manual_required) 持久提交
  → FIN 失败消息
```

handoff publish 失败/未知时原消息继续 requeue，但不再次调用业务 handler；只有 recorder 成功后才确认失败消息，recorder 失败时失败消息 requeue。两个 FIN 之间仍有 Broker 持久性窗口。第八次业务失败不是死信行已存在的证据。

QS recorder 保存原应用 UUID、原 NSQ 物理 ID、EventID、org、topic/channel、payload、attempts 和错误，以 `(provider, topic, channel, message_id, transport_message_id)` 保持物理失败幂等。新物理投递失败可形成新行；旧 handoff 缺物理 ID 时用空值保持历史去重。身份或组织/payload 冲突拒绝确认，已占用/终结的行不被重复中转覆盖。

迁移 `000086` 保留旧行，已有同 UUID 多次物理失败时拒绝丢失性降级。Worker 独立 recorder 使用配置的 Asia/Shanghai/+08:00；借用 API 连接池的 recorder 沿用该池时区。标准 Outbox 调度列则按 SDK UTC 时钟合同读取，不能混淆两种存储合同。

稳定 `FailedHandoffGroup` 只改变失败 topic 分组范围；旧中转水位与新 group 不会自动迁移。一般测评订阅留空按原 topic/channel 分组。通用中转算法和来源节点要求见[固定 SDK 文档](./10-架构与责任边界.md#sdk-版本与参考文档)。

## 主消费者与附加投影

`answersheet.submitted` 主 channel 调用 EnsureAssessment；`qs-apiserver-modelcatalog-hot-rank-v1` 独立处理 Hot-rank，使用 event ID Redis processed key。两者有独立消费进度、物理预算和失败审计，Redis 错误只影响投影 channel。独立投影不得放在 publisher hook 内。

幂等必须贴近副作用：Assessment 原业务关联、Evaluation run claim、报告业务键/claim/CAS、逐收件提醒账本各有不同边界。事件策略的唯一映射在[契约矩阵](./20-事件契约与演进.md)，业务窗口见[从事实到结算](./15-从事实到结算-失败窗口与状态机.md)。

report-status 写入/Signal 通知可失败后 ACK，attention 同步也存在记录后 ACK 的路径；幂等 overwrite 或重复投影不意味着本次已经写入。最终读取结果仍须核对业务事实。

## AI workflow 消息运行与维护

**M4 当前契约**：`MessagingRuntime` 只拥有最终 RocketMQ event subscriber 和观测；共享 `qs.mysql` owner 发送 command/ACK。构造要求原事务适配，缺失时拒绝，不构造 NSQ、DirectHandoff、普通消息中间 Relay 或发布扫描。Operation、Payload 和 ACK 仅认当前精确证据。原业务 Run/receipt/Inbox/正文/首次 wire、技术失败账本、准入和离线预检保留。完整边界见 [事务消息与业务效果恢复](./30-Outbox可靠出站链路.md)。

以下带阶段号的材料记录旧实现过程，保留历史解释和 anchor；其中 NSQ 启动、发布型 Outbox、`ai-mq-process`、未接入状态均不适用于最终运行。现行 required 验收使用 infra 的 `m4-current-readers.yml`、`m4-ai-runtime.yml` 和 `m4-qs-runtime.yml`，按精确候选与已发布稳定 SDK 执行。

QS 专用 AI 消息链路由 qs-apiserver 宿主装配。本节说明其原事务、准入门禁和发布绑定；前文的领域事件与 Worker 消费政策仍有各自的 owner。

Runtime commands and events use one MQ Outbox, event subscriber and relay at process startup. The legacy command scanner, staging/retry/settlement SQL and direct runtime gRPC write adapters are retired. The normal module does not export the legacy Results receiver; an explicitly registered compatibility receiver still authenticates mTLS and permanently returns FailedPrecondition without persistence or acknowledgement. Query/governance gRPC and read-only payload retrieval remain available. Disabling MQ cannot reactivate any old writer.

### Assembly and lifecycle

`ai_workflow.messaging.enabled` selects the host `MessagingCommandStore`. Management evaluation Start/Cancel and participant Retry use the same store. The normal bootstrap calls `StartAIWorkflowRelay`; MQ startup validates required database tables and all three business and failure Topic/Channel pairs before connecting. Key loading is explicit local bootstrap work. Constructors do not connect, migrate, or schedule.

`ai_workflow.messaging.nsqd` maps fixed TCP addresses to their corresponding fixed HTTP stats endpoints. Signing and encryption are separate P-256 JWK files. `signing_key_file` and `ai_recipient_key_file` select outbound keys; `decrypt_key_files` and `ai_signer_files` are local kid-to-file trust maps. Old decryption keys remain configured while historical messages may need them. No remote key retrieval or caller-provided endpoint is accepted. Runtime topology preflight is read-only; provision channels before startup.

The host owns one 1-second scan loop, batch 20 and concurrency 1 per subscriber. Broker publication does not decide a command or confirm a result. Shutdown stops relay admission and consumer RDY, waits for committed active handlers, then drains publisher resources before closing the shared governance connection. The module uses a 20-second stop budget. A failed drain reports an error and does not close borrowed host resources or permit another runtime start.

### Durable receiving and technical failure

Authentication precedes body reads and business writes. Inbox, original projection/command decision and final confirmation Outbox commit in one host transaction; only commit permits FIN. Duplicate events rearm the original immutable confirmation. Original raw wire hashes are retained; SDK failure reencoding is used only to authenticate the signed message, never as the original wire hash.

Migration 092 adds the host-owned logical failure ledger and Inbox outcome. The eight-attempt technical budget survives republishing and process/object recreation. A valid event whose budget is exhausted may commit a TECHNICALLY_HELD confirmation without applying a business projection. Physical NSQ attempts and failed-handoff claims cannot invent that logical budget or apply a business effect. Malformed/untrusted inputs enter raw-wire quarantine; failed storage leaves physical delivery unconfirmed. Oversized quarantine inputs retain the full hash with an empty stored wire, not a truncated hash.

### Public operation authorization

Public Start returns 202 `submitted`, original request/operation/command IDs and a fixed local status URL. AI acceptance/rejection is a later durable decision. The public GET `/api/v1/interpretation/ai-workflow/operations/{command_id}` requires `testee_id`, `assessment_id` and `request_id`.

The collection service uses the existing delegated read-only `GetAIWorkflow` RPC with additive `command_id` and `operation` fields; original field numbers and legacy read behavior remain intact. This reuses the established collection workload ACL. The API rechecks the current ProfileLink and assessment, the original request actor/org/testee/assessment, and the command's original request aggregate. Internal OrgAdmin operation queries are not exposed to participants. Closing new intake retains reads and idempotent queries of already committed requests.

### Validation limits and production gate

Local tests cover real MySQL 8.0.36/8.4 and NSQ 1.3.0 at the 262144-byte limit, original-wire retention, duplicate confirmation, lifecycle recreation, cancellation, transaction rollback, persistent technical budget and participant scope. Lifecycle recreation is not a process-kill proof. Original Go M0–M6 acceptance fixtures are not changed or executed by this batch.

Existing isolated evidence covers separate-process command/receipt/final-ACK loss after PUB, Broker and both-process kills, a 128 KiB protected reference through real mTLS, and real browser original-intent behavior against a synthetic HTTP backend. The process helper proves the original transport runtime, not a full QS host. Required remainder: full normal QS host health and each command family's accepted/refused/duplicate chain, reviewed historical inventory and apply tool, genuinely compatible MQ version rollback, final assets and production natural business samples. See the independent R1–R7 execution ledger; none of these tests is production acceptance.

The production review must explicitly include the read-only `/qsai.workflow.v1.MessagePayloads/Get` permission for the qs-ai workload, host key/network/topology mounts and schema ownership. Actual production ACL/configuration readiness must be verified independently; local mTLS service tests do not prove it. Host main merge/automatic deployment requires separate review. SDK prerelease approval is not host production authorization.

### 现用 MQ 只读数据库清单

`qs-ai-messaging audit` 是维护核查工具，不是消息服务。仅借用显式 DSN 建立宿主拥有的连接，用 MySQL READ ONLY / REPEATABLE READ 事务执行固定 SELECT；不加载密钥、不连接 NSQ、不记录正文、不执行迁移/移交/重投/清理或模型调用。二进制由独立 AI bridge CI 构建并记录源码 SHA。

```sh
# 凭据在操作环境中安全设置，不把实际 DSN 写进材料或命令参数。
qs-ai-messaging audit -limit 1000 > mq-database-inventory.json
```

连接从 `QS_AI_MESSAGING_AUDIT_DSN` 获取；构建时通过 `-ldflags '-X main.sourceSHA=<精确提交>'` 固定来源。输出含源码和数据库版本、schema head/dirty、现用 MQ 表是否存在、Outbox 各阶段与未确认消息统计、受保护正文引用的字节数/hash，以及 Inbox、隔离和失败账本数量。工具不再读取 `ai_bridge_commands` 或 `ai_messaging_legacy_commands`，不再输出旧命令待处理、delivered 或移交样本；历史交接与退休核验由专用维护流程承担。

样本截断明确为 incomplete，必须补齐清单后审核。缺 MQ 表显示为未安装；表存在不能证明迁移 head、Broker 拓扑、密钥、权限或业务就绪。现用 Runtime 继续负责组织隔离与操作关联完整性检查；本工具的计数不能替代这些检查或历史全量核验。

真实 MySQL 门禁验证数据库强制拒绝只读事务中的 UPDATE、原记录/预算不变、宿主池仍可用、旧表缺失时仍能读取现用 MQ，以及 held 阶段、持久 attempts、大整数 ID、Unicode 引用和样本截断。缺 schema 与截断均不能当成完整清单。测试仅创建和删除带随机 ID 的专属一次性数据库。

### 统一运行类维护门禁

迁移094只新增宿主数据库单行 `ai_messaging_admission`，初始 **closed=true / revision=0**。MQ 正常启动要求表和行存在，但门禁关闭不停止已提交消息的 Relay、接收或 ACK。配置 `ai_workflow.enabled` 的旧参与者入口开关不能代替该统一维护门禁。

Start、Change、参与者 Retry、评测 Start/Cancel 在同一条 `MessagingCommandStore.stageCommand` 中，先借原提交事务取得门禁共享行锁，再核对不可变原操作。新操作仅在开放时继续原业务写入、操作与 Outbox；锁保持至原事务提交/回滚。关闭者持有同一行的排他锁，因此成功提交关闭后，先进入的提交已经结束，后来的新操作不能越过门禁。没有缓存、第二个调度器或独立服务。

关闭后的同身份/内容/组织/操作人/资源/聚合/消息族操作返回原操作，不执行今天的版本/状态验证或重封装；当前调用权限仍在应用入口重检。内容/主体冲突依然拒绝。查询不受门禁影响。新操作明确 HTTP429：`AI runtime command admission is closed for maintenance; operation was not submitted`，无操作或Outbox；该关闭原因与 AI 容量/版本业务拒绝不同。公共同步委托 RPC 保留原通道，将固定关闭原因映射 ResourceExhausted 再由 collection 返回429，无每日容量 Retry-After。DB不可用、缺表/行或锁等待取消都保持不确定错误，不能冒充确定未提交。

准入子命令 `qs-ai-messaging admission inspect|close|open` 使用独立的 `QS_AI_MESSAGING_CONTROL_DSN`；变更必须传 `-expected-revision <已审核当前版本>`。inspect 用只读事务；close/open 用宿主事务，30秒有界等待，成功输出仅在提交后。旧revision拒绝，失败输出不含DSN/底层错误；遇不确定提交结果先inspect，不能猜测关闭已完成或重复开门。工具只操作门禁，不安装schema、不迁移、不连Broker、不触发模型。audit继续永久只读，无公开维护HTTPAPI。

生产开门仍需完整审核和现场 prerequisites。本批候选开发不授权主线合并/自动部署/切换，不执行down迁移。真实风险测试覆盖五族关闭/原幂等wire和时间、当前投影变化后复用原Change、关闭等待MySQL实际共享锁后原提交/回滚、取消/缺行无孤儿记录、旧revision及宿主池继续可用。

### 正常宿主配置解码

正常启动使用 Viper，而隔离进程 helper 直接读取 JSON。Viper 会把 `127.0.0.1:4150` 和 `qs.encrypt.v1` 内的点拆成配置树；直接解码到字符串映射会失败。MQ 选项仅对 NSQD、解密信任和 AI 签名信任三种本地映射接收该树，在宿主 `Options.Complete` 中恢复完整字面键，再沿原 Validate/KeyID/目标检查。不改变通用配置加载器、SDK Go 接口或 wire，不读取密钥或连接网络；直接 JSON / 构造选项保持原映射形态。非字符串叶值、保留的空分支及歧义拒绝，不将数字或列表转为可信密钥路径。Viper丢弃的空映射保持空值，仅兼容禁用配置；启用时沿原完整性校验拒绝，不能产生可信端点。沿现有 Viper 规则使用一致的小写本地 kid，并与 JWK 的固定 kid 精确一致。

正常镜像启动与配置加载的回归必须独立于 helper 证据；配置失败、IAM 关闭的部分探针以及镜像静态检查都不能关闭完整宿主权限验收。

### 宿主连接字符集与原 Unicode 正文

当前 component-base 宿主池协商 `utf8`（MySQL 8 对应 utf8mb3），而合法结果含四字节 Unicode。原 JSON 参数写入会报转换错误，普通 JSON 查询还会把这类字符转换成问号；只用驱动默认 utf8mb4 的测试连接不能覆盖该风险。

消息外围对已有请求、历史命令和结果投影的 JSON 参数显式使用 `CONVERT(CAST(? AS BINARY) USING utf8mb4)`，对保留的 JSON 查询使用二进制结果读取。原 JSON 的 UTF-8 字节在进入数据库 JSON 解释前不经过连接字符集转换，读取仍由原业务解码器处理。首次业务 hash、protobuf body、签名和 wire 不重建；JSON 数据库自身的表示规范化规则不改变。没有 SET NAMES、额外池、连接配置或 schema 修改。

必要存储回归必须显式协商宿主的三字节字符集并检查未被适配器更改，覆盖含 emoji/补充平面字符的原接单与历史回答、合法128KiB结果、原hash、重复复用ACK、ACK失败时投影与Inbox共同回滚。正常镜像中失败到技术挂起的旧隔离样本保留原身份、wire与预算；修复验证使用独立合成样本，不重置挂起样本或授予新模型调用。

### 最终 ACK 失败预算

当前固定 SDK `v0.3.0-mq-ai.2`（源码 `8633ba585b5a1c8f95fb16b19469fbd0097611c7`）。只对无需业务回执的最终 ACK，成功 PUB 不再消耗技术失败预算；Unknown 仍计入原持久预算，重复事件不能解除已有 held 状态。接收与 Relay 存储回归覆盖两次未知后连续16次成功重发、首次 wire/正文/时间及单次业务投影保留，以及8次失败挂起后的重复接收不能解挂。

旧 ACK 计数可能包含成功发布，补丁无法推断历史失败次数，不自动归零、解挂或重封装。需要按原事实治理历史挂起；技术重发不会授权模型调用。既有 Go subscriber、relay、transport/wire、接口和黄金样例与 alpha1 相同（只读源码差异核对）；不代签 M0～M6 业务验收。宿主正常镜像、兼容回退与生产对账单独取证。

### M3 V2 业务证据引用

`evidence.EventEvidenceV2` 保存原事件标准引用、首次SDK规范编码的精确transaction Reference及business binding摘要，支持JSON/BSON并保留MaxInt64 fence。它仅表示身份引用；Validate不会读库或证明commit。业务接入时必须把它与业务事实、CommitWitness写入同一受guard保护的原根事务，再由权威Store完成回查。

`DecodeRecord` 显式区分V1与V2，旧历史证据不会自动升级为witness，未知版本拒绝。旧V1入口继续拒绝V2；域字段的接入留待各业务批次。此批没有改变正常发布、Replay或消费责任。

### M3 不可变档案基础（尚未接入业务写入口）

MySQL106新增 `ai_messaging_archive`，与发布型 Outbox 分开。档案只保存原组织、首次 header/body/wire 和精确事务引用，不含扫描、attempt、due 或结算状态。`TransactionArchive.Bind` 必须先借原 `*sql.Tx` 取得 SDK guard，再从 reservation 赢家的冻结计划写入档案；`CommitWitness` 只暂存证据，最终 commit/rollback 仍归宿主。重复档案逐字节比较，不重新 Seal；重复观察者没有执行资格。

本地 codec `qs-ai-archive/v1` 使用大端无符号64位组织与序号、显式长度和原始字节。首次 header 包括 protobuf 未知字段，不经语言间重新序列化；SDK 计划保存此本地载荷，Broker 仍收到原 first wire。Go/Python 共用固定向量，向量中的假密文仅验证 codec，不能证明消息认证。SDK 的计划大小上限继续生效，超限在业务提交前拒绝。

显式装配 `MessagingReader.Archive` 后，新档案必须通过当前配置的 owner/store 及原生 execution/branch 双 committed 证据，匹配原指纹、wire hash、组织和正文引用后才可读取。存在 Prepared、损坏或矛盾档案时拒绝，不回落旧 Outbox；只有新身份不存在才走旧读取合同。未装配时旧 reader 保持原行为。档案没有发布职责，也不能替代 command operation 或业务 ACK。安装/原事务/损坏拒绝由 `TestM3TransactionSchemaNative` 的隔离双库门禁验证，生产未执行迁移。

### M3 默认事务宿主装配（T22 源码批次）

显式配置 RocketMQ 事务 owner 后，API resource stage 使用独立的 NORMAL 客户端，仅接受目录中的 best_effort 事件。随后惰性构造 `NewWithTransactionOwners`，借用原 MySQL/MongoDB；模块共享这两个 owner 和同一个目录。缺 owner、错误原连接、替换 owner 或同时启用旧发布型 Outbox 都拒绝；不会静默回退旧发布器。AI 功能关闭时不暴露 command 写端口，但空闲 Checker 仍登记本 owner 配置的全部事务 Topic。

构造不启动客户端、线程或 DDL。Start 先启动两个 owner 的 Checker，再按显式配置开放写准入，然后启动消费者。Close 先封准入；事务宿主先排空 AI 等业务模块，再停止事件消费者、排空 owner，最后由 process 关闭 NORMAL 客户端和原连接池。七类 scheduler 保持原执行配额，只增加真实循环结束的等待，不将取消信号当完成。

process 关闭、`CleanupContext` 和事件 `CloseContext/Wait` 共用各自唯一的清理协调器。调用超时返回 `ShutdownIncomplete` 和仍在运行的计数，清理继续持有依赖；重复调用等待同一完成结果。gRPC 排空也由同一进程协调器持有，不将等待超时当作请求已结束；已关闭的容器拒绝重新初始化。prepared server 等待同一进程协调器结束；事务模式关闭失败不以默认退出0冒充成功。清理失败不会继续关闭数据库，也不会报告成功。启动阶段失败时保留已构造的 container/transport，沿同一排空顺序释放资源；原错误与清理错误均保留。

默认事务宿主在两个 owner 启动后装配 MySQL/Mongo 到期 dispatcher，借用同一原数据库和 owner，不创建新的 producer 或连接池。启动扫描前分别以2秒新读取边界检查调度 schema 与绑定；缺失或冲突阻止启动，不执行 DDL。每 owner 单循环默认每5秒最多50条、每轮5秒预算。owner 写准入关闭时不取新计划；扫描只发送已有授权的到期事件，不调用评分、报告或模型，也不增加业务 attempt。它与 SDK 未决证据维护是独立责任，不能用其中一个代替另一个。

`system_governance.retry.dispatch` 可覆盖 `interval`、`budget`、`batch`，时间必须为正，批量限制1至50，未指定字段沿用默认值。`system_governance.retry.automatic_retry_enabled=false` 阻止自动计划准备半消息，仍允许有明确授权的 manual/force 计划。它是本 API 进程的固定启动配置；worker 的 `retry_governance.automatic_retry_enabled` 另控制延期消费，生产冻结清单必须协调配置，不能将它们当成一个全局动态开关。

到期循环注册到原 scheduler 生命周期。取消传递到扫描 context，但未返回的数据库调用仍占用原循环；关闭需等待真实返回，再关闭 owner 和原连接池。重复 Start/Wait 不创建额外循环。4个受影响包的293项定向 race 测试零失败/跳过，覆盖准入、deadline、重复启动、取消后的真实等待、启动预检失败及启动顺序；这些属于源码/单元验证。

完整宿主真实生命周期、跨实例回查、预算和数据库故障仍由 T22/T23 验证；默认到期接线及下述延期消费仍须真实依赖门禁闭环。无生产 schema、provider、资源或部署变更。进度统一见 [infra M3 执行总表](https://github.com/FangcunMount/infra/blob/main/docs/server/rocketmq-m3-execution.md)，本仓库不维护第二套任务计数。

事务模式的评分与报告模块不再要求或保留旧发布型 Outbox profile。创建尚无事件的 pending Assessment 借原本地事务保存；若对象已经携带事件，此入口在写库前拒绝。正式提交仍只经独立事务 submitter，Unknown 不回落事件缺失的保存路径。旧非事务模式仍要求原 stager，M4 再清理其实现。

### 当前 RocketMQ 暂停消费与恢复（T22 源码候选）

consume-only worker 使用 `DeferredDeliveryStore`，借用原 hold SQL pool。暂停自动消费时，在一个原SQL事务内保存原始运输证据104及SQL109的V2延期关联，成功才允许原delivery Ack。保存原始wire、元数据、物理消息ID和首次正文；重复只核验原记录，不重置终态或重新编码。V1记录不由V2读取器接管，旧未决责任仍须在T25/T32具名处置。

恢复只调用原dispatcher，复用事件ID、正文和原业务重试授权；没有publisher或新增业务attempt/模型调用授权。只接受m3-1评估/报告事务输入及既有automatic请求，错误owner、路由、身份或wire均拒绝。NORMAL输入仍按原独立订阅消费。SDK物理接收最多N条，延期循环额外最多1条等待责任；两者执行同用原worker的N个名额，配置48仍是48个实际执行，不放大并发。
