# MQ 发布、消费与结算

## 1. 链路总览

```text
DomainEvent
   ↓ EffectiveRegistry.Lookup(event type)
RoutingPublisher
   ↓ eventcodec envelope + eventmessaging metadata
MQ topic
   ├─ worker 主 channel → handler registry → ACK/NACK
   └─ additional channel → projection handler → 独立 ACK/NACK
```

发布端只向 Registry 已知的 Topic 路由；消费端只向显式 handler registry 分发。未知事件不会凭命名约定动态加载 handler。

## 2. RoutingPublisher 模式

| 模式 | 行为 | MQ-backed | Durable Outbox 可标记 published |
| --- | --- | --- | --- |
| `mq` | 编码并发布到配置 Topic | MQ publisher 非 nil 时是 | 是 |
| `logging` | 记录事件，不发送 MQ | 否 | 否 |
| `nop` | 忽略直接发布 | 否 | 否 |

默认环境映射为 production 使用 MQ、development 使用 logging、test 使用 nop。环境默认只是兜底；关键安全门禁是 `IsMQBacked()`。

对 best-effort 事件，logging/nop 是允许的退化：它本来就没有可靠投递承诺。对 durable event，ImmediateDispatcher 和 relay 只有在 MQ-backed 时才启动，
因此不会因为 logger 返回 nil 就把 Outbox 标成 published。

Registry 不认识的 event type 不会猜测 Topic，发布结果记录为 `unknown_event`。

## 3. MQ message 构造

`component-base/pkg/eventcodec` 把 DomainEvent 编码为统一 envelope，`component-base/pkg/eventmessaging` 构造 MQ message：

- message UUID 使用 event ID。
- body 是包含 `id`、`eventType`、`occurredAt`、`aggregateType`、`aggregateID`、`data` 的 JSON envelope。
- metadata 包含 `event_type`、`aggregate_type`、`aggregate_id`、`occurred_at`、`source`。

source 表示发布运行时来源，例如 apiserver。它用于观测和排障，不代替 event owner。

## 4. Worker 主消费者

worker 启动时：

1. 加载 `configs/events.yaml` 并构造 EffectiveRegistry。
2. 构造显式 handler registry。
3. 校验每个主 handler 都存在，且没有错误映射。
4. 按 Topic 建立订阅，channel 使用 worker service name。
5. 收到消息后提取 event type、解码 envelope、dispatch handler、执行统一结算。

handler factory/decorator 可以增加日志和指标，但不能改变业务 handler 的错误返回或运输层 ACK/NACK 语义。

NSQ 的 `msg_timeout` 是 broker 判断一条在途消息何时可重新投递的外层边界。worker 通过 `messaging.nsq-message-timeout` 显式配置它，配置校验要求该值严格长于 `grpc.ai-explanation-timeout`；
生产当前为 `6m > 5m`。这样长耗时 AI handler 仍在等待 apiserver/Provider 时，NSQ 不会按客户端默认值提前重投同一事件。未显式配置该字段的既有 subscriber 必须保留零值，由 NSQ 服务端协商默认超时；负值才属于非法配置。
该超时作用于 worker 的全部 NSQ topic，不代表 handler 可以运行 6 分钟，也不替代业务 Attempt lease、gRPC deadline、幂等和 `result_unknown` 规则；
如果未来需要自动 touch 或按 topic 区分超时，应在 messaging adapter 层另行设计并验证。

## 5. 统一结算策略

dispatch 结果与 handler error 分开：

```go
type DispatchOutcome string

const (
    DispatchHandled DispatchOutcome = "handled"
    DispatchUnknown DispatchOutcome = "unknown"
)
```

运输层映射固定如下：

| 场景 | 判定 | MQ 动作 | Consume outcome | 原因 |
| --- | --- | --- | --- | --- |
| metadata 无 event type 且 envelope 无法解析 | decode-invalid | NACK | `decode_nacked` / `decode_nack_failed` | 保留统一的运输失败证据，并进入有界运输重试 |
| event type 未注册 | unknown | ACK | `unknown_acked` / `unknown_ack_failed` | 当前进程无法处理，持续重投无收益 |
| handler 返回 error | handler failure | NACK | `nacked` / `nack_failed` | 交给 MQ redelivery 重试 |
| handler 成功或识别为重复 | handled | ACK | `acked` / `ack_failed` | 本 channel 已完成结算 |
| automatic retry 开关暂停且 hold 成功 | held | ACK | `held` / `hold_failed` | `retry_event_hold` 已接管恢复责任，不继续消耗运输预算 |

ACK/NACK API 自身失败会记录独立 outcome，不能把“handler 已处理”和“broker 已成功结算”混为一个指标。

NACK 不是无限调用业务 handler。subscriber 的默认和代码硬上限都是 8 次 handler delivery attempt，退避为 30 秒起步、5 分钟封顶、20% jitter；配置可以下调，关闭 bounded delivery 等价于只允许 1 次。
到达 `MaxAttempts` 后进入 provider terminal handoff；handoff 与 MySQL 持久化不是同一个原子步骤。

### 5.1 NSQ terminal handoff

当前 NSQ 代码路径为：

```text
业务 channel 达到 MaxAttempts
       ↓
发布 cb.failed.<hash> handoff topic
       ↓ publish success
finish 原消息
       ↓
独立 handoff consumer
       ↓
MySQL FailedMessageHandler / recorder
       ↓ success
event_delivery_dead_letter(manual_required)
```

- handoff publish 或连接准备失败时，原业务消息 requeue；后续 delivery 不再调用业务 handler，而是继续尝试 terminal handoff。
- handoff consumer 调用 recorder 失败时，handoff 消息按退避 requeue，形成独立于业务 channel 的积压窗口。
- recorder 成功后，才把应用消息 UUID、NSQ 物理投递 ID（旧 handoff 可为空）、event ID、组织、topic、channel、payload、attempt 和最后错误写入 MySQL。
- 相同 `(provider, topic, channel, message_id, transport_message_id)` 的重复 handoff 只刷新尚未占用的人工记录；已占用、已终结、已归档的记录和身份字段保持不变。重放保留应用 UUID，但新 NSQ 投递取得新的物理 ID，因此再次失败形成独立死信行。相同物理身份却出现不同组织、EventID 或 payload 时拒绝落库确认，handoff 继续重试。
- 旧 handoff 缺少物理 ID 时仍以空值按原逻辑 UUID 去重；迁移 `000086` 保留这些历史行，降级前若已有同 UUID 多次物理失败则拒绝丢失性回退。每条新失败初始为 `manual_required`，不会自动重新投递。
- Worker 独立打开的 MySQL recorder 使用宿主配置的 `Asia/Shanghai` 解析位置和 `+08:00` 会话时区；与 API 共用连接池的 recorder 沿用该连接池配置。两者都应按 UTC+8 写入和读取死信时间，不能仅以容器系统时区推断数据库会话时区。

因此，第 8 次 handler 失败只证明业务处理预算已耗尽，不能单独证明 MySQL dead-letter 行已经存在。排障时必须区分原 channel、`cb.failed.<hash>` handoff topic 和 recorder 三个位置。

component-base v0.6.11 保留上述结算顺序与原物理投递身份；新增的 `FailedHandoffGroup` 只改变 NSQ 失败中转 topic 的命名范围。留空仍按业务 topic／channel 分别创建中转；显式设置后，同一业务 topic 与稳定 group 的实例共用一个持久中转 channel，信封仍记录原业务 channel。QS 授权通知的 `ephemeral-nsq` 生产开关默认关闭，只有已提交版本十秒栅栏启用且单独验收后才可切换；一般测评业务订阅不因 SDK 升级改变分组。切换前需核对旧中转未完成水位，不能把新 group 当作旧失败消息的自动迁移。

### 5.2 RabbitMQ 实现边界

代码也支持 RabbitMQ：它声明 `<topic>.retry` exchange 与 `<channel>.retry.<attempt>` 延迟队列，并通过 dead-letter exchange 回到原 topic；
同时声明 `<topic>.dlx` 和 `<channel>.dlq`。预算耗尽时先调用 failed-message recorder；recorder 或 DLX publish 失败会回到 failed-only retry，成功后才 ACK 原 delivery。

这是代码支持能力的说明，不是当前生产 provider、真实拓扑健康或 RabbitMQ 环境已验收的证据。provider 的实际选择和运行状态必须由目标环境有效配置、broker 拓扑与运行证据确认。

IAM authz version subscriber 当前只由 apiserver 持有；collection-server 不再创建该 subscriber，也不参与这张业务 Event 死信表。

handler 仍必须区分可重试基础设施错误与已经落为业务终态的失败。若 handler 已保存明确结论并返回 nil，运输层会 ACK。

## 6. 死信人工重放

```text
event_delivery_dead_letter(manual_required)
       │ operator selects org-scoped rows + expected attempts
       ↓
events.replay_delivery（high risk + confirmation）
       │ prevalidate batch → claim one row → decode → RoutingPublisher.Publish
       ├─ decode failure before publish → manual_required + last_error
       ├─ publish and completion confirmed → terminal + replayed_at
       └─ publish/completion outcome unknown → claimed automatic + replay_request_id
```

治理动作每次最多接受 100 个 target，先预检整批组织、当前 disposition 和 `expected_delivery_attempts`，然后逐条占用和发布；每条占用时再次检查并发状态。中途失败不回滚此前已完成的投递，未处理的后续行仍保留 `manual_required`。未知结果的行在治理候选中显示为“投递结果待核对”，附操作请求 ID；不能因调用返回错误而盲目再次发布。它不是自动重试器，也不会修改 payload：
decode-invalid 消息即使形成死信，若 payload 不是合法 canonical event，重放仍会失败，需要先修复 producer/contract，再决定数据处置。

原重放已返回失败或超时而行仍由该操作占用时，操作员不能新建重放请求试探结果。报告生成事件可走独立的事实核实结案：提交新的稳定结案请求编号、原重放编号、物理死信 ID、原 EventID、预期投递次数、原因和明确确认；服务在同一 MySQL 事务中锁定原审计与死信，并验证当前报告及关注业务事实后写结案审计和 `resolved_verified`。接口不经 `events.replay_delivery` 的发布路径，也不经通用 `ActionExecutor.Run` 的分步审计。响应未知时先按同一结案请求编号读取回执或重试原输入；查询无回执不证明原事务未提交。原审计仍标记 `running`、业务事实不完整或事件类型不是 `interpretation.report.generated` 时拒绝结案。

## 7. 主消费者与附加消费者

YAML 中的 handler 表示 worker 主消费者。一个事件需要第二个读模型投影时，不在 publisher 前后增加业务 hook，而是在 EventSpec 中登记 `AdditionalConsumers`：

```text
qs.evaluation.lifecycle
   ├─ worker channel → answersheet_submitted_handler → Evaluation 主链
   └─ qs-apiserver-modelcatalog-hot-rank-v1
          → modelcatalog.hot_rank_projection → Redis hot-rank
```

两条 channel 有独立消费进度和失败结算：

- Hot-rank Redis 错误只 NACK projection channel。
- worker 主链不会因 Hot-rank Redis 故障受阻。
- projection 使用 event ID 对应的 Redis processed key 防止重复计数。
- logging/nop 或 MQ 不可用时附加 consumer 显示为 disabled，不通过 publish hook 更新热度。

附加消费者由 apiserver EventSubsystem 在 Start 前冻结 binding，按 Consumer ID 排序启动和关闭。

## 8. 幂等不是统一 ledger

at-least-once 允许以下重复来源：

- MQ 成功但 Outbox mark published 失败。
- immediate 与 relay 竞争同一事件。
- consumer NACK 后 redelivery。
- ACK 成功状态对调用方不可见。
- 人工重放 terminal dead letter。

当前不引入全局 event-id ledger，而是按事件副作用选择业务幂等：

| 策略 token | 主要方法 |
| --- | --- |
| `answersheet-id-lease-and-ensure-assessment` | 以 AnswerSheet/Assessment 业务键租约和 ensure 保护创建流程 |
| `evaluation-run-state-claim` | 通过 Evaluation run state claim 避免重复执行 |
| `report-business-key-run-claim-cas` | 以报告业务键、run claim 和 CAS 保护生成 |
| `report-status-overwrite` | 状态投影允许按业务键覆盖 |
| `repeatable-attention-projection` | attention 投影设计为可重复执行 |
| `terminal-failure-fact` | 写入终态失败事实 |
| `notification-event-metadata` | 通知携带事件 metadata，发送失败不阻断 handler |
| `redis-processed-key-by-event-id` | 以 event ID processed key 去重 Hot-rank 计数 |

best-effort lifecycle 后置动作使用自身发布生命周期策略。具体 token 的权威映射见[Event 契约与演进](./20-事件契约与演进.md)。

只有当某个外部副作用不可逆、现有业务键/CAS/状态机无法保护，并且重复成本明确时，才应为该事件立项 inbox/dedup record。不能为了抽象统一而先引入全局账本。

## 9. 错误边界

| 位置 | 错误处理 |
| --- | --- |
| envelope encode | 发布失败；durable Outbox 保留并重试 |
| MQ publish | best-effort 返回发布错误；durable 由 Store 记录失败后重试 |
| event type unknown at publisher | 不发布，记录 `unknown_event` |
| payload decode in handler | handler error，NACK |
| envelope/event type 无法解析 | NACK；运输预算耗尽后进入 provider terminal handoff，recorder 成功后才形成持久化死信 |
| 可重试依赖错误 | handler error，NACK |
| 已完成/重复事件 | handler nil，ACK |
| 非关键后置通知失败 | handler 内记录，按事件矩阵决定 ACK |
| dead-letter replay decode/publish 失败 | 回到 `manual_required`，保留最后错误 |

## 10. 可观测入口

发布、Outbox 和消费分别记录：

- `qs_event_publish_total`
- `qs_event_outbox_total`
- `qs_event_consume_total`
- `qs_event_consume_duration_seconds`

label 和 outcome 语义见[可观测性与故障恢复](./50-可观测性与故障恢复.md)。日志应带 event type、event ID、topic、aggregate、source/service 和 outcome，
便于在 producer、Outbox 与 consumer 之间关联。
