# MQ 发布、消费与结算

QS 决定消息的业务含义和持久处理边界，SDK 执行 NSQ 发布、物理重投和失败中转。生产者发送结算、每个 channel 的 FIN 与业务效果分别成立。

## 发布与传输范围

Durable 事件走原事务 Appender→标准 Store/Relay→SDK Publisher；best-effort 走 RoutingPublisher→SDK wire codec→WirePublisher。两条链都保持原事件 UUID 与 wire 合同，完整链见[架构](./10-架构与责任边界.md)。

RoutingPublisher 按 Registry 解析 topic：未知路由报错并记录 `unknown_event`；`mq` 编码并发送，`logging/nop` 只用于直接发布退化或独立测试。生产标准 Outbox 必须使用 NSQ/MQ-backed 配置，不会以日志发布标记 published。

当前 QS API、授权通知与 Worker 只支持 NSQ。`provider=rabbitmq` 在配置校验阶段拒绝；旧 RabbitMQ 参数和装配已移除。component-base `v0.8.0` 不再拥有通用消息或 Redis Signal 包，codec/transport 使用 reliable-messaging。

Wire 分两层：`wire/domain` 保持领域 JSON 的 id/eventType/occurredAt/aggregate/data，`wire/legacy` 的 Revision2 保存原 UUID、metadata 和领域正文。QS 使用 SDK 编码算法，保留业务 DTO、topic 与 source；重投时原 ID/bytes 不变。

## Worker 主 channel

Worker 加载 YAML 和 EffectiveRegistry，创建显式 handler registry，校验必需客户端与 handler 后订阅。channel 使用 Worker service name；首次消费前用宿主给定 NSQ 节点准备持久 channel。装配、拓扑准备和失败 recorder 都是启动前提。

`messaging.nsq-message-timeout` 作用于所有 Worker topic；版本化生产配置为 `6m > grpc.ai-explanation-timeout 5m`，校验要求消息超时严格长于该 gRPC 等待上限。它不是 handler 执行许可，也不能替代 run lease、deadline 或 unknown-result 规则。未显式配置的通用 subscriber 保留零值交给服务端协商，负值拒绝。现场 effective value 仍需部署证据。

## 当前结算政策

SDK 在 handler 尚未显式结算时，返回错误触发 NACK/重投，返回 nil 触发 ACK；显式结算只执行一次。QS 适配器必须把返回值绑定到正确持久责任。

| 路径 | QS 处理 | 当前 Consume outcome |
| --- | --- | --- |
| 缺少 event type 且领域 envelope 无法解析 | 返回错误，由 SDK NACK | `decode_failed` |
| Worker unknown event | 先用原应用/物理身份保存持久失败审计，成功才 ACK | `unknown_acked` / `unknown_ack_failed` |
| unknown 审计失败 | 返回错误，不能 ACK；SDK NACK | `unknown_persist_failed` |
| handler error | 返回原错误，由 SDK NACK | `dispatch_failed` |
| handler 成功或安全重复 | ACK | `acked` / `ack_failed` |
| automatic retry 暂停且 hold 成功 | durable `retry_event_hold` 接管责任后 ACK | `held` / `hold_failed` |
| hold 缺失、写入失败或 ACK 失败 | 返回错误，不把内存接收当持久恢复 | `hold_failed` |

Worker 的 unknown 不是“只有日志然后丢弃”，也不是等待未来版本的无限重投；它已有持久审计供治理判断。附加 Hot-rank consumer 使用自己的过滤合同：同 topic 上其他事件直接 ACK，不走 Worker unknown recorder；无法解析或目标 handler 失败仍返回错误。

旧 `decode_nacked/nacked/nack_failed` 常量保留，不代表当前 SDK Worker/附加投影生成同名指标。SDK 负责实际 NACK，QS 的 `decode_failed/dispatch_failed` 记录进入 SDK 前的失败；不能由它们直接证明 Broker 的最终 REQ/FIN。

## 物理预算与失败审计

QS 默认及硬上限为每次 NSQ 物理消息最多 8 次业务 handler delivery，配置可下调；退避 30 秒起步、5 分钟封顶、20% jitter。重新 PUB 原应用消息会获得新物理 ID，物理次数不能替代原业务 attempt。

SDK 在真实来源 nsqd 准备失败消费者并向该节点的 `cb.failed.<hash>` topic 转交；这是当前兼容命名，不能因前缀仍为 cb 就推断执行器来自 component-base。

```text
业务 channel 达到 MaxAttempts
  → 发布 cb.failed.<hash> handoff topic，取得 PUB 确认
  → finish 原消息（FIN）
  → 独立 handoff consumer
  → MySQL FailedMessageHandler / recorder
  → event_delivery_dead_letter(manual_required) 持久提交
  → FIN 失败消息
```

handoff publish 失败/未知时原消息继续 requeue，但不再次调用业务 handler；只有 recorder 成功后才确认失败消息，recorder 失败时失败消息 requeue。两个 FIN 之间仍有 Broker 持久性窗口。第八次业务失败不是死信行已存在的证据。

QS recorder 保存原应用 UUID、原 NSQ 物理 ID、EventID、org、topic/channel、payload、attempts 和错误，以 `(provider, topic, channel, message_id, transport_message_id)` 保持物理失败幂等。新物理投递失败可形成新行；旧 handoff 缺物理 ID 时用空值保持历史去重。身份或组织/payload 冲突拒绝确认，已占用/终结的行不被重复中转覆盖。

迁移 `000086` 保留旧行，已有同 UUID 多次物理失败时拒绝丢失性降级。Worker 独立 recorder 使用配置的 Asia/Shanghai/+08:00；借用 API 连接池的 recorder 沿用该池时区。标准 Outbox 调度列则按 SDK UTC 时钟合同读取，不能混淆两种存储合同。

稳定 `FailedHandoffGroup` 只改变失败 topic 分组范围；旧中转水位与新 group 不会自动迁移。一般测评订阅留空按原 topic/channel 分组。通用中转算法和来源节点要求见[固定 SDK 文档](./10-架构与责任边界.md#sdk-版本与参考文档)。

## 主消费者与附加投影

`answersheet.submitted` 主 channel 调用 EnsureAssessment；`qs-apiserver-modelcatalog-hot-rank-v1` 独立处理 Hot-rank，使用 event ID Redis processed key。两者有独立消费进度、物理预算和失败审计，Redis 错误只影响投影 channel。独立投影不得放在 publisher hook 内。

幂等必须贴近副作用：Assessment 原业务关联、Evaluation run claim、报告业务键/claim/CAS、逐收件提醒账本各有不同边界。事件策略的唯一映射在[契约矩阵](./20-事件契约与演进.md)，业务窗口见[从事实到结算](./15-从事实到结算-失败窗口与状态机.md)。

report-status 写入/Signal 通知可失败后 ACK，attention 同步也存在记录后 ACK 的路径；幂等 overwrite 或重复投影不意味着本次已经写入。最终读取结果仍须核对业务事实。
