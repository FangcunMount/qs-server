# Event 架构与责任边界

EventSubsystem 装配宿主数据库、原业务根事务与进程生命周期；可靠消息库仍是嵌入式 SDK。当前生产路径使用 RocketMQ 事务 owner，通知使用 NORMAL。

## 责任与依赖方向

| 责任 | 所有者 |
| --- | --- |
| 授权、冻结业务输入、业务成功响应、模型与外部副作用 | QS application/domain |
| 原事务、CAS、业务证据、调度计划、Inbox、首次 ACK/正文档案 | QS 存储适配 |
| 冻结计划、并发执行资格、witness、三阶段结果、精确回查 | reliable-messaging 事务 SDK |
| 准入、启动/关闭、连接池、owner 与 Topic 配置 | QS process/EventSubsystem |
| 消费幂等、未来重试、人工授权和结果未知治理 | QS 业务/worker |

## 两条发布链

可靠事件：冻结计划 → 全部分支半消息明确成功 → 原业务事务先绑定 guard → 业务/证据/witness 同根提交 → Broker 确认。MQ 不可用或准备未知时不启动业务；提交未知须查精确证据，不能新建事件或重做模型。

尽力通知：当前 NORMAL WirePublisher → 独立 NORMAL Topic。它不接受事务分支，也不提供持久业务重试。Redis Pub/Sub 仍只承担可丢的唤醒。

## 契约与两个 Profile

`mongo_domain_events`、`assessment_mysql_events` 是保留的领域目录分类，分别由原 Mongo/MySQL owner 承接。目录 `durable_outbox` 这个分类名不表示当前仍写发布队列。事件值、payload、逻辑订阅和消费结算政策继续由 QS 定义，见 [事件矩阵](./20-事件契约与演进.md)。

## 唯一装配与生命周期

`configuredEventSubsystem` 只进入 `NewWithTransactionOwners`，要求两个原数据库、显式 RocketMQ、两个原 owner 及独立 NORMAL 客户端。未提供当前 owner 不会降级到旧 Relay、NSQ 或 gRPC 写入。

owner 记录完整事务 Topic，即使空闲也运行 Checker。关闭先封新准入、等待真实在途、保留回查并排空，再关闭所属客户端；超时返回未完成状态，不能提前关闭宿主数据库。三个 worker 的逻辑订阅共享原并发预算。

## 消费、Signal 与业务效果

Broker 确认和 delivery ACK 都不证明报告、提醒或模型已完成。消费者仍需幂等；原 Run、Outcome、Generation、任务收件账本、AI response/checkpoint/artifact 与授权恢复规则不因消息清理而删除。

## SDK 版本与参考文档

当前固定 Go SDK 为 `v0.6.1`，源码 `48dfcdafbf29b44e99a5ac8b1ae01e5173138560`，不使用本地 replace。当前事务契约见固定版本的 [transaction](https://github.com/FangcunMount/reliable-messaging/tree/v0.6.1/transaction)、[MySQL 事务存储](https://github.com/FangcunMount/reliable-messaging/tree/v0.6.1/storage/transaction/mysql)、[Mongo 事务存储](https://github.com/FangcunMount/reliable-messaging/tree/v0.6.1/storage/transaction/mongo) 和 [RocketMQ 运输](https://github.com/FangcunMount/reliable-messaging/tree/v0.6.1/transport/rocketmq)。

旧 Outbox/Relay/NSQ 的 SDK 兼容包及隔离合同可以继续存在，但不再是最终生产接入契约。源码依赖、已发布 tag、镜像和实际运行分别验证，不因文档更新宣称生产升级。
