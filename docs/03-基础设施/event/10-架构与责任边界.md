# Event 架构与责任边界

EventSubsystem 是 QS 的宿主装配边界；`reliable-messaging` 是嵌入式 SDK。独立的是代码与版本发布，业务事务、数据库、业务许可和服务生命周期仍由 QS 管理。

## 责任与依赖方向

| 责任 | 所有者与入口 |
| --- | --- |
| 业务事件值、payload、owner、组织范围、路由、幂等与结算政策 | QS `internal/pkg/event`、`internal/pkg/eventing/{payload,outcome,catalog}` |
| 通用消息身份、不可变 bytes/指纹、领域及历史 wire codec | SDK `message`、`wire/domain`、`wire/legacy` |
| 原事务选择、提交/回滚及业务成功响应 | QS application、事务 runner；Mongo/MySQL Stager 绑定这笔原事务 |
| 标准追加、Store claim、数据库时钟、租约与条件结算 | SDK `storage/{mongo,mysql}`、`outbox` |
| 发现、并发发送、运输结果和 NSQ 物理重投/失败中转 | SDK `relay`、`transport/nsq`；QS 提供技术预算、拓扑与监督 |
| consumer 业务效果、retry hold、持久失败审计、人工恢复授权 | QS Worker、各业务 application 和 system governance |
| 效果缺口判断、原消息恢复许可与回退准备 | QS `answersheetgap`、原效果恢复、业务治理及运维 |
| 进程启动、取消、等待、drain、数据库资源所有权 | QS process、EventSubsystem、RelaySupervisor；SDK ManagedPublisher 明确持有专用 NSQ Producer |

业务模块只依赖事件值及 `ProfileBinding` 的 Stager/PostCommit 窄端口，不构造 SDK Store、Relay 或 Broker client。库不定义“报告已完成”“允许再调用模型”或“可再次提醒某收件人”。

## 两条发布链

```text
durable：QS 原事务 → Stager → SDK Appender → rm_outbox
          commit → PostCommitWake → 受 QS 监督的 SDK Relay → SDK Publisher

best-effort：QS 生命周期后置动作 → RoutingPublisher
              → SDK wire/domain + wire/legacy → WirePublisher
```

Durable wire 在暂存前首次编码，并以原事件 ID、原 bytes 保存。Relay 复用原意图，不重新产生业务事件。业务事实在哪个数据库，Outbox 就在哪个数据库；不存在中央消息库或 Mongo/MySQL 分布式事务。

## 取舍与重新决策条件

答卷已受理却未创建测评，或 outcome 已提交却未生成报告，都会留下跨库业务缺口。因此这类事实在原事务暂存意图：直接在 commit 前后 PUB 都会留下数据库与 Broker 的双写窗口，移到中央消息库也不能获得原事务原子性。更换普通 Broker 适配器同样不关闭这个窗口；事务消息需要独立的宿主状态检查与迁移合同，当前未采用。

接受的代价是业务库承担意图、索引与扫描写入，PUB/Confirm 窗口允许重复，published 后还须由宿主核对效果。周期扫描换取 Wake 丢失后的活性，不承诺每条事件立即发送或按旧 priority 排序；纯缓存提示和允许丢失的外部通知继续用 Signal/best-effort，避免替它们扩大持久责任。

只有实际 oldest age、扫描负载、业务期限或必要效果证据显示现有边界不再满足需求时，才重新评估扫描预算、独立 Relay 部署或 Broker 协议。先保留原事务、身份、回退和未知结果规则，再定义隔离容量与故障验证；库抽出本身不是这些重新设计的许可。

## 契约与两个 Profile

`configs/events.yaml` 与 QS EventSpec 合并为 EffectiveRegistry。YAML 保留 topic、delivery、主 handler 等 wire 清单；EventSpec 保存工程策略，Registry 校验事件集合、业务 owner 和策略。主 handler/binding 还由消费装配校验，不能只凭 Registry 存在推断接线完成。

| Profile | 权威存储 | 当前用途 |
| --- | --- | --- |
| `mongo_domain_events` | Mongo `rm_outbox` | 答卷提交，报告生成/失败，Interpretation 重试授权 |
| `assessment_mysql_events` | MySQL `rm_outbox` | Evaluation 请求/结果/失败/重试，以及启用后的 Task 开放提醒意图 |

事件明细只在[事件契约矩阵](./20-事件契约与演进.md)维护。`immediate/priority` 是保留兼容字段；当前 SDK 不按旧 priority tier claim，也不构造旧 ImmediateDispatcher 或 Redis ready-index。

## 唯一装配与生命周期

apiserver resource bootstrap 构造一次 EventSubsystem，Container 使用同一实例派生 `Publisher()`、`Profile()`、附加 consumer binding、status 与 Outboxes。标准装配入口为 `process/standard_event_subsystem_m4.go`。

每个已提供宿主数据库都必须有完整标准 Profile。缺配置、存储预检失败、NSQ 配置不完整或非 MQ-backed 模式均启动失败；标准 Profile 不以 logging/nop 运行 pending-only 链路，也不自动回退旧 writer。RoutingPublisher 自身仍有 logging/nop 供直接发布与独立测试使用。

Start 在完成装配后执行：先冻结/校验附加 consumer binding，再按 ID 启动 consumer，最后按 Mongo、MySQL 顺序启动 Profile Supervisor。部分启动失败会清理已启动资源。

Close 先取消并等待 Profile Run 退出，再 drain 标准 Publisher，最后逆序停止/关闭附加 subscribers；错误汇总，重复或并发 Close 复用同一次清理。SDK 的真实发送可能晚于调用者 deadline 返回，因此 drain 必须等待实际发送退出。宿主数据库与借用的 Redis 连接由外层资源 owner 关闭。

## 消费、Signal 与业务效果

Worker 按 YAML 显式 handler registry 消费主 channel；当前唯一附加 consumer 为 `modelcatalog.hot_rank_projection`。它与 Worker 使用相同 topic、不同 channel，Redis 故障只影响投影消费。具体 ACK、unknown 持久审计及 hold 边界见[消费与结算](./40-MQ发布消费与结算.md)。

Signal 不进入 EventSubsystem。通用 Redis transport 归 SDK，业务 Signal 与 watcher/TTL/权威回读归 QS CacheSubsystem 或 report-status runtime，见[Signal](./60-Signal一次性信令.md)。

发送结算、消费结算与业务完成分别成立；标准 Store 不自动重扫 `published`。QS 必须核对答卷→Assessment 等业务效果缺口，不能把效果扫描和恢复授权整体搬进 SDK。现有 scanner 尚未接入生产调度/API，范围与证据限制见[Outbox 与业务效果恢复](./30-Outbox可靠出站链路.md)。
