# Event 可观测性与故障恢复

排障先定位责任：原事务、标准 Outbox 发送、某 channel 消费、持久失败记录或最终业务效果。配置、当前进程 snapshot、时序指标和单条业务事实分别提供证据，不能互相补成完成。

## 当前指标接线

| 指标 | Labels | 当前证据范围 |
| --- | --- | --- |
| `qs_event_publish_total` | source,mode,topic,event_type,outcome | RoutingPublisher 直接发布；不是标准 Relay 的发送计数 |
| `qs_event_outbox_total` | relay,topic,event_type,outcome | 标准 SDK Store/Publisher 的 QS 薄观测包装 |
| `qs_event_consume_total` | service,topic,event_type,outcome | QS Worker/附加消费者的处理和显式 ACK 请求结果 |
| `qs_event_consume_duration_seconds` | service,topic,event_type,outcome | Worker dispatch 到本地结算返回的耗时；不覆盖所有消费运行时 |
| `qs_event_outbox_backlog` / `qs_event_outbox_oldest_age_seconds` | store,status | SDK 标准未完成状态的数量与最老 created_at 年龄 |
| `qs_event_outbox_backlog_by_type` / `qs_event_outbox_oldest_age_by_type_seconds` | store,event_type,status | 支持 per-type reader 的 Profile；当前标准 Mongo 支持，MySQL 不提供该接口 |
| `qs_event_outbox_status_scrape_total` | store,outcome | 宿主 status reader 的读取成功/失败 |

### 直接发布

RoutingPublisher outcomes 为 `mq_published/mq_failed/encode_failed/unknown_event/fallback_logged/logged/nop`。logged/nop/fallback 不证明 Broker 接受；标准 Outbox 配置无法在这些模式下启动。

### 标准 Outbox

`ObserveRelayDelivery` 包装实际 SDK Store/Publisher，不改变它们的返回值、原消息或错误：

| outcome | 真实触发点 | 不能推出 |
| --- | --- | --- |
| `claim_failed` | Store.ClaimDue 返回错误；topic/event_type 为空，因为没有已知单条消息 | 某特定事件已发送失败 |
| `publish_failed` | Publisher 返回非 Confirmed（包括 Unknown/Rejected） | 没有发送、消费者业务失败或可重新执行外部调用 |
| `published` | Store.Confirm 返回成功 | 消费完成、同步落盘、报告生成 |
| `mark_published_failed` | Store.Confirm 返回错误，含失效 claim | 数据库一定未更新；应回查原状态 |
| `mark_failed_failed` | Store.Retry/Quarantine 返回错误 | 已丢事件或业务 run 失败 |

labels 从真实 Message/Claim 取 destination/event_type，relay 为宿主 Profile 名。成功 PUB 不提前计 published；没有旧 ImmediateDispatcher，因此不产生 `immediate_skipped`。观测桥也不把技术领取次数伪装成业务 attempt。

SDK Relay observer 的 scan 事件用于 Supervisor `scan_healthy/last_failure_kind`，它本身没有 Message 身份，不能发明 event type 标签。历史部署若未接入本桥，缺少样本不能解释为零失败；本轮源码修复也不证明现场已更新。

### 消费与外部副作用

当前 Worker/投影失败入口产生 `decode_failed/dispatch_failed`；显式结算产生 `acked/ack_failed`。Worker unknown 审计与 ACK 为 `unknown_persist_failed/unknown_acked/unknown_ack_failed`；hold 为 `held/hold_failed`，hold replayer 为 `hold_replayed/hold_replay_failed`。旧 decode_nacked/nacked/nack_failed 常量不代表当前 SDK 主链仍生成相应样本，精确结算见[消费与结算](./40-MQ发布消费与结算.md)。

SDK 自动 NACK 与失败中转没有完整的 QS handoff 成功/失败/lag counter。NACK 型处理错误停止增长而死信未出现，仍可能停在来源节点中转、失败 consumer 或 MySQL recorder。`transport_terminal` 是保留的观测 outcome，不能据它推断当前领域 Event recorder 已持久化。

`qs_worker_best_effort_side_effect_total{event_type,result}` 与 `qs_worker_best_effort_side_effect_last_failure_timestamp_seconds{event_type,result}` 已在当前源码接入五条流：questionnaire.changed、assessment_model.changed、task.completed/expired/canceled。result 为 `call_succeeded/call_failed/response_rejected/not_configured`，首次失败可由 timestamp 观察。

handler 可在外部调用失败后 ACK。call_succeeded 只说明调用未报错，不代表最终收件；call_failed 可包含结果未知，须核对外部状态后决策。缺网关/Webhook 地址时记 not_configured，不能把 no-op 当成功。非量表模型不触发二维码后处理，missed_open_window 抑制仍是业务规则。新的 task.opened.reminder.requested 使用独立持久账本，不在这五流指标内。

## 状态接口与证据边界

`GET /internal/v1/events/status` 只读 EventSubsystem，保留 catalog/outboxes，并输出 events/profiles/consumers。标准 Profile snapshot 读取 SDK `pending/retry_wait/publishing/quarantined`，失败读取必须呈现退化，不能当作零积压。

Profile 的 running/scan_healthy 是当前 Supervisor 状态；兼容的 immediate/reconciler 字段不代表旧运行时存在。附加 consumer status 只覆盖 apiserver 管理的投影，Worker 主 channel 要结合 Worker 指标、日志及 NSQ 拓扑。

`GET /internal/v1/system-governance/events?window=5m` 聚合 snapshot、Prometheus 窗口、Signal 清单及当前组织的业务失败/Outbox/hold/dead letter。缺数据必须保留证据缺口。页面渲染属于 qs-operating-system 独立版本，后端 JSON 和本仓测试不证明前端现场兼容。

qs-operating-system 的页面路由、重定向与渲染行为是跨仓事实，不在本文档的 exact-SHA closure 内。跨仓验收须另行绑定 qs-operating-system 的独立 exact SHA、实际部署版本与页面证据。

## 恢复层次与许可

| 持久责任 | 入口 | 边界 |
| --- | --- | --- |
| Outbox/hold 待授权 | `events.replay_pending` | 比较组织、原身份、attempt/disposition；不是直接调用业务 handler |
| 某 channel 持久死信 | `events.replay_delivery` | 一次受控发布原事件；不改 poison payload，不提供无限重放 |
| published 后效果缺失 | QS 业务效果扫描与原身份恢复 | 按冻结业务事实核对并授权，SDK 不自动重扫 published |
| 报告生成重放结果未知且效果已核实 | 独立 delivery-resolutions | 核实后同事务结案，不再次投递 |

四种 attempt 的 owner、预算和持久状态不同，见[业务失败窗口](./15-从事实到结算-失败窗口与状态机.md#四类预算不是一个总重试数)。quarantined 的人工/terminal 投影见[标准状态](./30-Outbox可靠出站链路.md#标准状态与-qs-治理投影)，不能沿用旧 failed 状态查询。

### Transport replay

每次最多 100 个 target，整批预检组织、manual_required 与 expected_delivery_attempts，逐项再次占用校验。中途失败不撤销前面已投递行；后续未处理行保持原状态。

发布或完成结果未知时，保留占用及 replay_request_id 并列为待核对候选。原 action 已 failed/timeout 也不能证明没有效果，不能换新请求编号试探。先按原 EventID、物理死信 ID、原操作审计和业务事实核对。

通用重放拒绝 questionnaire.changed、assessment_model.changed 与旧 task.opened/completed/expired/canceled 六条 best-effort 事件，因其外部副作用没有统一持久去重/回执保证。Task 持久提醒仍按独立收件账本与期限处理。非法 canonical payload 无法靠 replay 修复，应修 producer/contract 并独立决定数据处置。

### 报告事实核实结案

delivery-resolutions 只接受 interpretation.report.generated。输入绑定新的稳定结案请求编号、原重放编号、物理死信、原 EventID、预期次数、原因与确认；锁定原审计/死信并核实同一测评、当前报告、参与者可读结果和关注事实后，将结案审计与 resolved_verified 同一 MySQL 事务提交。

原审计仍 running、死信占用不符、其他事件或证据不全均拒绝。接口不经普通 ActionExecutor 的分步发布路径。响应未知先按相同结案请求编号查回执或重试原输入；暂时查不到回执不证明原事务未提交。代码/测试存在不代表真实样本与 operator 权限已现场验收。

## 症状到责任路径

| 现象 | 检查 |
| --- | --- |
| backlog/age 持续增加 | 标准 Profile 配置、Supervisor scan 健康、实际 Store 状态、publish/写回计数与 NSQ |
| mark_published_failed 增长 | 原行 state/token/version、数据库错误与重复消费；不假定更新未提交 |
| unknown_persist_failed 增长 | MySQL 审计与原消息身份；不能跳过审计 ACK |
| unknown_acked 增长 | producer/consumer 版本、YAML/handler、持久 unknown 行 |
| decode_failed/dispatch_failed 增长 | 原 payload、handler 错误、SDK/来源节点重投与中转 |
| handler 预算耗尽但无死信 | 来源 nsqd 的 cb.failed topic/channel、失败 consumer、recorder 日志与 MySQL |
| held 或 hold_replay_failed 增长 | retry 开关、retry_event_hold、原 ID、next_attempt_at 与预算 |
| Outbox published 但无 Assessment | [答卷效果扫描](./30-Outbox可靠出站链路.md#published-后的业务效果由-qs-核对)，不查旧 ready-index |
| ACK 后状态仍未刷新 | 权威报告/attention、report-status Redis 及 Signal；ACK 不证明后置写入 |
| replay 待核对增加 | 原 action/物理行占用、业务效果及回执；禁止仅凭超时重发 |

告警以 oldest age、持续趋势、读取退化和版本错位为主，具体阈值与 PromQL 归部署配置。单条诊断串联原 EventID、aggregate/业务关联、topic/channel、Profile、物理 ID 和 action request ID；这些高基数字段放日志/审计，不放指标 label。

## 验证与剩余现场证据

普通测试、实库/真实 Broker 故障测试见[扩展与验收](./70-扩展与验收.md)。当前真实缺口包括：SDK NACK/失败中转各阶段的完整 QS handoff 指标，以及答卷效果 scanner 的生产调度/API/授权装配。目标环境仍须绑定部署 SHA、effective config、NSQ 来源节点、MySQL/Mongo 与 scrape 窗口，分别证明持久事务、失败中转、效果恢复和人工权限。新增观测桥通过本地回归也不能补成这些现场结论。
