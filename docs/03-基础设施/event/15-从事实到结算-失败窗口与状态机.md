# 从事实到结算：QS 业务失败窗口

QS 用本地事务保存业务事实和出站意图，用消费幂等连接不同数据库的事实。SDK 负责运输和调度，QS 负责证明答卷、测评、报告或提醒究竟完成到哪里。本篇沿实际业务链分析，不再复制 SDK Store 或 Broker 的通用状态机。

## 完成点必须带上责任对象

| 完成点 | 直接证据 | 仍未证明 |
| --- | --- | --- |
| 答卷受理 | Mongo 同一原事务保存 AnswerSheet、提交证据和原 Outbox | Assessment 已建立 |
| 原事件发送结算 | `rm_outbox.published`，对应有效 claim 的 PUB 确认已写回 | 某消费者收到或业务效果存在 |
| Assessment 接入 | API 按原 AnswerSheet 关联创建/复用测评并推进接入 | Evaluation/Report 完成 |
| 某 channel 消费结算 | 当前 handler 持久责任完成或转交 hold 后 ACK | 其他 channel 完成，所有后置投影成功 |
| 报告等最终业务效果 | 对应业务权威结果、可读投影与原执行/回执 | 任意外部收件人必达 |

`202` 只承诺答卷与 Outbox 已持久受理。PUB、FIN、业务接单与最终效果不能互换。Consumer 可以在生产者尚未成功写回 `published` 时开始处理，两端没有共同结算事务。

## 答卷到测评

```text
collection AcceptDurably
  → API 原 Mongo 事务：AnswerSheet + SDK Outbox
  → commit / 202
  → PostCommitWake 或周期扫描
  → NSQ 投递 answersheet.submitted
  → Worker 请求 EnsureAssessment
  → API 按 answer_sheet_id 在 MySQL 创建/复用及补提交
  → Worker ACK
```

| 失败窗口 | QS 如何保持责任 |
| --- | --- |
| 原事务回滚 | 答卷与意图不共同成立；不能承认 202 |
| Mongo commit 响应未知 | 按原提交 key/指纹只读回查，实际查到 durable 结果才承认成功 |
| 提交后 Wake 丢失或进程退出 | SDK 周期扫描原 Outbox；Wake 本身不 claim 或 publish |
| PUB 未确认、状态写回失败或 claim owner 退出 | 依据原意图、宿主 RetryPolicy 与 SDK 租约恢复；原 ID/bytes 不变 |
| MySQL 已接入但 gRPC 响应或 FIN 丢失 | EnsureAssessment 按原业务关联复用；Redis 抑制只减少重复工作 |
| 原 Outbox 已 published，但没有 Assessment | QS 效果扫描核对原答卷、冻结准入和关联，形成受控恢复证据；不会被普通 pending 扫描自动发现 |

Mongo 答卷与 MySQL 测评是各自的本地事务；创建已有 pending Assessment 与补提交也可分步持久化。技术重投不得重新生成事件身份或绕过原业务关联。实际恢复边界见[Outbox 与业务效果恢复](./30-Outbox可靠出站链路.md)。

## Evaluation 到报告与参与者读取

Evaluation 请求、失败/重试授权与 outcome 意图在 MySQL 事务保存；报告生成/失败/重试授权在 Mongo 原事务保存。消费端使用 run state claim、报告业务唯一键和 CAS，而非一个宣称全局 exactly-once 的 ledger。

report-status Redis/Signal 是后置读模型和唤醒：`evaluation.failed`、`interpretation.report.generated/failed` 可在 Redis 写入或通知失败时最终 ACK。报告生成后的 attention 同步错误也可被记录后 ACK。因此报告事实、参与者可读结果、attention、Redis 状态与唤醒分别核对；ACK 不能补齐缺失投影的证据。

如果报告生成死信重放结果未知，现有事实核实结案仅针对 `interpretation.report.generated`：核对原重放审计、物理死信和对应测评/报告/参与者读取/关注事实后，结案审计与 `resolved_verified` 同事务提交，不再次投递。完整恢复入口见[故障恢复](./50-可观测性与故障恢复.md)。

## Task 提醒是独立外部副作用

旧 `task.opened/completed/expired/canceled` 为 best-effort 通知。新的 `task.opened.reminder.requested` 在启用后与 Task 开放事实同 MySQL 事务形成意图；逐收件账本、SELF 收件人、有效期、完成/取消抑制与微信结果未知都是 Plan 产品合同。

这些规则不归通用 SDK，也不能靠同一 event ID 或新 NSQ 物理 ID 自动许可再发送。详见[任务调度、入口与提醒](../../02-业务模块/60-plan/23-核心设计-任务调度、入口与提醒.md)。

## 四类预算不是一个总重试数

| 层 | 动作与 owner | 当前默认/硬上限 | 结束后 |
| --- | --- | ---: | --- |
| Evaluation / Interpretation | QS 再执行一次业务 run | 3 | 业务 manual_required 或 terminal |
| 标准 Outbox | SDK 投递原意图，QS RetryPolicy 决定预算 | 30 | `quarantined`；QS 按错误与原事实投影治理处置 |
| Retry hold | Worker 重新发布暂停期间持久保存的 retry event | 30 | `retry_event_hold.manual_required` |
| NSQ 物理投递 | SDK 再调用某 channel handler | 8 | 失败中转；QS recorder 成功后才有死信行 |

Outbox `attempt_count` 在领取时增加，`failure_count` 在有效 Retry/Quarantine 等失败结算时增加；租约回收不是一次新的业务执行授权。物理消息重新 PUB 会取得新 NSQ ID，物理次数不能限定原业务总次数。

automatic business retry 暂停时，Worker 必须持久保存 hold 后 ACK；保存失败返回错误，由 SDK NACK。恢复后 hold replayer 继续原 UUID/event ID，不重新生成业务意图。

## 重复必须由最靠近业务事实的约束裁决

| 副作用 | QS 当前幂等依据 |
| --- | --- |
| 创建/接入 Assessment | 原 AnswerSheet 关联、业务唯一键、ensure |
| 推进 Evaluation | run state claim 与原授权 |
| 生成报告 | report 业务键、run claim、CAS |
| Hot-rank | 独立 channel，event ID Redis processed key；投影可重建 |
| 覆盖 report-status | 业务键上的状态投影合同，写入/Signal 仍可降级 |
| 主动提醒 | 逐收件持久账本和有效期，未知外部结果核对 |

PUB 确认丢失、发送写回失败、FIN 丢失和人工重放都可能产生重复。统一 ledger 只有与副作用原子提交或外部稳定幂等 key 配合才闭合窗口；不能据其存在推导 exactly-once。

## 新需求的审查顺序

1. 明确业务事实和丢失损失，选择 durable、best-effort 或 Signal。
2. 列出原事务、发送结算、消费者持久处理、各投影/外部效果的证据。
3. 明确重复、未知提交、未知外部调用与已发布效果缺口分别由谁处理。
4. 为每个副作用选择唯一键、claim、CAS、原回执或专属账本。
5. 分别定义业务、Outbox、hold、物理 delivery 的预算和授权边界。
6. 核对可观测性、原身份保留、人工恢复及真实停止/回退证据。
