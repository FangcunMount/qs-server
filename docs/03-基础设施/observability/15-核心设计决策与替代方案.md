# Observability 核心设计决策与替代方案

可观测性不是“多打日志”或“给每个函数加指标”。它要让工程师在未知故障中回答：影响范围多大、请求或事件走到哪一步、权威事实停在哪里、当前看到的是零还是数据源不可用，以及采取恢复动作会不会制造第二次副作用。

## 1. 决策总览

| 决策 | 当前选择 | 主要替代方案 | 核心理由 |
| --- | --- | --- | --- |
| 证据模型 | logs + metrics + runtime snapshot + durable evidence | 只依赖日志/APM | 四者时间尺度和证明能力不同，必须交叉验证 |
| 关联标识 | request/event/business/idempotency/action ID 分工 | 用一个 trace ID 贯穿全部语义 | 技术调用、消息、业务意图和持久实体生命周期不同 |
| tracing 状态 | 只承认日志 ID 传播；不宣称全链 OTel | 把任意 trace_id 当 span | 避免配置名或字段名造成能力误报 |
| metrics label | 仅有限枚举 | 把用户/业务 ID 放 label | 控制时序基数与监控成本 |
| probe 分层 | liveness/readiness/synchronization/deep check 分工 | 一个 `/health` 检查所有依赖 | 避免重启风暴，也避免把浅检查误作业务健康 |
| unknown 建模 | unavailable 与 zero 分开 | 查询失败时返回 0/healthy | 缺证据不能变成正面证据 |
| 异步诊断 | Event/Outbox/hold/dead-letter + 业务状态 | 只看 consumer 日志 | 日志会丢，可靠恢复必须依赖持久状态 |
| 日志隐私 | 稳定 ID/分类/阶段，禁止敏感 payload | 全量 body 便于排障 | 当前默认 body 日志已构成风险，便利性不能覆盖隐私成本 |
| 运维端点 | 依赖网络边界，目标是受限管理面 | 直接公开在业务监听面 | metrics/pprof/governance 不受普通业务 JWT 自动保护 |

## 2. 决策一：使用四个证据平面，而不是寻找“唯一真相面板”

### 四类证据的分工

- **Logs**：解释某一次执行走过哪些分支，保留错误上下文。
- **Metrics**：显示一段时间内的比例、分布、并发和趋势。
- **Runtime snapshot**：解释当前实例如何装配、哪些 family/能力处于 degraded。
- **Durable evidence**：回答业务事实、Outbox、claim、checkpoint、retry/dead-letter 的持久状态。

### 为什么必须组合

`consume nack` 指标上升不能证明事件丢失；某条日志说 publish success 也不能证明 consumer 已完成；Outbox row 为 sent 不能证明最终业务状态已经推进。不同证据回答不同层次的问题。

推荐诊断序列：

```text
告警/用户症状
   ↓ metrics 定范围和拐点
runtime snapshot 确认装配/降级
   ↓ logs 定具体分支和错误类别
durable state 定事实位置与恢复动作
```

### 替代方案

- **日志中心作为唯一入口**：适合单次错误，但难做精确比例、尾延迟和长期趋势；日志丢失也不能恢复事实。
- **APM trace 作为唯一入口**：适合调用拓扑，采样后不保证每个业务实体都有记录，也不保存权威状态。
- **数据库查询作为唯一入口**：能看 durable state，看不到瞬时资源饱和、排队和未提交失败。

面板是证据的导航，不是第五种事实源。

## 3. 决策二：不同 ID 表达不同生命周期

### 当前模型

| ID | 回答的问题 |
| --- | --- |
| `request_id` | 这次同步 HTTP/gRPC 调用发生了什么？ |
| `event_id` | 这份 Event envelope 如何发布、投递和结算？ |
| 业务 ID | 这份 AnswerSheet/Assessment/Run/Report 的生命周期是什么？ |
| `idempotency_key` | 多次请求是否表达同一业务意图？ |
| `action_request_id` | 高风险人工动作是否已经执行或可回放？ |

### 为什么不能统一成一个 ID

一个业务实体会经历多次请求和多个事件；一次请求可能涉及多个业务实体；网络重试会产生新 request，却仍是同一 idempotency intent。把它们合成一个 ID 会丢失关系，而不是减少复杂度。

合理做法是在日志/持久事实中同时保留相关 ID，并明确父子关系。Prometheus 不能用这些高基数 ID 做 label。

### 当前边界

入站 `X-Request-ID` 可由调用方提供，当前没有格式/长度约束。因此它是关联数据，不是可信身份、授权依据或无界 label；边界代理和 middleware 应限制大小与字符集。

## 4. 决策三：日志相关性不等于分布式追踪

当前 HTTP/gRPC/Event 链路会生成和传播 request/trace/event ID，但 repo 中未发现三个进程统一初始化 OpenTelemetry `TracerProvider`、exporter、HTTP/gRPC/MQ instrumentation 和 collector pipeline。`iam.enable-tracing` 作用于 IAM SDK，不能扩展解释成 qs-server 全链 tracing。

### 为什么坚持这一区分

真正的 span 至少包含：parent/child context、时间边界、status、attributes、sampling 和 exporter；一个名为 `trace_id` 的日志字段只提供关联。

### 替代方案

- **只保留结构化日志关联**：实现和成本低，适合当前基础；跨异步拓扑、临界路径和采样分析较弱。
- **全链 OpenTelemetry**：诊断能力更强，但要设计采样、PII、tail-based sampling、collector 容量和 MQ context 传播。
- **Vendor APM 自动注入**：上线快，但隐式 instrumentation、成本和可移植性需评估。

如果后续落地 OTel，必须把 Outbox stage、MQ publish/consume 和业务 ID 关系纳入设计；仅 instrument HTTP 不能解释异步链路。

## 5. 决策四：Prometheus label 只使用有限枚举

### 为什么高基数危险

每一组独特 label 值都会创建时间序列。把 request/user/event/business ID、raw URL 或错误原文放进 label，会让时序数量随流量增长，导致内存、存储和查询成本失控。

### 当前策略

使用 component、family、operation、topic、event_type、outcome、strategy 等有界字段。高基数上下文放结构化日志或持久审计。

### 替代方案与补充

- Exemplars 可把少量 histogram 样本关联到 trace，但前提是先有真正的 trace pipeline。
- 日志派生指标可用于临时分析，但仍需控制字段和值域。
- Top-K/采样可分析热点业务键，但不应把任意输入变成长期 Prometheus label。

指标评审必须要求列出 label 的理论值域和最坏时序数；“当前数据里不多”不是基数上界。

## 6. 决策五：Probe 按用途分层

### 四种问题

1. **Liveness**：进程是否卡死到需要重启？
2. **Startup/synchronization**：首次策略、缓存或控制面同步是否完成？
3. **Readiness**：当前实例是否应继续接收某类流量？
4. **Deep health/synthetic**：完整依赖和业务路径能否工作？

### 为什么不能用一个 endpoint

如果 liveness ping 所有数据库和 IAM，依赖短暂故障会触发所有实例重启，放大事故。如果 readiness 只返回进程存活，却命名为“ready”，负载均衡会继续把无法兑现的流量送入实例。

### 当前实现与限制

- apiserver `/health` 和 Generic `/healthz` 是浅 liveness。
- apiserver `/readyz` 只表达 Redis runtime；status service 缺失/报错还会 fallback ready。
- collection `/readyz` 表达 Redis + 首次 resilience control sync；`/serve-readyz` 只要求 control sync，允许 Redis degraded 后继续服务。
- worker `/readyz` 主要表达 Redis，不证明 MQ subscription、gRPC 和 handler 健康。

这些语义是部署契约，不能因为 endpoint 名称相同就统一解释。

### 替代方案

- 每种流量独立 readiness：最精确，但 endpoint/路由和部署配置更复杂。
- 聚合 readiness：简单，但一个非核心依赖可能摘除全部流量。
- synthetic transaction：证明力强、成本高，应低频运行并隔离测试数据。

合理目标是浅 liveness、明确 startup gate、按核心承诺划分 readiness，再用受保护 deep check/synthetic 提供诊断。

## 7. 决策六：Unknown、Unavailable、Zero 必须分开

Prometheus 查询超时、远程 component 不可达、status provider 为 nil，都表示“没有证据”，不是“值为 0”或“健康”。

当前 System Governance 对远程/Prometheus 证据保留 `available=false`、partial 和 error reason，这个方向是正确的；apiserver readiness provider 异常时回退 `Ready=true` 则是需要整改的反例。

可选状态至少应包含：

- configured / not_configured；
- initializing / synchronized；
- available / unavailable / partial；
- healthy / degraded / failed；
- observed_at / stale_after。

替代的布尔值模型简单，但会把“没装配”“查不到”“确认为空”压成同一结果，导致自动化做出危险决策。

## 8. 决策七：异步链路以持久状态作为恢复依据

### 当前证据链

```text
business fact + Outbox
       ↓ relay state / backlog / oldest age
MQ attempt + settlement
       ↓ retry hold / dead letter / manual_required
business checkpoint / claim / terminal state
```

metrics 用于发现趋势，日志用于解释失败，但 replay/force/release 必须基于 Outbox、dead letter、retry hold、checkpoint 和目标业务状态。

### 为什么不靠日志重放

日志可能采样、丢失、重复、延迟或被脱敏；它不是具备唯一键和状态机的命令存储。从日志提取 payload 再发布无法证明原事件契约、当前目标状态和是否已执行副作用。

替代方案是完整 Event Sourcing：所有业务状态由事件日志重建，证明力强但会彻底改变当前领域持久化模型。qs-server 当前是 state store + durable integration event，不应混称 Event Sourcing。

## 9. 决策八：日志可诊断性必须服从隐私边界

### 当前风险

collection-server 显式安装 `APILogger()`；默认记录 request/response headers 和最多 16 KiB body。通用字段名脱敏无法识别 AnswerSheet answers、报告正文、姓名等领域敏感数据。

JWT middleware 在 Debug 级还会记录 verifier result、raw/mapped claims；worker production YAML 当前又配置 debug/console/development/color。这些都应保留为风险，不应解释为“方便排障所以合理”。

### 目标选择

- 生产默认不记录 body。
- 按 route allowlist、有限字段和短期采样开启诊断。
- 记录稳定 ID、阶段、耗时、错误分类和 payload size/hash，不记录完整内容。
- 敏感调试走受控审计、短保留、严格权限，不进入普通应用日志。

替代的全量 body logging 虽能缩短一次排障，却增加数据泄露、合规、索引成本和二次传播风险，长期不可接受。

## 10. 决策九：运维端点需要独立安全边界

metrics、pprof、Redis/resilience governance 会泄露内部拓扑、容量、状态和性能信息。它们通常不经过业务 JWT middleware。

可选部署方式：

1. 独立 loopback/management port，由 sidecar 或 agent scrape。
2. 独立管理网段 + mTLS/network policy。
3. 与业务端口共存，但由反向代理精确 ACL；配置最省，误暴露风险最高。

当前 apiserver/collection/worker 的暴露方式不统一，生产验收必须查看真实 listener 和网络策略，不能只读 route code。

## 11. 告警与 SLO 的取舍

collector 丰富不等于可运维。一个有效告警至少要有：

- 用户/业务影响的 SLI；
- 时间窗口和持续条件；
- 候选原因的辅助指标；
- owner、严重级别和 runbook；
- 恢复条件，避免抖动；
- unknown/source unavailable 的单独处理。

不应对每个 error counter 的单次增长告警。Event/Outbox 更适合 backlog、oldest age、terminal failure rate；Backpressure 更适合 timeout rate + in-flight/wait + dependency latency；缓存更适合 hit/miss 与 DB 放大联合观察。

## 12. 评审新观测点的顺序

1. 它支持哪个具体决策或故障问题？
2. 需要聚合趋势、单次上下文、当前装配还是持久恢复证据？
3. 关联 ID 分别是什么，是否错误地把高基数 ID 放进 label？
4. source unavailable 如何表示？多久后算 stale？
5. 是否包含 token、答案、报告、身份 claims 或资源 URL？
6. probe 失败会重启、摘流量、降级还是只告警？
7. 谁抓取/保存/查询，保留多久，网络权限是什么？
8. 对应 runbook 如何从症状追到 durable state？
