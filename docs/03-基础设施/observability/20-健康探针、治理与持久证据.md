# 健康探针、治理与持久证据

## 1. 当前结论

`/healthz`、`/readyz`、`/serve-readyz`、`/metrics` 和 governance endpoint 表达不同状态。返回 200 只能按 handler 实际检查项解释，不能扩大为“服务、依赖、数据和业务全链健康”。生产结果必须进入 dated、exact-SHA 的证据台账。

本页是 `observability/probes` 主题的 canonical 文档。

## 2. 当前探针语义

| 进程/端点 | 当前判断 | 返回非 2xx 的条件 | 没有覆盖 |
| --- | --- | --- | --- |
| apiserver `/health` | 固定结构的 `healthy` | 无 | MySQL、Mongo、Redis、IAM、MQ、模块 |
| apiserver `/healthz` | Generic server 静态 `ok`（配置开启时） | 无 | 全部依赖 |
| apiserver `/readyz` | Redis runtime summary | summary `Ready=false` | DB、IAM、MQ；status service 异常还会 fallback ready |
| collection `/health` | 固定 `healthy` + Redis snapshot | 无 | apiserver/IAM 可达性、业务 handler |
| collection `/readyz` | Redis summary + resilience control 初次同步 | Redis not ready 或 control 未同步 | apiserver gRPC、IAM、完整业务路径 |
| collection `/serve-readyz` | resilience control 初次同步；同时披露 Redis summary | control 未同步 | Redis degraded 时仍可返回 200；不证明完整业务路径 |
| worker `/healthz` | 固定 `healthy` + Redis snapshot | 无 | MQ consumer、apiserver gRPC、DB |
| worker `/readyz` | Redis runtime summary | summary `Ready=false` | MQ、consumer registration、gRPC、业务 handler |

`configs/apiserver.prod.yaml` 的 `grpc.healthz-port: 9091` 当前不是独立 HTTP health listener 的代码事实；部署探针应以真实监听和标准 gRPC Health 为准。

## 3. Governance 与 deep check

governance endpoint 汇总本地/远程 runtime snapshot、Prometheus 窗口和持久 checkpoint。它们是诊断投影，不是业务事实源。正确使用顺序：

```text
liveness/readiness alert
  -> 逐实例与入口探针
  -> runtime/governance snapshot（configured/degraded/synchronized）
  -> metrics 窗口与日志关联
  -> Outbox / checkpoint / retry-hold / dead-letter /业务实体查询
  -> 必要时执行只读 audit
```

远程组件不可用应表达 `available=false`/错误类别，不能伪装成指标为 0。deep check 应有超时、限流和访问控制，不能放大故障。

## 4. 持久证据层

| 证据 | 适用问题 | 风险 |
| --- | --- | --- |
| business fact + version | 业务写是否提交、当前状态 | 只查一个聚合可能漏跨库异步状态 |
| durable Outbox | 可靠事件是否与事实同事务持久化、是否发布 | Outbox 存在不等于 consumer 已结算 |
| checkpoint / SyncRun | scheduler/长任务推进到哪里 | stale running 需要具名恢复语义 |
| retry hold / dead letter | 自动重试为何停止、是否需人工处理 | replay 必须授权、幂等和审计 |
| action audit | 谁在何时执行治理动作 | 审计记录不自动证明动作结果正确 |

Statistics coordinator 的失败结算复用请求 context，context 已取消时可能无法把 run 标失败；修复与 stale-run recovery 演练完成前，这一项保持 gap。

## 5. 环境验收

1. 逐实例而非只经负载均衡请求探针，记录镜像 digest 与 effective-config hash；
2. 对 Redis、MySQL、Mongo、IAM、MQ 分别做受控故障，确认每个 endpoint 的状态与文档一致；
3. 验证 worker 9092、profile/governance 端点的允许采集与非授权拒绝；
4. 验证 Prometheus 抓取、alert/query 和日志关联，但不把一次 scrape 作为持续健康；
5. 用真实持久状态复核 probe/governance 结论，保存查询和时间窗；
6. 证据记录 `observed_at`、deployed SHA、effective config、owner、limitations 和 `expires_on`。

## 7. 未闭合 gap

- apiserver readiness fail-open 且依赖覆盖窄，需要修正或在入口另设严格 serving readiness。
- `grpc.healthz-port` 配置与当前实现不一致。
- worker 管理端点缺少与当前 checkout 绑定的生产网络反向证据。
- Statistics stale running 的结算/恢复语义未闭环。
- 当前 checkout 无 CI、部署、effective config 和生产窗口证据；历史结果只能作为 dated evidence。
