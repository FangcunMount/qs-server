# 可观测性、压测与验收

## 1. 结论

Concurrency / Resilience 验收必须区分四层证据：

1. 仓库版本化配置说明“代码准备按什么预算装配”；
2. runtime snapshot 说明“当前实例暴露了什么状态”；
3. Prometheus 时间窗口说明“过去一段时间发生了哪些决定和等待”；
4. 隔离环境故障注入与压测说明“在明确拓扑下是否守住业务不变量”。

任何单层都不能独立证明目标环境安全容量。尤其要避免两种误读：

- `*.prod.yaml` 是仓库配置意图，不是已部署 effective config；
- LockLease snapshot 当前展示 catalog DefaultTTL，不是 caller override 或 active run effective TTL。

## 2. 证据分层

| 证据 | 回答什么 | 不能证明什么 |
| --- | --- | --- |
| 仓库配置 | baseline QPS、burst、inflight、timeout、action flag 的版本化意图 | 目标环境已采用、容量安全 |
| Runtime snapshot | policy source/version、当前 in-flight、Redis family、LockLease catalog capability | 历史峰值；LockLease caller/active TTL |
| Prometheus 时间窗口 | reject/timeout 增量、wait histogram、阶段延迟、故障频率 | 未被 scrape 的瞬时状态、单个业务事实 |
| Unit/miniredis test | 分支、状态机和适配器契约 | 真实网络、真实数据库与多实例行为 |
| 隔离环境验收 | 指定 SHA/配置/拓扑下的吞吐、尾延迟、故障与恢复 | 其他拓扑或未来版本自动成立 |

system governance projector 会合并 component snapshot 与 Prometheus evidence。
Backpressure utilization 当前按 `in_flight / max_inflight` 计算，`>=0.8` warning，`>=0.9` critical。

## 3. 核心指标

### 3.1 统一决策

```text
qs_resilience_decision_total{
  component,
  kind,
  scope,
  resource,
  strategy,
  outcome
}
```

当前主要用于区分：

- RateLimit allowed / limited / degraded-open；
- Backpressure acquired / released / timeout；
- LockLease acquired / contention / error；
- duplicate skipped。

查询必须带足够 label，避免把不同 component、scope、resource 和 strategy 合成一个数字。

### 3.2 Gate 与可靠提交

| 指标 | 当前含义与边界 |
| --- | --- |
| `collection_http_gate_wait_seconds` | collection HTTP Gate 等待；没有 route/gate label |
| `collection_grpc_inflight_wait_seconds` | collection 到 apiserver gRPC 槽位等待 |
| `qs_collection_submit_gate_reject_total` | submit Gate 进入统一 reject callback 的次数 |
| `qs_collection_answersheet_submit_total{outcome}` | collection durable accept 结果 |
| `qs_collection_answersheet_submit_stage_duration_seconds{stage,outcome}` | envelope、preflight、identity、ProfileLink、gRPC、total 等阶段耗时 |
| `qs_apiserver_answersheet_durable_submit_total{outcome}` | apiserver created、idempotency hit/conflict、failed |
| `qs_apiserver_answersheet_durable_stage_duration_seconds{stage,outcome}` | Mongo transaction、Outbox 等 durable 阶段耗时 |

`qs_collection_submit_gate_reject_total` 不能被精确解释为“等待 50ms 后容量饱和”：`WaitStrategy` 在 request context cancellation 和槽位等待超时时都进入同一个 reject callback。
当前 counter 没有 reason label；诊断时要同时查看请求取消、HTTP route 指标和 Gate wait。

### 3.3 Backpressure

| 指标 | 含义 |
| --- | --- |
| `qs_resilience_backpressure_inflight` | 当前接入共享 limiter 的依赖在途数 |
| `qs_resilience_backpressure_wait_duration_seconds{outcome}` | 取得槽位或 timeout 前的等待 |
| `qs_resilience_decision_total{kind="backpressure",...}` | acquired/released/timeout 次数 |

Backpressure 指标只覆盖显式调用 limiter acquire 的方法，不能按“limiter 已注入 repository”推导全方法覆盖。
MySQL Actor read model 经 `WithContext()` 直接查询、assessment MySQL Outbox Store 直接使用 GORM DB；
Mongo AnswerSheet read model/repository 经 `Collection()` 直接 `Aggregate` / `CountDocuments` / `FindOne`。
诊断 DB 总压力时必须关联 driver pool、Outbox backlog、worker 并发和方法级覆盖清单；不能把 limiter 指标当作进程全部 MySQL/Mongo 使用量。

### 3.4 LockLease

```text
qs_locklease_operation_total{
  component,
  name,
  operation,
  result
}
```

需要同时观察：

- acquire error 与 contention；
- renew lost / failed；
- release error；
- active runs；
- Redis lock family degraded；
- body cancellation 后未退出告警。

runtime snapshot 的 `ttl_seconds` 与 `renew_every_seconds` 当前来自 catalog DefaultTTL。
例如 `plan_scheduler_leader` 的 snapshot 是默认 50s/约 16s，而仓库 `apiserver.prod.yaml` 的 caller 配置意图是 2m；snapshot 不能证明 active run 使用哪一个 TTL。

### 3.5 Control action 与审计恢复

当前没有专用的统一 control-operation Prometheus counter，无法用单一指标覆盖完整治理事务。控制面操作结果仍必须从审计、state/command、snapshot 和日志组合判断。

现有直接指标包括 terminal audit fallback 和 command poll 两个维度：

| 指标 | 含义 |
| --- | --- |
| `system_governance_audit_fallback_pending` | 等待回填 MySQL 的 terminal audit 数 |
| `system_governance_audit_fallback_total{operation,outcome}` | fallback load/put/list/delete 结果 |
| `qs_resilience_control_command_poll_total{trigger,outcome}` | apiserver 因 startup/signal/recovery 触发命令检查的成功或失败次数 |

command poll 指标不能证明命令存在、被 claim 或 data-plane effect 成功；fallback 指标也不能证明 Redis state 或 effect。
治理排障仍要读取 MySQL action audit、Redis state/version、command result、逐实例 snapshot 和日志。精确提交顺序见 [运行时治理与故障恢复](./60-运行时治理与故障恢复.md)。

## 4. 症状到责任层

| 症状 | 首先检查 | 不应直接下的结论 |
| --- | --- | --- |
| submit 429 增长，RateLimit limited 不增长 | Gate reject、request cancellation、stage latency、gRPC wait | 不能只凭 reject counter 断言 Gate 容量不足 |
| RateLimit limited 增长，Gate wait 很低 | global/user scope、热点 key、客户端重试 | 不能据此提高 Gate |
| `degraded_open` 增长 | Redis rate backend/family、local fallback、下游 Gate/BP | 不表示业务正确性已经失败 |
| gRPC wait 上升 | collection gRPC inflight、apiserver latency | 不一定是 Mongo 单点问题 |
| Mongo BP timeout 增长 | Mongo operation latency、driver pool、Outbox backlog | 不等同于 HTTP QPS 过高 |
| durable transaction failed 增长 | Mongo error、unique conflict、unknown commit recovery | 503 不等于一定没有 commit |
| idempotency hit 增长 | 客户端 timeout/retry、重复 key | 可能是合法重试，也可能是重试螺旋 |
| lock contention 增长但业务吞吐正常 | workload/key 分布 | 单 owner workload 的 contention 可能正常 |
| lock renew failure/lost | Redis、网络、caller TTL、body 时长 | snapshot 默认 TTL 不是 active TTL 证据 |
| governance action error/timeout | audit、Redis state/command、target effect/result | error 不等于没有效果 |

## 5. 容量与故障验收原则

每次验收至少记录：

- commit SHA、镜像、仓库配置与目标环境 effective config；
- collection/apiserver/worker 实例数和资源规格；
- DB/Redis/MQ 拓扑；
- token、测试用户与数据规模；
- QPS profile、持续时间、VUs；
- cache 是否预热；
- 客户端 timeout、retry 和退避；
- 压测前后 snapshot、Prometheus 窗口和业务事实计数。

推荐按 smoke、单场景、稳态、burst、混合场景、实例故障、依赖故障、恢复的顺序逐层增加变量。每轮只改变一个主要变量，才能解释拐点来自哪一层。

验收不仅看 HTTP 成功率，还必须回答：

1. 哪个保护层做了允许、等待、拒绝或降级决定？
2. 目标吞吐下 P95/P99 和依赖余量是否可接受？
3. AnswerSheet、Outbox、幂等事实是否一致？
4. 停止 burst 或恢复依赖后，backlog、policy 和 error rate 是否回落？
5. 429/503 是否触发客户端重试放大？

## 6. 当前验证入口

标准入口：

```bash
make perf-run PLAN=baseline
make perf-run PLAN=admission
make perf-verify
```

SubmitCoalescer 专项仍通过 diagnose registry 运行；本文只保留稳定入口，具体参数和阈值以 `scripts/perf/README.md`、runner 与 K6 脚本为准：

```bash
scripts/perf/run-submit-coalescing.sh --help
make perf-run PLAN=diagnose CASE=submit-coalescing-healthy
make perf-run PLAN=diagnose CASE=submit-coalescing-conflict
make perf-run PLAN=diagnose CASE=submit-coalescing-redis-lock-failure
make perf-run PLAN=diagnose CASE=submit-coalescing-redis-signal-failure
make perf-run PLAN=diagnose CASE=submit-coalescing-redis-unavailable
```

collection 双实例运行时验收入口：

```bash
scripts/perf/run-collection-runtime-acceptance.sh --help
make perf-run PLAN=diagnose CASE=collection-runtime-status
make perf-run PLAN=diagnose CASE=collection-runtime-healthy-smoke
make perf-run PLAN=diagnose CASE=collection-runtime-healthy
make perf-run PLAN=diagnose CASE=collection-runtime-degraded-low
make perf-run PLAN=diagnose CASE=collection-runtime-degraded-global
make perf-run PLAN=diagnose CASE=collection-runtime-degraded-user
make perf-run PLAN=diagnose CASE=collection-runtime-recovery
```

这些 runner 遵守以下边界：

- 不停止、隔离或恢复 Redis；故障注入必须由经过评审的独立步骤完成；
- 精确全局 counter delta 只允许在隔离窗口使用，并由流量分类证据辅助判断；
- HTTP 行为 smoke 可以关闭 metrics 精确验证，但不能据此声称 transaction/readback 数量通过；
- 必须从本次部署证据给出预期副本数，并验证各实例地址、`/readyz`、`/serve-readyz` 和 `/metrics`；
- 每次写测试使用新的 idempotency key，并记录会创建真实 durable AnswerSheet 的副作用；
- Redis 故障场景应守住 Mongo 最终幂等，不把 lease/signal 故障映射成重复业务事实；
- 恢复场景必须证明 local fallback 不再增长、distributed Redis decision 恢复增长。

完整环境准备和结果解释见 [300QPS 混合场景压测 SOP](../../04-接口与运维/11-300QPS混合场景压测SOP.md)。脚本 target 名称只是输入档位，不是容量结论。

## 7. 故障验收矩阵

| 场景 | 必验不变量 | 预期证据 |
| --- | --- | --- |
| Submit Gate 饱和 | 已受理请求不因后续请求取消 | bounded reject、无额外 AnswerSheet；区分 cancellation |
| RateLimit 饱和 | 不误报 409/503 | 429、Retry-After、limited label |
| Redis rate 故障 | 小流量仍可受理，正确性不变 | degraded-open/local fallback、下游保护接管 |
| 同 key 同内容风暴 | 只形成一个 durable AnswerSheet 事实 | 相同 AnswerSheet ID、transaction/readback 证据 |
| SubmitCoalescer Redis 故障 | 同 key 同内容仍只一份 AnswerSheet | degraded-open、Mongo idempotency hit |
| 同 key 不同内容 | 只承认一个 fingerprint | 一方 202，另一方 409 |
| Mongo 饱和 | 不返回无 durable 结果的 202 | BP timeout/503、transaction metric、事实计数 |
| worker lock 故障 | handler 可重入，不制造重复最终事实 | degraded-open、消费与业务幂等证据 |
| lease loss | body 收到 cancellation | renew lost/error、body 退出与后续副作用核对 |
| control Pub/Sub 丢失 | 最终仍应用 versioned state | 周期 reconcile 后逐实例 version 收敛 |
| tune local apply 失败 | state 与 terminal error 可分离 | Redis version、逐实例 snapshot、audit failed |
| release command timeout | 不把 timeout 当作无效果 | cooldown、active run、延迟 command result |
| MySQL action complete 故障 | 同 request ID 不重复执行 | Redis fallback、recovery 回填 |

## 8. 容量验收模板

| 维度 | 验收问题 |
| --- | --- |
| Throughput | 稳态完成量是否达到目标，而不是只看发送量？ |
| P95/P99 | 尾延迟是否处于 SLO，升压后是否出现拐点？ |
| Reject/timeout | 哪一层拒绝，能否区分容量、取消和依赖错误？ |
| Dependency utilization | DB/Redis/IAM 是否仍有恢复余量？ |
| In-flight/wait | 是否持续贴顶，是否有等待或 release 泄漏？ |
| Correctness | AnswerSheet、幂等记录、Outbox 数是否一致？ |
| Recovery time | 停止 burst/故障后多久回到基线？ |
| Retry amplification | 429/503 后客户端发送量是否继续上升？ |

缺少 correctness 与 recovery 证据时，只能说明“短时间跑过”，不能说明系统可靠。

## 9. 文档与代码门禁

文档变更至少运行：

```bash
make docs-hygiene
make docs-facts
```

相关代码契约测试必须禁用 Go test cache：

```bash
go test -count=1 ./internal/pkg/resilience/...
go test -count=1 ./internal/collection-server/concurrency/... \
  ./internal/collection-server/resilience/... \
  ./internal/collection-server/infra/redisops/... \
  ./internal/collection-server/application/answersheet/... \
  ./internal/collection-server/transport/rest/...
go test -count=1 ./internal/apiserver/resilience/... \
  ./internal/apiserver/application/systemgovernance/... \
  ./internal/apiserver/application/survey/answersheet/...
```

Mongo integration test 需要真实 replica set 和权限；只通过 unit test、miniredis 或编译不能声称 transaction/idempotency E2E 已验证。

## 10. 当前证据缺口

| 状态 | 缺口 |
| --- | --- |
| `观测缺口` | HTTP Gate wait 缺 route/gate label；submit reject 缺 timeout/cancellation reason。 |
| `观测缺口` | MySQL `WithContext` / GORM DB 与 Mongo `Collection` 直连方法可旁路 acquire；Backpressure 指标只表示已显式接入的方法，不是全部 MySQL/Mongo 并发。 |
| `观测缺口` | LockLease snapshot 只投影 catalog DefaultTTL，不展示 caller/active effective TTL。 |
| `观测缺口` | 没有专用 control-operation counter；治理效果需组合多类证据。 |
| `待环境验收` | Redis degraded submit、双实例 SubmitCoalescer 与恢复脚本需要隔离环境结果。 |
| `待补证据` | 目标环境自动续租 effective value、renew error/lost、取消传播和长任务退出时间。 |
| `待补证据` | 部署 SHA、实例拓扑、effective config 和 Prometheus 窗口尚不能由仓库文档替代。 |
